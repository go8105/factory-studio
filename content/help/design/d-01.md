# 여섯 솔루션을 독립 제품으로 나눈 이유

## 결정
MES(생산)·ERP(경영)·FEMS(에너지)·QMS(품질)·WMS(창고)·BEMS(건물)를 **각자 데이터를 소유하는 독립 솔루션**으로 만들었습니다. 공유하는 것은 로그인·개인 공간·데이터 세대 같은 플랫폼 계층뿐입니다.

- 업무 데이터 사이에는 **외래키가 0건**입니다. 품목·설비가 여러 솔루션에 따로 있어도 결함이 아니라 설계입니다.
- 다른 솔루션의 값이 필요하면 **읽기 전용 조회 함수**로 읽고, 그 시점의 값(코드·수량)을 복사해 둡니다. 쓰기와 테이블 직접 조회는 금지합니다.
- 물리적으로는 PostgreSQL 한 대, 스키마 7개(플랫폼 1 + 업무 6), API 서버 1개입니다.

## 검토한 대안
| 대안 | 버린 이유 |
|---|---|
| 하나의 통합 DB에 모든 업무를 FK로 연결 | 실제 공장은 MES와 ERP를 다른 회사 제품으로 쓰는 경우가 많습니다. 통합 DB로 보여 주면 "연계"라는 가장 어려운 문제를 건너뛰게 됩니다 |
| 솔루션마다 DB 인스턴스 분리 | 게스트 공간을 한 번에 복사하려면 여러 DB에 걸친 분산 트랜잭션이 필요합니다. 이 규모에서는 비용이 이득보다 큽니다 |
| 공통 품목 마스터 하나 | 한 솔루션을 끄거나 바꾸면 다른 솔루션이 깨집니다. 독립이라는 설명이 성립하지 않습니다 |

## 선택 이유
- **솔루션을 끄고 켤 수 있어야 독립입니다.** 내 공간에서 MES를 꺼도 ERP는 품목과 수량만으로 출하합니다. QMS를 꺼도 MES는 그대로이고 보류 배지만 사라집니다.
- **연계 지점이 눈에 보입니다.** MES 팔레트 번호를 ERP 출하에 붙여 넣고, WMS가 MES·ERP 확정 기록을 읽어 "반영"을 누르는 식으로, 실제 운영에서 인터페이스가 필요한 자리를 화면으로 드러냅니다.
- 조회 함수는 제공하는 솔루션이 계약을 소유합니다. 내부 테이블이 바뀌어도 함수가 유지되면 읽는 쪽은 영향이 없습니다.

## 한계
- 같은 DB 인스턴스라 **스키마 간 FK를 물리적으로 막을 수단이 없습니다.** 경계는 자동 검사(업무 스키마 간 FK 0건, 플랫폼→업무 FK 0건, 다른 솔루션은 조회 모듈만 가져오기 등)로만 지킵니다.
- 마스터가 중복됩니다. 시드는 같은 코드를 각 솔루션에 심어 두지만, 사용자가 한쪽에서만 품목을 바꾸면 어긋납니다. 실제 운영이라면 마스터 연계 인터페이스가 필요합니다.
- 복사한 값은 원본이 나중에 바뀌어도 따라가지 않습니다(의도한 동작이지만, 실시간 동기화가 아님).
