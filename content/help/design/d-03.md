# 데이터 모델 원칙 — 범위 키·복합 참조·확정 불변

## 결정
- **범위 키:** 모든 업무 행은 (공간, 세대)를 가집니다. 업무 외래키는 모두 **(공간, 세대, 참조 id)** 복합 참조입니다. 다른 공간의 행을 가리키는 것이 스키마 수준에서 불가능합니다.
- **달력 값은 문자열:** 연월은 `YYYY-MM`, 주차는 `YYYY-Www`로 저장하고 형식을 CHECK로 강제합니다.
- **삭제는 막는다:** 참조된 행은 지우지 못합니다(RESTRICT). 쓰인 기준정보는 삭제 대신 "사용 안 함"으로 둡니다. 삭제를 거부할 때는 참조처별 건수를 알려 줍니다.
- **확정·게시한 것은 바꾸지 않는다:** 실적·전표·출하·검사 판정은 확정 후 수정하지 않습니다. 고칠 일이 있으면 되돌림 전표나 새 버전(정정)을 만듭니다.

## 검토한 대안
| 대안 | 버린 이유 |
|---|---|
| id만으로 참조 | 코드 실수 하나로 다른 방문자의 데이터를 가리킬 수 있습니다 |
| 연월을 정수·날짜로 저장 | 정렬·표시·복사 때 해석이 흔들립니다(예: 2026-9 vs 202609) |
| 확정 데이터 직접 수정 허용 | 매출과 채권, 원장과 재고처럼 서로 맞물린 값이 어긋납니다. 수정 이력도 사라집니다 |

## 선택 이유
- 규칙을 **DB가 지킬 수 있는 것은 DB 제약으로** 둡니다. 현재 93테이블·954컬럼에 외래키 209, 제약 615건(기본키 93·유일 208·조건부 유일 16·CHECK 239·인덱스 59)입니다.
- DB 한 행만 봐서는 판단할 수 없는 규칙(합계 한도, 겹침, 상태 전이)은 **서비스 정책 111건**으로 따로 적고 트랜잭션 안에서 검사합니다. 설계서에서 둘을 구분해 적어, 무엇이 DB 제약이고 무엇이 코드인지 헷갈리지 않게 했습니다.

## 한계
- 서비스 정책은 DB 제약이 아니므로 **DB에 직접 쓰면 막지 못합니다.** 시드는 생성기 검증으로, 제품은 API 경유로만 지킵니다.
- 복합 키 때문에 테이블마다 (공간, 세대, id) 유일키가 하나씩 더 있고, 쿼리가 길어집니다.
- NULL이 섞인 유일 조건은 일반 유일 제약으로 막히지 않아 조건부 유일 인덱스나 서비스 검사로 보완합니다.
