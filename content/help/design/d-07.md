# 어떻게 검증했나 — 정책·수용 기준·스모크

## 결정
기능마다 **실제 DB에 대고** 결과를 확인합니다. 문법 검사나 화면 시제품만으로 완료로 치지 않고, 실행하지 않은 검증은 "미실행"으로 적습니다.

| 층 | 무엇을 | 현재 규모 |
|---|---|---|
| 백엔드 통합 테스트 | API → PostgreSQL. 게스트 공간을 만들어 시드 위에서 업무를 실행 | 724 통과 · 1 건너뜀 |
| 프런트 단위 테스트 | 화면 규칙·오류 안내·패널 동작 | 481 통과 |
| 브라우저 스모크 | 실제 서버 + 새 게스트 공간에서 화면 흐름 | 231 통과 · 1 건너뜀 |
| 설계 검증 | 스키마 메타데이터와 실제 DB 카탈로그 대조, 스키마 격리 규칙 | 오류 0 |

## 검토한 대안
| 대안 | 버린 이유 |
|---|---|
| 목(mock) DB로 빠른 테스트 | 복합 외래키·조건부 유일·동시 잠금 같은 핵심 규칙은 실제 DB에서만 드러납니다 |
| 수동 확인만 | 솔루션 여섯 개가 서로 영향을 주는지 매번 사람이 볼 수 없습니다 |

## 선택 이유
- **동시성은 흉내 내지 않고 실제로 동시에 보냅니다.** 두 연결에서 같은 순간 요청해 한쪽만 성공하는지 확인합니다.
- 수용 기준을 표로 추적했습니다. 한 차례 통합 점검에서 46건 중 검증 33·부분 5·미구현 4·폐기 4로 판정했고, 그때 결함 1건(쓰기 잠금을 기다리는 사이 게스트 공간이 만료되면 쓰기가 통과하던 문제 — 잠금 뒤 만료를 다시 확인하도록 수정)을 찾아 고쳤습니다. 부분·미구현은 숨기지 않고 범위 밖으로 기록했습니다.
- 스키마 설계서(메타데이터)와 실제 DB가 어긋나지 않는지 자동 대조합니다. 설계서가 곧 DB입니다.
