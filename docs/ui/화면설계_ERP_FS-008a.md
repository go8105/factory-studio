# FS-008a ERP 화면 설계

작성일: 2026-09-22
전제: [FS-013 전환 결정](../plan/독립솔루션_전환결정_FS-013.md) · 스키마 v0.8.0 / FS-014b (`erp` 27테이블)
선행: [포털 화면 설계](화면설계_포털_FS-008a.md) 6장의 공통 규격을 따른다.
성격: **스토리보드 3차 — ERP.** MES가 마지막이다.

---

## 1. ERP는 무엇을 보여주는가

**돈의 흐름을 끝까지 닫는다.** 견적에서 시작해 매출로 끝나지 않고, 채권·수금까지 가서 잔액이 0이 되는 것을 보여준다.

```
견적 → 판매계획 → 수주 → 출하지시 → 출하 → 매출 인식
                                          ↓
                            세금계산서 · 매출채권 → 수금 → 소명
매입 전표 → 매입채무 → 지급 → 소명
                    ↓
              분개 미리보기 (저장 안 함)
```

이 솔루션의 판단 기준은 **"채권 잔액이 맞는가"** 하나다. 매출 100, 수금 60이면 잔액 40이 어느 화면에서도 같게 나와야 한다. 잔액을 컬럼으로 저장하지 않고 집계로 산출하는 이유가 여기 있다(FS-014b).

### 범위 밖 (설명 카드로 처리)

결산 · 재무제표 · 원가계산 · 고정자산 · 예산 · 구매발주 · 입고검수 · 대손 · 역분개 · 선수금 · 외화 · 전자세금계산서 연동.

**화면에서 이 목록을 숨기지 않는다.** 회계 영역에 "1차 범위에서 제외한 것" 안내를 두고 이유를 적는다. 반쯤 맞는 재무제표보다 제외 사유를 말하는 쪽이 낫다는 것이 D7의 판단이었다.

## 3. 대시보드

### E-01 대시보드

| 항목 | 내용 |
|---|---|
| 목적 | 이번 달 매출과 미수금을 3초 안에 파악한다 |
| 데이터 | `sales_record` `receivable` `receipt_apply` `sales_order` `payable` |

```
┌──────────────────────────────────────────────────┐
│ 경영 개요                              [당월 ▾]   │
├──────────────────────────────────────────────────┤
│ ┌────────┐ ┌────────┐ ┌────────┐ ┌────────┐      │
│ │ 당월매출│ │ 미수금 │ │ 미지급 │ │ 수주잔 │      │
│ └────────┘ └────────┘ └────────┘ └────────┘      │
├──────────────────────────────────────────────────┤
│ 월별 매출 추이            │  거래처별 미수금 상위 5 │
├──────────────────────────────────────────────────┤
│ 판매계획 대비 실적         │  처리 대기            │
│ (계획 vs 매출)            │  · 미발급 세금계산서 n │
│                          │  · 미소명 수금 n       │
└──────────────────────────────────────────────────┘
```

- **미수금 = Σ(채권 원금) − Σ(소명액).** 집계로 산출한다. 캐시 컬럼 없음.
- "처리 대기"는 다음 행동을 만드는 영역이다. 대시보드가 숫자만 보여주고 끝나면 평가자가 클릭할 곳이 없다.
- 판매계획 대비 실적은 `sales_plan_line.plan_qty`와 `sales_record`를 월 단위로 비교한다.

## 4. 영업

### E-02 견적

| 항목 | 내용 |
|---|---|
| 데이터 | `quotation` `quotation_line` `quotation_status_history` `partner` `item` `partner_item_price` |

- **개정 이력이 이 화면의 볼거리다.** `revision_no`로 버전을 쌓고 `quotation_status_history`로 상태 변경을 남긴다. 이전 개정본을 읽기 전용으로 열 수 있어야 한다.
- 품목 선택 시 `partner_item_price`에서 **해당 거래처·해당 시점 단가를 자동으로 끌어온다.** 사용자가 수정하면 그 값이 `quotation_line.unit_price`에 스냅샷으로 남는다. 마스터 단가가 나중에 바뀌어도 과거 견적은 변하지 않는다.
- 단가 자동 적용 시 **출처를 표시한다** — "거래처 단가 적용" / "수동 입력". 어디서 온 숫자인지 보이지 않으면 신뢰가 안 생긴다.
- 상태 전이: 작성 → 제출 → 수주전환 / 실효. 수주로 전환된 견적은 수정 불가.

### E-03 판매계획

| 항목 | 내용 |
|---|---|
| 데이터 | `sales_plan` `sales_plan_line` `item` |

- `target_month`는 `'YYYY-MM'` 문자열이다. 월 선택기는 문자열로 질의한다.
- 확정(`confirmed_at`) 후에는 수정 불가. 변경은 새 계획으로.
- **MES 생산계획이 이 계획을 참조한다.** 다만 FS-013에서 FK를 끊고 `sales_plan_code` 문자열로 바꿨으므로, ERP 화면에서 "이 계획이 MES에서 쓰이고 있는지"는 알 수 없다. 단방향이다.
- 이 사실을 화면에 명시한다. "독립 솔루션이라 연계는 코드 기준입니다"를 감추지 않는다.

### E-04 수주

| 항목 | 내용 |
|---|---|
| 데이터 | `sales_order` `sales_order_line` `quotation` `partner` |

- 견적에서 전환하거나 직접 등록한다. `quotation_id`는 nullable이므로 **견적 없는 수주가 정상 경로다.**
- 수주 명세별 **출하 진행률**을 표시한다. `shipment_order_line`과 `shipment_line`을 역추적해 "10개 중 6개 출하"를 보여준다.
- `due_on`은 **납품 기일이지 결제 만기가 아니다.** 이 구분이 채권 관리에서 문제가 된다(갭 E-G02).

## 5. 출하·매출

### E-05 출하지시 / E-06 출하

| 항목 | 내용 |
|---|---|
| 데이터 | `shipment_order` `shipment_order_line` `shipment` `shipment_line` |

- 출하지시는 수주 명세에서 수량을 배정한다. 배정 합계가 수주 수량을 넘을 수 없다.
- **출하 명세의 패킹 정보는 `packing_no` 문자열이다.** FS-013에서 `mes.packing_unit` FK를 제거했다. 따라서 MES 패킹 목록을 조회해 고를 수 없고 **수기 입력**이다.
  - 화면에 이유를 적는다. "MES와 독립이므로 패킹번호는 직접 입력합니다. 실제 운영에서는 인터페이스로 연계합니다."
  - 오타를 막을 방법이 없다는 것이 설계상 비용이다(갭 E-G04).
- **품목·수량만으로도 출하가 성립한다.** MES 없이 ERP만 써도 흐름이 끊기지 않는 것이 독립 솔루션의 증명이다.
- 출하 확정(TX-08) 시 매출이 함께 생성된다(TX-09).

### E-07 매출

| 항목 | 내용 |
|---|---|
| 데이터 | `sales_record` `shipment` `partner` |

- 공급가액 · 세액 · 합계를 표시한다. 통화는 KRW 단일.
- **확정 후 금액 수정 불가.** 취소는 상위 거래 취소로만 가능하며, 다음 조건을 모두 만족해야 한다.
  - 유효 소명 **0행**
  - 세금계산서가 **발급대기면 함께 삭제**, **발급완료면 취소 금지**
- 취소 버튼을 조건 미충족 시 비활성화하고 **막힌 이유를 툴팁에 쓴다.** "취소할 수 없습니다"만 띄우면 사용자가 다음 행동을 못 정한다.
- 매출 확정 시 채권이 자동 생성된다. **채권 수기 등록 경로는 없다**(FS-014b).

### E-08 세금계산서

| 항목 | 내용 |
|---|---|
| 데이터 | `tax_invoice` `sales_record` `partner` |

- **매출 1건 : 세금계산서 1건.** 월합계 방식은 채택하지 않았다.
- 국세청 연동 없음. **승인번호와 발급일자를 수기 입력**한다.
- 상태 2종: 발급대기 / 발급완료. 발급취소 상태는 없다.
- 선발행 불가. 매출 인식이 선행해야 생성 가능하다.
- 화면에 "실제 운영에서는 전자세금계산서 연동이 필요하며 1차 범위에서 제외했다"를 명시한다.

## 6. 채권·수금

이 영역이 ERP를 ERP로 만드는 부분이다.

### E-09 매출채권 현황

| 항목 | 내용 |
|---|---|
| 데이터 | `receivable` `receipt_apply` `partner` `sales_record` |

```
┌─────────────────────────────────────────────────────┐
│ 매출채권 현황        [거래처 ▾] [상태 ▾] [기간 ▾]    │
├─────────────────────────────────────────────────────┤
│ 거래처      원금      소명액     잔액     상태        │
│ (주)가나   1,000,000   600,000  400,000  일부회수    │
│ (주)다라     500,000   500,000        0  회수완료    │
│ (주)마바     300,000         0  300,000  미회수      │
├─────────────────────────────────────────────────────┤
│ 합계       1,800,000 1,100,000  700,000              │
└─────────────────────────────────────────────────────┘
```

- **상태는 저장 컬럼이 아니라 잔액에서 파생한다.**
  - 잔액 = 원금 → 미회수
  - 0 < 잔액 < 원금 → 일부회수
  - 잔액 = 0 → 회수완료
- 원금 0원인 채권은 **회수완료를 우선**한다(FS-014b 명시).
- 행을 펼치면 소명 이력(어느 수금에서 얼마가 붙었는지)이 나온다.
- **연령분석(aging)은 이번 범위에서 제공하지 않는다.** 만기일 기준이 없기 때문이다(갭 E-G02).

### E-10 수금 등록·소명

**ERP에서 가장 조작이 복잡한 화면이다.** 여기가 어색하면 회계를 이해 못한 것처럼 보인다.

| 항목 | 내용 |
|---|---|
| 데이터 | `receipt` `receipt_apply` `receivable` |

```
┌──────────────────────────────────────────────────────┐
│ 수금 등록                                             │
│ 거래처 [(주)가나 ▾]  수금액 [1,200,000]  일자 [...]   │
├──────────────────────────────────────────────────────┤
│ 소명 대상 채권                    [FIFO로 채우기]     │
│ ☑ 2026-08 매출  원금 1,000,000  잔액 1,000,000       │
│                             소명액 [1,000,000]        │
│ ☐ 2026-09 매출  원금   500,000  잔액   500,000       │
│                             소명액 [        0]        │
├──────────────────────────────────────────────────────┤
│ 수금액 1,200,000 = 소명 1,000,000 + 미소명 200,000   │
│                                        [저장]         │
└──────────────────────────────────────────────────────┘
```

핵심 동작 4가지:

1. **FIFO는 기본 제안일 뿐이다.** 버튼을 눌러야 채워지고 사용자가 수정할 수 있다. 자동 확정하지 않는다. 거래처가 "8월 건 입금"이라고 지정하는 실제 패턴을 표현해야 한다.
2. **과입금을 막지 않는다.** 소명 합계보다 수금액이 크면 미소명 잔여로 남긴다. 화면 하단에 항상 `수금액 = 소명 + 미소명` 등식을 보여준다.
3. **확정 후에도 소명 추가·취소가 가능하다.** 확정되는 것은 수금액이지 배분이 아니다. 미소명 200,000원을 나중에 다른 채권에 붙일 수 있어야 한다.
4. **소명 취소는 물리 삭제다.** 이력은 `core.audit_event`에 남는다. 취소 시 "이 기록은 운영 기록에 남습니다" 안내를 둔다.

제약 표시:

- `Σ소명액 ≤ 수금액`과 `Σ소명액 ≤ 채권 원금`은 **DB 제약이 아니라 SERVICE 정책이다.** 여러 행을 참조하므로 일반 CHECK로 표현할 수 없다. 화면에서 실시간 검증하되, 서버 검증이 최종이다.
- 저장 시 서버가 재계산해 초과하면 전체 롤백하고 **어느 채권이 초과했는지** 알려준다.

### E-11 ~ E-13 매입·채무·지급

매출 쪽과 **대칭 구조**다. 화면 패턴을 그대로 재사용한다.

| 화면 | 대응 |
|---|---|
| E-11 매입 전표 | E-07 매출에 대응. `purchase_invoice` + `purchase_invoice_line` |
| E-12 매입채무 현황 | E-09에 대응. 파생 상태 동일 |
| E-13 지급 등록·소명 | E-10에 대응. 동작 4가지 동일 |

차이점 2가지:

- **매입 취소는 세금계산서와 무관하다.** `tax_invoice`는 매출 발급확인 전용이다. 매입 취소는 지급 소명 0행 조건만 확인한다.
- 매입 전표는 **구매발주·입고검수 없이 직접 등록**한다. 그 앞 단계는 WMS 영역이므로 뺐다. 화면에 이유를 적는다.

## 7. 회계

### E-14 분개 미리보기

| 항목 | 내용 |
|---|---|
| 데이터 | `posting_rule` `account` + 거래 데이터 |
| 성격 | **계산해서 보여줄 뿐 저장하지 않는다** |

거래 유형 4종:

```
매출 인식  (차) 외상매출금        / (대) 제품매출, 부가세예수금
수금       (차) 보통예금          / (대) 외상매출금
매입       (차) 원재료, 부가세대급금 / (대) 외상매입금
지급       (차) 외상매입금        / (대) 보통예금
```

- **미리보기 단위는 거래 건이 아니라 소명 행이다.** `receipt_apply` 1행 = 분개 1세트. 이렇게 잡으면 과입금이 별도 예외 없이 소명분만 나온다.
- **미소명 잔여는 분개 표 안에 넣지 않는다.** 표 밖에 별도 안내로 둔다. 선수금 계정이 없어 대변을 받을 곳이 없기 때문이다.
- 소명을 추가·취소하면 미리보기가 다시 계산된다.
- 이 화면은 **독립 화면이자 공통 패널**이다. E-07·E-10·E-11·E-13에서 "분개 보기"로 같은 컴포넌트를 연다.
- 화면 하단에 범위 안내: "전표 확정·총계정원장·결산은 1차 범위에서 제외했습니다."

## 8. 기준정보 (E-15 ~ E-18)

FEMS와 동일하게 **목록 + 등록/수정 패널** 패턴이다. 공통 규칙(삭제 RESTRICT, 참조처 건수 표시, 비활성화 우선 안내)은 포털 6장을 따른다.

| 화면 | 테이블 | 비고 |
|---|---|---|
| E-15 거래처 | `partner` | `partner_kind`로 매출처·매입처 구분 |
| E-16 품목 | `item` `item_unit_conversion` | **MES 품목과 독립이다.** 화면에 명시 |
| E-17 거래처별 단가 | `partner_item_price` | 거래처 × 품목 × 적용 구간 |
| E-18 계정과목·분개규칙 | `account` `posting_rule` | 읽기 전용에 가까움 |

- **E-16 상단에 독립 소유 안내를 둔다.** "이 품목은 ERP 전용입니다. MES 품목과 코드가 같아도 별개 데이터입니다." 이걸 안 적으면 평가자가 버그로 읽는다.
- **E-17은 적용 구간이 겹치지 않아야 한다.** 같은 거래처·품목에 기간이 겹치는 단가가 둘이면 어느 것을 쓸지 정해지지 않는다. 등록 시 겹침을 검사하고 경고한다.
- **E-18은 편집을 최소화한다.** 계정 7개와 고정 분개 규칙 10개는 사실상 상수다. 사용자가 분개 규칙을 자유롭게 바꾸면 미리보기가 회계적으로 틀린 결과를 낼 수 있다. 읽기 전용 + "왜 이렇게 매핑했는가" 설명을 우선한다.

### 처리 제안

- **E-G01이 가장 무겁다.** 선택지 둘이다.
  1. `item`에 과세구분 컬럼 추가 + 세율을 상수로 고정 (테이블 증가 없음)
  2. `tax_rate` 마스터 신설 (테이블 +1)

  포트폴리오 범위에서는 **1번을 제안한다.** 면세 품목을 실제로 다루지 않는다면 세율 마스터는 과설계다. 다만 **세율 10%가 코드에 박혀 있다는 사실은 문서에 명시**해야 한다.

- **E-G02도 결정이 필요하다.**
  1. `receivable`에 `due_date` 추가 + `partner`에 결제조건 추가 (컬럼 2개)
  2. 연령분석을 범위에서 제외하고 잔액 관리만

  **1번을 제안한다.** 컬럼 2개로 "언제까지 받아야 하는 돈인가"가 생기고, 대시보드에 연체 금액을 띄울 수 있다. 채권 관리에서 만기 없는 잔액은 절반짜리다.

- E-G03은 스키마 확인 후 판단. 기존 설계에 답이 있을 수 있다.
- E-G04·E-G06은 화면 안내로 해소한다. 스키마 변경 없음.
