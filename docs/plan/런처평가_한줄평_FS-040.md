# FS-040 런처 평가(별점·한줄평)

작성일: 2026-10-01 · 상태: **확정 — 사용자 지시 2026-10-01**("실제 방문자 · 게스트 포함 · 1번만 · 게스트는 별칭과 후기 · 다른 별칭이면 다시 허용 · 범위는 한줄평과 별점 · SPC와 동시에 진행")
관련: [CORE 모듈 설계](../modules/core/CORE_모듈설계_FS-005f.md) · [FS-027 게스트 별칭](게스트별칭_접속이력_FS-027.md) · P-02 앱 런처
번호: D70~D74 · AC-240~246 (CMMS D45~ · GW D60~69와 겹치지 않게 잡았다)

## 1. 결정

| # | 항목 | 결정 |
|---|---|---|
| D70 | 평가 대상·내용 | 운영 중인 솔루션(타일)마다 **별점 1~5 + 한줄평(2~100자)**. 둘 다 필수. 수정·삭제 없음(확정 데이터 불변) |
| D71 | 1회 규칙 | 회원: **계정당 솔루션별 1회**. 게스트: **게스트 공간(세션)당 솔루션별 1회**이고, **같은 별칭으로는 솔루션별 1회**. 나갔다가 다시 들어와 **다른 별칭이면 허용**. 별칭 비교는 앞뒤 공백 제거 후 정확히 일치 |
| D72 | 작성자 표시 | 회원은 `app_user.display_name`, 게스트는 평가할 때 입력한 별칭(2~20자, FS-027 D33과 같은 규칙). 공개 화면에 보인다 |
| D73 | 저장 위치 | `core.app_review` 1테이블(core `ops`, 범위 global). 공간·세대 범위가 아니다 — 게스트 공간이 정리돼도 평가는 남아야 하므로 `workspace`에 FK를 두지 않고 게스트는 `guest_actor_key` 값만 보관한다. 회원은 `core.app_user` FK(RESTRICT). 업무 스키마와 연결 없음 |
| D74 | 화면 | P-02 각 타일 아래 한 줄 `★ 4.8 · 후기 12`(평가 0건이면 `평가 모으는 중`). 누르면 대화상자: 평균·건수, 최근 한줄평 5건, 별 5개를 눌러 고르는 입력 + 한줄평(+게스트는 별칭). 이미 평가했으면 입력 대신 "평가 완료" |

## 2. 이유와 경계

- core는 인증·공간·세대·운영만 소유한다(FS-013). 제품 평가는 업무 데이터가 아니라 **운영 피드백**이라 core `ops`에 둔다. 새 스키마를 만들면 격리 검사·정리 순서·생성기 목록을 모두 고쳐야 해서 이득이 없다.
- 공간을 넘는 **집계 조회**는 이 테이블만 한다(평균·건수·최근 목록). 업무 데이터는 여전히 공간 밖으로 나가지 않는다.
- 게스트 같은 별칭 거부는 조건부 유니크 인덱스(`actor_kind='GUEST'`)가 강제한다. 회원 별칭(표시 이름)과 게스트 별칭은 서로 비교하지 않는다.
- **별칭 보관 기간 예외**: FS-027 D36은 접속 기록의 별칭을 90일 뒤 지우지만, 평가의 별칭은 공개 표시용이고 같은 별칭 거부에 쓰이므로 지우지 않는다. 입력 칸에 "공개 표시 · 실명 대신 별칭"을 안내한다.
- 악용 한계: 게스트는 별칭만 바꾸면 다시 평가할 수 있다(사용자 결정). IP·브라우저 정보는 수집하지 않는다. 게스트 공간 상한·정리 타이머가 생성 속도를 제한하는 유일한 장치다.
- 별점 순으로 타일을 재배치하지 않는다. 업무 흐름 순서가 유지된다.

## 3. DB — `core.app_review`

| 테이블 | 이름 | 범위 |
|---|---|---|
| `core.app_review` | 런처 평가 | global(core `ops`) |

| 컬럼 | 타입 | NULL | 규칙 |
|---|---|---|---|
| id | bigint identity | N | PK |
| module_key | varchar(24) | N | `mes·erp·fems·qms·wms·bems·spc` |
| actor_kind | varchar(10) | N | `MEMBER` / `GUEST` |
| user_id | bigint | Y | 회원만. FK `core.app_user(id)` RESTRICT |
| guest_actor_key | uuid | Y | 게스트만. 공간 UUID 값(FK 없음) |
| nickname | varchar(20) | N | 표시 이름 스냅샷. 회원은 표시 이름 앞 20자 |
| rating | smallint | N | 1~5 |
| comment | varchar(100) | N | 공백 제거 후 2자 이상 |
| created_at | timestamptz | N | now() |

제약: 주체 일치 CHECK(회원 = user_id만, 게스트 = guest_actor_key만) · 조건부 유니크 3개(회원 `module_key,user_id` / 게스트 `module_key,guest_actor_key` / 게스트 `module_key,nickname`) · 인덱스 `module_key,created_at`. 마이그레이션 `fs040_app_review`(down `fs026a_wms_receiving_reservation`), schema.json v0.15.0.

## 4. API (`/api/v1/core`)

| 메서드 | 경로 | 내용 |
|---|---|---|
| GET | `/reviews/summary` | `[{moduleKey, average, count, reviewed}]` — 평가가 없는 솔루션은 빠진다. `reviewed`는 현재 주체가 이미 평가했는지 |
| GET | `/reviews?moduleKey=mes` | 최근 5건 `[{nickname, rating, comment, createdAt}]` |
| POST | `/reviews` | `{moduleKey, rating, comment, nickname?}` · CSRF · Idempotency-Key. 201. 중복은 409 `ALREADY_REVIEWED`(같은 주체) / 409 `NICKNAME_TAKEN`(같은 별칭). 입력 오류 400 `VALIDATION_FAILED`(`fields`) |

## 5. 인수 기준 (AC-240~246)

| AC | 기준 |
|---|---|
| 240 | 별점 0·6, 한줄평 1자·101자, 모르는 솔루션 → 400, 행 0 |
| 241 | 게스트가 별칭·별점·한줄평으로 평가 → 201, 요약 평균·건수·`reviewed=true` |
| 242 | 같은 게스트가 같은 솔루션을 다시 평가(별칭을 바꿔도) → 409 `ALREADY_REVIEWED` |
| 243 | 새 게스트가 같은 별칭으로 같은 솔루션 → 409 `NICKNAME_TAKEN`, 다른 별칭 → 201 |
| 244 | 회원은 표시 이름으로 저장되고 같은 솔루션 두 번째는 409 |
| 245 | 같은 Idempotency-Key 재전송 → 같은 결과(201), 행 1 |
| 246 | 게스트 공간이 정리돼도 평가 행은 남는다 |
