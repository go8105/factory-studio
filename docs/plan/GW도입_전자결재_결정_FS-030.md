## 1. 기획 의도와 확인한 차이

ERP 문서의 검토 근거를 보관하고 순차 결재·반려·재상신을 체험한다. GW는 결재 절차의 주인이며 ERP 문서 확정·출하·재고의 주인은 아니다. 게시판은 GW의 글 게시 기능이다. 전사 요약 대시보드와 전사 공지 집계는 EIP 범위로 남긴다.

| 발견 사항 | 보완안 |
|---|---|
| 개인/게스트 공간에는 로그인 주체 한 명만 있다 | 합성 결재 담당자 역할 전환을 명시한다. 실제 계정과 합성 담당자를 별개로 기록하며 실제 다중 사용자 권한이라고 설명하지 않는다 |
| 지시의 “게시판(글·댓글·첨부 없음)”은 게시판과 모순된다 | **글 포함, 댓글·첨부 제외**로 승인 요청한다 |
| ERP 원문은 GW 결재와 무관하게 수정·취소될 수 있다 | 상신본을 고정하고 현재 원문과의 차이를 표시한다. 결재 완료를 ERP 현재 원문에 대한 승인으로 오인하지 않게 한다 |
| 반려 후 같은 행 수정은 과거 결재 근거를 지운다 | 새 문서/회차로 재상신하고 이전 회차와 연결한다 |
| ERP 기존 조회는 금액·거래처를 갖춘 결재 원문 계약이 아니다 | 읽기 전용 전용 조회를 추가한다. 기존 WMS용 함수의 반환은 변경하지 않는다 |
| 새 솔루션 킷은 공용 DB 업그레이드/템플릿 재생성을 포함한다 | 이번 명시 지시가 우선이다. Codex 전용 DB에서만 검증하고 공용/운영 반영은 사용자·통합 담당자에게 인계한다 |
| 병합 전 down_revision 수정 지시와 적용 migration 불변 규칙이 충돌할 수 있다 | DB 구현 전 최신 head를 다시 확인한다. 적용·공유된 revision은 고치지 않으며 병합 시 새 연결 revision 등 별도 조율한다 |

로드맵의 “한 번에 하나”에 대한 이번 예외는 사용자의 **SPC/CMMS와 GW 분담 지시**로 한정한다. 다른 솔루션을 추가 착수하지 않는다.

## 2. 결정 제안 — D60~D69

아래는 승인 전 제안이다. 확정된 경계의 재확인과 신규 정책을 함께 표시했다.

| 번호 | 항목 | 제안 |
|---|---|---|
| **D60** | 범위·경계 | `gw`, `/gw/*`, `/api/v1/gw`, G-01~07. 전자결재와 공지/자유 게시판. GW 업무 현황만 요약하며 전사 대시보드·전사 공지 집계는 EIP에 둔다. core 업무 테이블·교차 쓰기 금지는 확정 경계 유지 |
| **D61** | 인증·체험 담당자 | core 인증·CSRF·공간/세대·기존 쓰기 권한을 그대로 사용. GW에는 계정이 아닌 합성 담당자 코드/이름/직무와 결재선만 둔다. **“담당자 역할 체험”** 선택으로 기안자→팀장→임원 전환. 서버는 같은 S의 활성 담당자와 현재 결재 순서를 검사한다. 기안자와 같은 합성 담당자의 자기 결재, 결재선 중복 담당자 금지. 실제 로그인 주체는 서버 인증에서만 얻고 클라이언트 입력으로 바꿀 수 없다 |
| **D62** | 대상·상신본 | 1차는 **ERP 매입 전표 + GW 일반 기안**. 일반 기안은 ERP off에서도 동작한다. 매입은 문서 종류·번호·거래처 코드/명칭·공급가액·세액·합계·통화·상태·명세 의미 값을 서버 조회해 복사한다. 상신 시 원문을 다시 읽고 사용자가 본 내용과 달라졌으면 재검토를 요구한다. 상신본·결재선은 이후 불변. 견적·출하지시 추가는 후속으로 둔다 |
| **D63** | 결재 상태 | `DRAFT → IN_REVIEW → APPROVED / REJECTED`. 순차 결재 1~3단계, 현재 단계만 승인/반려 가능. 마지막 승인에서 완료. 한 번이라도 승인되면 회수 불가; 승인 전 기안자만 사유를 남겨 `WITHDRAWN` 회수. 반려·회수본은 불변이고 **새 DRAFT 생성**으로 재상신(이전 문서 연결). 병렬·합의·대결·위임·완료 취소는 제외 |
| **D64** | 중복·경합·감사 | 같은 S·원천 종류·문서 번호에 진행 중 결재 한 건만 허용. 최종 상태는 과거 이력으로 남고 새 결재 회차를 만들 수 있다. 일반 기안은 GW 문서 번호 기준. 변경은 멱등키·expectedVersion·공간→문서 잠금 순으로 원자 처리. 결재/반려/회수/상신/재상신 연결 이벤트는 추가만 하고 수정·삭제하지 않는다. 실제 인증 주체와 합성 역할, 사유, DB 처리 시각을 구분 기록 |
| **D65** | ERP 차이·꺼짐 | 진행 중 원문이 달라져도 고정된 상신본은 바뀌지 않는다. 차이/취소/없음/조회 불가를 표시하고 **“상신 당시 문서 검토”**라는 의미로 GW 처리를 계속할 수 있다. ERP off이면 신규 ERP 연결·상신만 차단; 기존 결재·일반 기안·게시판은 동작. ERP 확정 여부와 GW 결재 여부는 별개이며 서로 차단하지 않는다 |
| **D66** | ERP 배지 | **이번 사이클에 E-11 매입 전표 상세의 읽기 전용 배지 포함을 제안**. 진행 중 우선, 없으면 최신 종결 회차와 이력 링크. 현재 원문과 상신본이 다르면 “과거 상신본 승인 · 원문 변경”으로 표시해 단순 “승인”으로 오인하지 않게 한다. GW off는 “결재 조회 불가”, 기록 없음은 “결재 기록 없음”으로 구분. ERP 기존 상태 전이/버튼에는 영향 없음. 사용자 선택으로 배지 자체는 후속으로 미룰 수 있다 |
| **D67** | 게시판 | 공지·자유 2종, 제목·본문·작성 역할. 초안 수정→게시. 게시 후 본문은 불변, 정정은 새 글과 이전 글 연결, 철회는 사유를 가진 별도 이력으로 표시. 삭제로 이력 소실 금지. 공지는 합성 운영 담당자 역할, 자유 글은 작성 역할로 관리. 모든 글은 현재 공간 안에서만 공개. 댓글·첨부·메일·채팅·일정·조회수/읽음 추적 제외 |
| **D68** | 체험·시각·복사 | 합성 담당자 4명 내외·결재선 2종·초안/진행/승인/반려/회수/재상신·게시판 예시로 결정적 체험 구성. 런타임 사건 시각은 DB `clock_timestamp()`; FS_TODAY는 체험 업무일/시드 날짜에만 사용. 게스트 복사는 GW 내부 FK와 이벤트 주체를 새 공간에 맞춰 처리하고 날짜는 일관 이동, 의미 값 digest는 시간 이동 때문에 다시 만들지 않는다 |
| **D69** | 구현·병합·검증 | 결정서 승인→모듈/화면 전체 설계 승인→a DB→b API/화면→c 시드/도움말/통합 검증, 매 단계 보고 후 대기. D60~69, AC220~239, 임시 버전 v0.15.0-gw 사용. 기존 migration 수정 금지. main/SPC/CMMS의 모듈 키·시드 합계·검증기·홈 목록을 rebase 때 보존. Codex 전용 DB, 전용 포트 또는 동시 사용이 없는지 확인 후 브라우저 실행. push·배포·main 병합 제외 |

### D62·D65 보충 — 원문과 결재의 의미

- 상신 가능한 매입은 ERP의 취소되지 않은 초안/확정 문서다. 확정 문서 선택 시 **사후 검토**라고 표시한다. GW 승인 없이도 ERP는 확정할 수 있다.
- `sourceDigest`는 원천 종류·번호, 거래처, 통화, 공급가액/세액/합계, 명세 순서·품목·수량·단위·단가 등 **검토 대상 의미 값**을 정규화해 만든다. 숫자는 decimal 문자열이다. 조회 시각·생성 시각·확정 시각·업무일은 제외하고, 원천 상태는 별도 값으로 비교한다. 금액 정의는 ERP가 제공하며 GW에서 독자 재계산하지 않는다.
- 매입 번호가 복사 시 바뀌는지 모듈 설계에서 확인한다. 바뀐다면 원천 키/참조를 함께 재매핑하는 계약을 먼저 정한다. 날짜 이동을 핑계로 원문 변경을 감추는 digest 재계산은 하지 않는다.
- 클라이언트가 준 금액/거래처/현재 원천 상태를 ERP 스냅샷으로 신뢰하지 않는다. 일반 기안은 별도 유형이며 ERP 연결처럼 표시하지 않는다.
- 일반 기안의 금액은 선택이고 통화와 함께 저장한다. 서로 다른 통화 금액을 대시보드에서 합산하지 않는다.
- 승인 후 같은 ERP 문서에 새 회차가 생기면 과거 승인을 최신 회차 승인처럼 표시하지 않는다. GW 이벤트 순번/회차로 순서를 정하고 시계 비교에 의존하지 않는다.

### D61·D64 보충 — 권한을 과장하지 않는 체험

실제 사용자/게스트는 자기 공간을 조작한다. 합성 담당자 선택은 **업무 역할 시뮬레이션**이며 다른 실사용자로 로그인하는 기능이 아니다. 결재선의 현재 담당자만 승인할 수 있는 업무 규칙과 실제 인증·공간 격리를 각각 검사한다. 합성 역할 선택으로 core 관리자 권한을 얻지 못한다. 사용자·게스트 기록을 업무 FK로 참조하지 않는다(R2). 로그인 주체의 감사 식별자는 서버에서 기록하며 시드 이력을 실제 사용자가 승인한 기록으로 위장하지 않는다. 별칭·개인정보 보관 및 게스트 정리 정책을 상세 설계에서 명시한다.

## 3. 교차 조회 계약 제안

앞 두 인자는 `(connection, scoped)`. 내부 업무 ID/ORM/커서를 넘기지 않고 값만 반환한다. 제공 쪽 행 잠금과 쓰기는 금지한다. 상세 필드·페이지 규약은 모듈 설계에서 확정한다.

| 제공 | 함수 제안 | 의미 |
|---|---|---|
| ERP 추가 | `approval_documents(..., kind, filters)` | 결재 대상 목록. 1차 `PURCHASE_INVOICE`만 허용. 종류별 allowlist, 범위·검색·페이지 제한 |
| ERP 추가 | `approval_document(..., kind, document_no)` | 번호로 원문 스냅샷 조회. ERP off와 문서 없음 구분: off는 None, 없음은 명시적 not-found 결과. GW가 ERP 테이블을 직접 읽지 않음 |
| GW 신규 | `enabled(...)`, `approvals(..., document_refs)` | 원천 종류+번호별 진행/최신 종결 회차·문서 번호·상신 digest·원천 상태·GW 링크용 정보. 일괄 조회로 N+1 방지. GW off=None, 기록 없음=해당 키의 빈 결과 |

호출 방향은 GW→ERP 원문 조회, ERP→GW 배지 조회까지다. **interface 내부에서 상대 interface를 다시 호출하지 않는다.** GW 조회는 저장된 GW 값만 반환하고, ERP가 자기 원문과 비교해 배지를 표시한다. EIP가 나중에 사용할 수 있도록 계약만 남기며 EIP 화면은 구현하지 않는다.

ERP README의 현재 표에는 실제 존재하는 `shipment_orders()`가 누락돼 있다. b 단계에서 제공 조회 표를 갱신할 때 기존 함수를 함께 기재하되 기능은 바꾸지 않는다.
