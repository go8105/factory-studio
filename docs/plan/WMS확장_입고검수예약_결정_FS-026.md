## 1. 기획 의도 검토

운영 중인 WMS에 실물 입고 전후와 출고 준비 과정을 추가한다. 현재 6테이블 `warehouse`, `storage_location`, `item`, `item_unit_conversion`, `stock_document`, `stock_move`와 W-01~07을 재사용한다. **현재고의 원천은 확정 전표에 속한 stock_move의 합계**라는 원칙을 유지한다. 별도 재고 잔량 원장이나 새 WMS를 만들지 않는다.

사용자는 입고 예정을 등록하고, 트럭 도착을 확인하고, 합격·격리·부족 수량을 검수한 뒤 재고를 확인한다. 출고 전에는 정상 위치의 재고를 예약하고, 기존 원천 반영으로 출고가 기록되면 예약이 해소되는 흐름을 체험한다.

`fad0c3a`의 신규 WMS 설계는 참고 자료일 뿐이다. 테이블·화면 번호·EA 정수 전용·원자재 LOT·별도 stock_balance를 가져오지 않는다. 기존 KG/EA, numeric(18,3), 단위 환산, 완제품 LOT/원자재 품목 추적을 유지한다.

## 4. 입고 중복 방지와 검수 수량

### 4.1 경로 선택과 원천 선점

| 상황 | 처리 권장안 |
|---|---|
| ERP 매입이 미반영 | 기존 직접 반영을 선택하거나 입고 예정에 연결하여 검수 경유로 선점 |
| 검수 예정에 연결된 원천을 W-03에서 반영 | 새 원장 생성 거부. 검수 화면/상태를 안내. 일괄 반영도 동일 |
| 이미 직접 반영된 매입을 예정에 연결 | 거부. 검수로 다시 입고하지 않음 |
| 검수 예정 취소(확정 전) | 원천 선점 해제. ERP가 취소되지 않았다면 이후 직접 반영/새 예정 연결 가능 |
| 검수 확정 후 ERP 매입 반영 재시도 | 기존 검수 전표를 반환. 추가 원장 0 |
| 검수 확정 후 경로 변경 | 거부. 확정 기록 불변 |
| 서로 다른 탭에서 연결/반영/확정 동시 실행 | 기존 공간 쓰기 잠금 안에서 선점·원장 존재를 재확인. DB 유니크와 멱등 키를 함께 적용 |

최초 범위는 **매입 전표 1건 ↔ 입고 예정 1건 ↔ 검수 확정 최대 1건**이다. 품목 중복 줄은 품목·기본 단위로 합산하여 비교한다. 기본 단위 환산 값은 연결 시 스냅샷으로 남긴다. 확정 직전 원천 취소/수량 변경을 interface로 다시 확인한다. 한 매입의 여러 트럭 분납/여러 매입 합배송은 후속이다.

직접 반영과 검수 경유는 모두 동일 ERP 원천 키(`ERP:PURCHASE:<번호>`)를 기준으로 중복을 판단한다. 연결 선점의 구체적 저장 구조와 신규 전표 유형은 모듈 설계에서 정하며, **서로 다른 source_key를 발급하는 것만으로 중복 방지를 대신하지 않는다.**

### 4.2 ERP 없이 만드는 예정

WMS 독립 동작을 위해 수동 예정도 허용한다. 중복 방지 업무 번호를 필수로 받고 원천은 WMS 수동 입고로 명시한다. ERP 매입이 나중에 생기면 **검수 확정 전에 연결**하거나, 이미 검수 확정했다면 별도의 **기입고 대사 연결(원장 변동 0)**을 사용한다.

기입고 대사 연결은 아직 직접 반영되지 않은 ERP 매입과 미연결 수동 검수 건을 1:1로 연결하고, 품목별 기본 단위 예정 수량이 일치해야 한다. 연결 후 해당 ERP 원천은 검수 처리 완료로 간주해 직접 반영하지 않는다. ERP가 먼저 직접 반영된 경우 자동 합치기/전표 삭제는 금지하고 중복 경고와 조정 절차로 안내한다. **연결하지 않은 두 독립 입력이 같은 실물인지는 시스템이 추정할 수 없다.** 번호가 유사하다는 이유로 자동 매칭하지 않는다.

ERP 꺼짐 상태에서는 기존 ERP 연결 예정의 검수 확정/대사 연결을 보류한다(원천 유효성 확인 불가). ERP 미연결 수동 예정은 계속 처리할 수 있다. 이는 WMS 독립 동작과 원천 확인을 구분하는 제한이다.

### 4.3 수량 식과 예시

품목 기본 단위의 소수 셋째 자리까지 다룬다. 예정 = 합격 + 격리 + 부족, 각 값은 0 이상이다. 초과 입고는 확정 전에 예정을 수정하고 원천 연계 건은 원천과 다시 대사한다. 부분 입고를 여러 차례 검수 확정하는 기능은 제외한다.

예: RM-PBT **100 KG 예정 → 합격 95 KG + 격리 3 KG + 부족 2 KG**. 검수 확정은 정상 위치 +95, 격리 위치 +3으로 현재고를 98만 증가시킨다. 부족 2는 원장에 쓰지 않는다. ERP 매입이 100 KG더라도 차이 2 KG는 대사 표시이며 채무/매입전표를 WMS가 고치지 않는다.

전량 부족이면 검수 완료 이력과 원천 처리 완료 표시는 남기되 0수량 stock_move는 만들지 않는다. 전표 생성 여부·대사 연결 상태의 제약은 모듈 설계에서 정의한다. 이 경우도 W-03 재시도로 전량 입고되지 않아야 한다.

### 4.4 취소와 정정

- 도착 전/후 검수 미확정 예정은 사유를 남겨 취소할 수 있다. 입고 원장 없음.
- ERP가 취소된 연결 예정은 검수 확정을 거부하고 취소/연결 해제를 안내한다.
- 검수 확정 후 ERP 취소는 재고를 자동 차감하지 않는다. 원천 취소 경고는 ERP를 켠 상태에서 조회할 때 확인하며, 꺼짐은 정상으로 간주하지 않는다.
- 기존 FS-024 직접 반영 전표는 기존 취소 되돌림 규칙을 유지한다. 신규 검수 경유 여부를 분명히 식별해야 한다.
- 확정 검수 수정·삭제는 금지한다. 실물 반품/잘못 입력한 수량은 원 검수 번호를 참조하는 사유 있는 조정으로 보정한다. 격리 재고를 이미 옮겼다면 실제 현재 위치에서 처리한다.

## 5. 예약과 음수 재고의 관계

예약 단위는 **위치·품목·LOT(완제품만)**이며 원자재는 LOT 없이 처리한다. 수량은 품목 기본 단위다. 예약은 활성 → 해제 또는 소진으로 끝나며 자동 만료는 이번 범위에서 제외한다. 변경은 해제 후 재등록하며 증가분은 재검증한다.

예: 정상 95, 격리 3, 예약 40이면 전체 현재고 98, 예약 가능 55다. ERP 미출하 지시가 40이어도 40을 다시 빼지 않는다. 이후 미예약 ERP 출하 70이 반영되면 정상 현재고 25, 예약 40, 계산상 가용 −15로 **부족 15**를 표시하고 새 예약은 거부한다. 가용의 음수를 0으로 숨기지 않는다.

원천 반영·기존 수동 조정/이동의 D15 동작은 유지한다. 따라서 다른 이동으로 예약 위치 재고가 빠질 수도 있다. 부족 경고에서 예약 해제/재예약 또는 근거 있는 재고 정정을 안내하고, 임의로 예약을 자동 소진/삭제하지 않는다. 수량 비교는 공간 쓰기 잠금 안에서 다시 수행한다.

### 예약 소진 규칙

- 예약은 WMS 안에서 ERP 없이도 등록/해제 가능하다. 실제 소진은 ERP 확정 출하를 명시적으로 연결해 반영할 때만 한다. MES 투입에 자동 연결하는 생산 불출 예약은 이번 범위에서 제외한다.
- ERP 출하지시 번호를 참고로 적는 것과 확정 출하에 연결하는 것을 구분한다. 문자열만으로 자동 소진하지 않는다.
- 최초 범위는 한 출하에 한 예약 묶음을 연결하고 **완제품 품목별 기본 단위 수량 전량 일치**를 요구한다. 예약에는 LOT 미지정 완제품을 허용하지 않는다. 부분 출하/여러 출하에 걸친 소진은 후속이다.
- 연결된 출하의 차감 위치·LOT는 검증된 예약 배분을 사용한다. ERP packing_no가 있으면 기존 MES 입고 원장으로 확인되는 LOT 구성과도 일치해야 한다. 불일치/확인 불가이면 예약 연결을 거부한다.
- 연결 없는 ERP 출하는 기존 FS-024 LOT 매칭/미지정 정책으로 그대로 반영한다. 예약 연결 실패를 이유로 ERP 출하나 기존 원천 반영 자체를 막지 않는다. 사용자가 연결 없이 반영하면 남은 예약은 명시적으로 해제해야 하며 자동 소진으로 표시하지 않는다.
- 출하 반영과 예약 소진은 같은 트랜잭션이다. 재시도는 기존 결과를 반환한다. 이미 반영된 출하에 예약을 소급 연결하여 다시 차감하는 기능은 없다.
- ERP의 출하지시 취소/변경이 WMS 예약을 자동 해제하지 않는다. 조회 가능한 때 불일치를 안내하고 사용자 해제를 요구한다.

ERP 출하지시/확정 출하의 식별·수량 조회가 더 필요하면 **fs/erp/interface.py의 읽기 전용 반환 계약만 확장**한다. WMS가 ERP 테이블을 직접 조회하거나 ERP 상태를 변경하지 않는다. 상세 인터페이스 계약은 단계 2에서 확정한다.

## 6. 격리·트럭·시드 정책

- 기존 storage_location은 NORMAL로 이행하고, WH-RAW/WH-FG 각각 필요한 QUARANTINE 위치를 추가한다. 기본 원천 반영 위치는 NORMAL만 허용한다.
- 원장이 있거나 활성 예약/진행 중 예정이 참조하는 위치의 유형 변경을 금지한다. 기존 재고를 격리하려면 위치 유형을 바꾸지 않고 이동 전표를 만든다.
- 격리 해제는 QUARANTINE → NORMAL 이동, 재격리는 반대 이동이다. 사유 필수이며 이동 양쪽 합은 0이다. 격리 위치의 신규 예약은 거부한다. QMS 보류의 자동 이동/자동 해제는 하지 않는다.
- 트럭은 입고 예정 번호를 선택하고 진행시킨다. 도착 요청은 멱등이며 서버가 예정 상태와 권한을 검증한다. 브라우저에서 도착 애니메이션이 끝나도 서버 저장 실패 시 완료로 표시하지 않는다. 재접속은 서버 상태로 복원한다.
- 3D를 열지 않아도 WMS에서 수동 도착 처리할 수 있다. 실차 GPS·배송 지도·외부 운송 서비스는 이번 범위가 아니다.
- 기존 품목 5종과 창고 2개를 유지한다. 3D의 알루미늄 블록은 실제 WMS 품목/생산 실적으로 표시하지 않는다. 신규 알루미늄 품목·BOM·수량 연계는 별도 결정이 필요하다.

## 7. 사용자 질문과 권장안

| 질문 | 권장안 | 선택 시 의미 |
|---|---|---|
| Q1. ERP 매입과 검수 중 누가 입고 원장을 만드는가? | D25: 원천별 직접 반영/검수 경유를 상호 배타적으로 선택. 수동 기입고의 사후 ERP 대사 연결 포함 | 기존 운영 유지, 검수 건만 실물 검수 수량 반영. 분납·합배송 제외 |
| Q2. 검수 후 ERP 매입 취소 시 실물도 되돌릴 것인가? | D26: 검수 건은 경고만, 실물은 사유 있는 조정. 기존 직접 반영은 기존 되돌림 유지 | 회계 취소가 창고의 실물을 자동 제거하지 않음 |
| Q3. 예약과 ERP 미출하 수량을 모두 가용에서 뺄 것인가? | D27·D28: WMS 예약만 차감, ERP 미출하는 참고. 부족한 신규 예약은 거부하고 원천 반영 음수는 허용 | 중복 수요 차감 방지, 예약 후 부족은 경고로 관리 |
| Q4. 예약은 어디까지 출고와 연결하는가? | D31: 명시적 ERP 출하 전량 연결만 소진, 별도 WMS 출고 차감·부분 소진은 제외 | 원장 차감은 1회. MES 투입 예약 연계는 후속 |
| Q5. 격리와 트럭은 어떻게 처리하는가? | D29·D30: 위치 유형으로 격리, 트럭은 도착 상태만, 검수 확정만 입고 | 재고 원장 재사용, 3D 중복 실행으로 입고되지 않음 |
| Q6. 알루미늄 품목도 시드에 추가하는가? | D32: 이번에는 기존 5품목 유지, 알루미늄은 시각 시연 | 기존 MES/ERP/WMS 예제와 단위·LOT 기준 유지 |

## 8. 승인 후 단계와 검증 계획

1. **이번 단계:** 결정서만 작성하고 사용자 확인을 기다린다. FS-024 문서의 확정 정책은 아직 덮어쓰지 않는다.
2. 승인 후 기존 모듈 설계에 새 revision, 기존 테이블 재사용/추가 테이블·상태·멱등·잠금·인터페이스 명세를 작성한다. W-08 이후 또는 기존 화면 확장과 **AC-139부터** 인수 기준을 작성하여 다시 확인받는다.
3. 전체 설계 승인 후에만 개발한다. 새 migration은 현재 head `fs025b_bems_module` 다음이며 착수 시 head 전진 여부를 확인한다. 이미 적용한 migration은 수정하지 않는다. schema.json·DB설계서.xlsx·ERD를 같은 작업에서 갱신한다.

후속 인수 기준에 반드시 넣을 검증 주제: 직접 반영/검수 경유 동시 요청, 전량 부족 재시도, 단위 환산·소수 수량, ERP 취소 전/후, 수동 기입고 대사, 예약 동시 경합, 예약 후 음수, 격리 제외, 예약 LOT와 출하 불일치, 예약 소진 재시도, 트럭 중복 도착·통신 실패·새로고침, ERP 꺼짐, 공간/세대 격리 및 게스트 복사/초기화. **아직 AC 번호 부여·테스트 구현·실행은 하지 않았다.**

## 9. 이번 단계 검증과 한계

기존 FS-024 결정·모듈·화면 및 WMS service/schema/router, ERP interface의 현행 동작과 정적으로 대조했다. 새 테이블 수·API 경로·제약의 구체적 이름은 단계 2 대상이다. 이번 단계는 문서만 변경하며 DB·제품 코드·시드·운영 상태를 바꾸지 않는다. push·배포는 사용자 확인 후 별도 진행한다.
