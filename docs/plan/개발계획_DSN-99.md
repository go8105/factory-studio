## 3. 마이그레이션 전략 (Q1)

| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| **(a) 단계별 새 revision** | 기존 16개는 그대로 두고, 단계(W1~W6)마다 그 단계 솔루션의 새 표·열·제약을 새 revision으로 추가 | 운영 회원 계정·런처 평가(FS-040)가 남는다. AGENTS.md §4 규칙 그대로. 열 삭제·형 변경이 없어 위험이 낮다 | revision이 많아진다(단계당 1~3개) |
| (b) 운영 DB 새로 만들기 | 목표 DB 전체를 새 기준 revision 하나로(`schema_ddl.py`가 DDL을 만든다) 만들고 `docker compose down -v` 후 재설치 | 마이그레이션이 단순하다 | 회원 계정·평가를 따로 백업·복원해야 한다. 이미 공유한 revision 이력을 끊는다 |

**제안: (a).** 합성 데이터는 단계마다 템플릿 시드를 다시 만든다(배포 절차 4-3). 기존 데이터와 충돌하는 제약 교체(유일 키 교체 등)는 그 revision 안에서 시드 재생성 순서로 처리한다. (b)는 (a)가 막힐 때의 대안으로 남긴다.

## 4. 개발 방식 — 단계 하나의 사이클

각 단계 W는 같은 순서를 따른다. **단계 안에서는 솔루션 하나씩**, 끝나면 보고·확인 후 다음으로(AGENTS.md §1).

1. **a DB**: 새 revision → `schema.json`·Excel·ERD 같은 작업에서 갱신 → `npm run db:validate`·`db:build`·`build_erd`. 목표 DB와 같아졌는지 대조(그 솔루션 범위).
2. **b API·화면**: 공통 엔진(마스터 CRUD·전표 상태 전이·멱등·낙관적 잠금) 위에 검증 규칙·계산만. 화면은 패턴 정의(설정 객체), 특수 화면만 직접. interface 함수는 DSN-90 2장 계약 그대로.
3. **c 시드·도움말·흐름 맵**: 코드 사전 공유 시드(DSN-90 5장), 도움말·흐름 맵은 리포지토리 정적 파일(FS-013 D4·D6).
4. **검증**: pytest(그 솔루션 + 교차 조회) · Vitest · 브라우저 확인 · 격리 감사. **실행하지 않은 검증은 통과로 적지 않는다.**
5. **배포·동결**: `tools/deploy.sh`(W0에서 작성, 사용자가 실행) → 운영 확인 → 동결.

공통: 30분마다 WIP 커밋(`.env`·`work/` 제외, 파일 경로 지정 staging), 세션 끝에 HANDOFF 갱신, 현황·progress 갱신.
