## 1. 확정된 결정

| # | 항목 | 결정 |
|---|---|---|
| D1 | 솔루션 간 경계 | **공통 인증만 공유.** 업무 DB·API·마스터는 각 솔루션이 독립 소유한다 |
| D2 | 물리 구성 | **단일 PostgreSQL 인스턴스 + 스키마 분리 + API 서버 1개(라우터 분리)** |
| D3 | 기존 설계 처리 | **v0.6.0의 67테이블을 3솔루션으로 분해·재배치한다.** references Excel 3종은 누락 보완 입력으로만 사용하고 기준본으로 삼지 않는다 |
| D4 | 학습 기능 | **도움말·업무 안내로 축소.** 과정·단계·진도·시도·채점은 전부 폐기한다 |
| D5 | 게스트 체험 | **유지.** `S = (workspace_id, generation_id)` 범위 키와 세대 복사 방식을 그대로 쓴다 |
| D6 | 흐름 맵·도움말 저장 | **DB 테이블이 아닌 리포지토리 정적 파일(JSON/Markdown)** |
| D7 | ERP 회계 범위 | **A층(채권채무·수금지급) 구현 / B층(계정과목·자동분개 규칙 + 분개 미리보기) 읽기 전용 / C층(결산·재무제표·원가·고정자산·예산) 제외** |

### D2 보충 — 논리 독립과 물리 분리

"독립 솔루션"은 **소유권과 참조 규칙의 독립**을 뜻하며 인스턴스 분리를 뜻하지 않는다.
단일 인스턴스를 유지하는 실질적 이유는 **게스트 체험(D5)** 이다. 인스턴스를 3개로 쪼개면 약 6,840행 세대 복사가 단일 트랜잭션으로 성립하지 않고, 이 규모에서 2단계 커밋이나 보상 삭제를 도입하는 것은 비효율이다. 인스턴스 분리는 채택하지 않는다.

이 선택의 한계도 같이 기록한다. 같은 인스턴스에 있으므로 **스키마 간 FK를 물리적으로 막을 수단이 없다.** 경계는 자동 검사(6장)로만 지켜진다.

### D7 보충 — 회계 범위를 이렇게 자른 이유

채권채무와 수금지급이 없으면 돈의 흐름이 닫히지 않아 ERP라 부를 수 없으므로 A층은 제외하지 않는다.
반면 결산·재무제표·원가계산은 구현량보다 **정확성 리스크**가 크다. 계정과목 체계, 과세·영세·면세 구분, 재공품 평가를 부분적으로만 맞추면 회계를 아는 평가자에게 오류가 먼저 보인다. 반쯤 맞는 재무제표보다 A층을 정확히 닫고 C층은 제외 사유를 설명하는 쪽을 택한다.
원가계산은 유일하게 아쉬운 항목이므로 **ERP-2 후보로만 남기고 1차 범위에는 넣지 않는다.**

## 2. 계층 구조

```
┌─ 포털 (schema: core) ─────────────────────────────────┐
│  인증·계정·역할·세션 / 개인 공간·세대 / 모듈 사용여부  │
│  운영: 작업 실행·감사·요청 영수증                      │
│  흐름 맵·도움말: 정적 파일 (DB 아님)                   │
└──────────┬──────────────┬──────────────┬──────────────┘
           │   인증 subject + 범위 키 S 만 전달
    ┌──────┴────┐  ┌──────┴────┐  ┌──────┴────┐
    │  mes 스키마 │  │ erp 스키마 │  │ fems 스키마│
    │  자체 마스터│  │ 자체 마스터│  │ 자체 마스터│
    │  자체 업무권한│ │ 자체 업무권한│ │ 자체 업무권한│
    └───────────┘  └───────────┘  └───────────┘
       업무 스키마 간 FK 0건. 코드 체계만 문서로 정합.
```

### 인증 경계

- 비밀번호 해시·세션·CSRF 토큰은 **`core`만 보유한다.** 각 솔루션은 인증 주체(subject)와 범위 키만 받는다.
- **업무 권한(역할·메뉴 접근)은 각 솔루션이 자체 보유한다.** `core.role`은 플랫폼 역할(소유자·게스트·관리자)만 다룬다.
- references의 MES Excel에 있는 사용자 비밀번호 해시 컬럼은 채택하지 않는다.

### 마스터 중복에 대한 입장

품목·설비를 솔루션별로 복제하면 같은 코드가 여러 스키마에 존재한다. 이는 결함이 아니라 D1의 필연적 결과이며, 실제 제품에서도 시스템 간 마스터 연계는 인터페이스로 푸는 문제다.
대응은 두 가지다.
1. **표준 코드 체계 문서**를 두고 시드가 동일 코드를 각 스키마에 심는다. 사용자가 같은 품목을 세 번 등록하는 일은 없다.
2. **"실제 운영이라면 마스터 연계 인터페이스가 필요하다"**를 포털 설명 카드에 명시한다. 감추지 않고 설계 의도로 드러낸다.

### 3.5 FEMS가 품목 마스터를 갖지 않는 이유

결과적으로 FEMS는 MES 없이도 원단위를 산출할 수 있고, 마스터 복제는 한 벌 줄어든다.

## 6. 새 경계 검사 규칙

`tools/audit_module_boundary.py`는 판정 대상(core 필수참조 + 타모듈 nullable 선택참조)이 사라지므로 **폐기하고 `tools/audit_schema_isolation.py`로 대체한다.**

검사 규칙:

| # | 규칙 | 위반 시 |
|---|---|---|
| R1 | 업무 스키마(`mes`, `erp`, `fems`) 간 FK는 **0건**이어야 한다 | 오류 |
| R2 | 업무 스키마 → `core` FK는 **범위 앵커(`core.workspace`, `core.data_generation`)에 한해 허용**한다 | 그 외 오류 |
| R3 | `core` → 업무 스키마 FK는 **0건**이어야 한다 | 오류 |
| R4 | `learning`, `process_map`, `bems` 스키마 테이블이 존재하면 안 된다 | 오류 |
| R5 | 각 업무 스키마는 자체 범위 키 컬럼(`workspace_id`, `generation_id`)을 보유해야 한다 | 오류 |

R2가 예외인 이유는 D5다. 게스트 체험을 유지하는 한 모든 업무 행은 어느 공간·세대에 속하는지 알아야 하고, 이 앵커까지 끊으면 세대 복사와 회수가 성립하지 않는다. **앵커는 플랫폼 계층 참조이지 업무 참조가 아니다.**

**스크립트 구현은 이번 작업에 포함하지 않는다.** `schema.json`이 아직 v0.6.0이므로 지금 작성하면 전 규칙이 위반으로 나온다. FS-014에서 스키마 재구성과 같은 작업으로 작성해야 검사가 의미를 갖는다.

## 7. 게스트 세대 복사 순서 (3스키마)

단일 트랜잭션은 유지되나 삽입 순서는 스키마를 넘나든다. 부모 → 자식 순서는 다음과 같다.

```
1. core.workspace → core.data_generation
2. mes 마스터 (site → location → equipment → item → item_unit_conversion → process → ...)
3. erp 마스터 (partner → item → partner_item_price)
4. fems 마스터 (site → location → equipment → energy_source → meter → meter_channel)
5. mes 업무 → erp 업무 → fems 업무 (스키마 내부 순서는 기존 잠금 순서 유지)
```

정리(삭제)는 역순이다. 스키마 간 FK가 0건이므로 2·3·4 사이에는 순서 제약이 없고 병렬 삽입이 가능하다.

**기존 제약은 그대로 남는다.** 약 6,840행 단일 트랜잭션에 대한 `statement_timeout 10초` 부족 우려는 해소되지 않았다. 실측은 FS-009 이후다.
