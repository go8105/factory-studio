## 2. 순서의 이유

| # | 시스템 | 먼저 필요한 것(읽는 조회) | 새로 내놓을 조회(제안) | 이 순서인 이유 |
|---:|---|---|---|---|
| 1 | SPC | MES `lot_snapshot`·**신규** `operation_runs`(LOT·공정·설비·시각) | `out_of_control(lot_no)` → QMS | MES·QMS만 있으면 된다. 관리도·Cpk는 화면 효과가 크다 |
| 2 | CMMS | MES **신규** `equipment()`, BEMS **신규** `open_alarms()` | `equipment_down(on_date)` → MES, `part_requests()` → ELB | 기존 BEMS 경보가 보전 작업지시로 바로 이어진다. WMS 부품 재고 조회는 FS-026 뒤로 미룬다 |
| 3 | POP | MES **신규** `released_work_orders()` | `confirmed_entries()` → MES가 가져오기 | 현장 입력 전용 화면. MES가 가져오는 방향(§6-1) |
| 4 | TMS | ERP **신규** `open_shipment_orders()`, WMS 출고(FS-026 계약) | `deliveries()` → ERP | FS-026의 트럭 도착·출고 예약과 경계를 맞춰야 한다 |
| 5 | PLM | — (원천 시스템) | `released_boms()`·`item_revisions()` → MES 가져오기 | 받는 것이 없어 독립적이다. MES BOM 가져오기 버튼 1개가 이웃 변경의 전부 |
| 6 | CRM | ERP `confirmed_shipments`, QMS `latest_results` | `won_opportunities()` → ERP 견적 가져오기, `claims()` → QMS | 기존 조회만으로 시작할 수 있다 |
| 7 | SCM | ERP 수주·출하, WMS 입고, QMS 판정 | `demand_forecast(month)` → ERP 판매계획 | 여러 솔루션을 읽는 집계형이라 이웃이 많을수록 좋다 |
| 8 | ELB/MRO | CMMS `part_requests`, WMS 재고 | `purchase_receipts()` → WMS·ERP | CMMS가 먼저 있어야 요청 원천이 생긴다 |
| 9 | EIP | 모든 솔루션 `enabled`·요약 조회 | — | 요약할 솔루션이 다 있어야 의미가 있다 |
| 10 | GW | ERP 전표(결재 대상) | `approvals(doc_ref)` → ERP·EIP | EIP와 경계를 정한 뒤에 한다 |
| 11 | RWS | MES·CMMS 이슈 | — | 가장 독립적이고 전시 가치가 가장 낮다 |

**현재 조회 연결(운영 코드 기준, 2026-09-30):**

```
MES ─ inspectable_lots·lot_snapshot·items ──→ QMS
MES ─ items·finished_goods_receipts·completed_material_issues ──→ WMS
ERP ─ confirmed_shipments·purchase_receipts·open_shipment_qty ──→ WMS
QMS ─ held_lot_nos·latest_results ──→ MES(배지)
FEMS ─ site_electricity·manufacturing_electricity ──→ BEMS
```

`fs/wms/interface.py`와 `fs/bems/interface.py`는 아직 없다. 새 솔루션이 필요로 할 때 그 사이클에서 만든다.

## 3. 규칙(모든 사이클 공통)

- 교차 조회는 `fs/<제공>/interface.py`의 읽기 전용 함수로만 한다. 쓰기·스키마 간 FK·다른 스키마 직접 SQL은 금지(격리 검사 R6).
- 제공 솔루션이 꺼져 있으면 함수는 `None`을 돌려주고, 소비 쪽은 "조회 불가"로 표시하고 계속 동작한다.
- 가져온 값은 코드·수량 **스냅샷**으로 저장한다. 원천이 바뀌어도 이미 저장한 값은 바꾸지 않는다.
- 새 조회 함수가 필요하면 제공 솔루션 README 맨 위 "제공 조회 함수" 표를 **같은 커밋에서** 갱신한다. 동결 솔루션도 조회 함수 추가는 허용한다.
- 마이그레이션 head가 한 줄로 이어지게 한다. 다른 작업자(Codex) 브랜치에 새 revision이 있으면 먼저 순서를 맞춘다.

## 4. 홈 17타일 분야별 묶음(설계만, 구현은 타일이 늘어날 때)

현재 홈(P-02)은 여섯 타일을 한 줄로 보여 준다. 17개가 되면 한눈에 읽을 수 없으므로 **분야별 묶음**으로 바꾼다. 분야는 `content/systems.json`의 계층을 합쳐 5개로 둔다.

| 묶음 | 타일(순서) | 현재 운영 |
|---|---|---|
| 생산·품질 | MES · POP · QMS · SPC · CMMS | MES · QMS |
| 공급망·물류 | SCM · WMS · TMS · ELB/MRO | WMS |
| 에너지 | FEMS · BEMS | FEMS · BEMS |
| 영업·제품 | CRM · PLM | — |
| 경영·협업 | ERP · EIP · GW · RWS | ERP |

- **운영 중인 솔루션만 타일로 보인다.** 예정 솔루션은 타일을 만들지 않는다("준비 중" 남발 금지, 현황 문서 1장). 비어 있는 묶음은 제목도 숨긴다.
- 전체 17개와 예정 상태는 P-03 "계층 아키텍처·시스템 카탈로그"에서 보여 준다(MAP-02, 상태 "예정"으로 표시).
- 넓은 화면은 묶음 2열, 좁은 화면은 1열. 묶음 안 타일은 현재 타일 크기를 그대로 쓴다.
- 구현 시점: 7번째 솔루션(SPC)의 b 단계에서 홈을 묶음 구조로 바꾼다. 그 전에는 지금 모양을 유지한다.

## 6. 확정된 결정 (2026-09-30 사용자 승인 — 모두 제안대로)

1. **POP의 쓰기 방향.** POP가 MES 실적을 직접 쓰면 "교차 쓰기 금지"를 어긴다. **확정:** POP는 자기 스키마(`pop`)에 현장 입력을 확정하고, MES가 `pop.interface.confirmed_entries()`를 읽어 **가져오기**로 실적에 반영한다(WMS가 MES 입고를 가져오는 방식과 같음).
2. **SPC 측정값의 주인.** MES에는 측정값 테이블이 없다. **확정:** 측정값은 SPC가 소유하고(시드로 생성), LOT·공정·설비는 MES 코드 스냅샷으로 둔다. MES에는 조회 함수 `operation_runs()` 1개만 추가한다.
3. **EIP·GW·포털의 경계.** 포털(core)이 이미 로그인·진입·흐름 맵을 맡고 있다. **확정:** EIP = 전사 요약 대시보드·공지(`eip` 스키마, 모든 솔루션 요약 조회), GW = 전자결재·게시판(`gw`), 포털 = 인증·앱 런처만. core에는 업무 테이블을 넣지 않는다(FS-013).
4. **CMMS의 WMS 부품 연동 시점.** FS-026이 WMS 재고 계약을 바꾸는 중이다. **확정:** CMMS 1차는 부품 요청만 기록하고, WMS 재고 조회는 FS-026 병합 뒤 CMMS "살 붙이기"로 넣는다.
5. **RWS 범위.** 영상·AR은 만들 수 없다. **확정:** 원격 지원 요청 → 전문가 배정 → 단계별 작업 안내(텍스트·체크리스트) → 완료 기록. 합성 데이터로 시연할 수 있는 범위다.
6. **순서.** §1의 1~11 순서로 **확정.**
