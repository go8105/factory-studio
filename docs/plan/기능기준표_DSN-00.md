# DSN-00 — 기능 기준표 양식과 목표 DB 작업 방법

작성: 2026-10-05 (Claude Code) · 상태: **작성 — 사용자 확인 대기**
전제: [ROADMAP-02](전체설계우선_전환_ROADMAP-02.md) D77(기준표)·D78(산출물·목표 DB). 이 문서는 DSN-11~30의 **공통 양식**이다. 각 솔루션 설계는 이 양식을 그대로 채운다.

---

## 1. 기능 수준 3단계

| 수준 | 뜻 | 판단 질문 | 기본 범위 |
|---|---|---|---|
| **필수** | 이게 없으면 그 솔루션이라고 부를 수 없다. 업무 흐름이 끊긴다 | "이 기능 없이 하루 업무를 마칠 수 있나?" — 아니오 | 포함 |
| **표준** | 중소 제조업용 상용 패키지(ERP는 이카운트 수준)에 기본으로 들어 있다 | "상용 제품 데모에서 당연히 보이나?" — 예 | 포함(솔루션별로 제외 결정 가능) |
| **고급** | 대기업·특정 업종용, 외부 연동(전자세금계산서 발행, 은행 연동, PLC 등)이 필요하다 | "합성 데이터 체험에서 의미가 있나?" — 대체로 아니오 | 목록만, 범위 밖 |

- 범위는 솔루션마다 사용자가 정한다. 기본값은 **필수 + 표준 포함, 고급 제외**.
- 실제 외부 기관·결제·발송이 필요한 기능은 수준과 관계없이 **"기록만"**(예: 세금계산서는 발행 기록만, 국세청 전송 없음)으로 한다.

## 2. 솔루션 설계 문서 구조

파일: 기존 솔루션은 `docs/modules/<m>/<M>_보강설계_DSN-1x.md`, 신규는 `docs/modules/<m>/<M>_설계_DSN-2x.md`. 장 순서는 고정한다.

1. **기준표** — 기능 영역별 표(3장 형식). 기존 솔루션은 "지금" 칸에 현재 상태를 적는다.
2. **갭 요약** — ✗·△ 중 범위에 넣은 것, 영역별 개수.
3. **기능 목록** — 범위에 넣은 기능의 처리 규칙(상태 전이, 계산식, 불변 규칙). 한 기능 3~6줄.
4. **DB** — 4장 형식. 새 테이블 표, 기존 테이블 변경 표, 제약·정책.
5. **화면 목록** — 5장 형식.
6. **교차 조회** — 이 솔루션이 제공하는 조회 함수 / 다른 솔루션에서 읽는 것.
7. **결정 질문** — 사용자에게 하나씩 확정받을 항목.

## 3. 기준표 형식

```
### 영역: 회계 — 전표·장부

| ID | 기능 | 수준 | 지금 | 범위 | 비고 |
|---|---|---|---|---|---|
| ERP-F31 | 일반 전표 입력(대체·입금·출금) | 필수 | ✗ | ○ | 분개 미리보기(E-14)만 있다 |
| ERP-F32 | 총계정원장·계정별 원장 | 필수 | ✗ | ○ | 전표에서 조회 계산 |
| ERP-F38 | 은행 거래내역 자동 수집 | 고급 | ✗ | ✕ | 외부 연동 |
```

- **ID**: `<솔루션 약어>-F<두 자리>`. 영역마다 10 단위로 띄운다(영업 F01~, 구매 F11~ …). 한 번 붙인 ID는 바꾸지 않는다.
- **지금**: ✓ 있음 · △ 일부(무엇이 빠졌는지 비고에) · ✗ 없음 · — 해당 없음. 신규 솔루션은 칸을 비운다.
- **범위**: ○ 포함 · △ 기록만(외부 연동 없이) · ✕ 제외.
- 출처를 비고에 적는다: 기존 화면 ID(E-14), 결정 번호(D12), "이카운트 메뉴 참고" 등.

## 4. DB 형식 — 목표 설계 파일

**목표 DB는 `docs/db/schema-metadata/schema-target.json` 하나다.** 실제 DB 기준인 `schema.json`은 개발 때까지 그대로 둔다.

### 4-1. 문서에 적는 표

새 테이블은 첫 칸을 `` `스키마.테이블` ``로 쓴다. **검증기가 이 표를 읽어 목표 파일의 테이블 목록과 맞춘다**(`docs/modules/*/*_DSN-*.md`). 문서에 없는 테이블이 목표 파일에 있으면 검증이 실패한다.

```
| 테이블 | 한글명 | 목적 | 주요 제약 |
|---|---|---|---|
| `erp.journal_entry` | 전표 | 일반·자동 전표 머리 | 전표번호 UK, 확정 후 불변 |
```

기존 테이블 변경은 별도 표: `| 테이블 | 변경 | 이유 |` (컬럼 추가·CHECK 변경 등). 첫 칸에 백틱을 쓰지 않는다(새 테이블 표와 구분).

### 4-2. 목표 파일 고치는 방법

- 목표 파일 전체 재생성: `python3 tools/apply_dsn00.py --rebuild && python3 tools/apply_dsn11.py` (이후 DSN 스크립트를 번호 순서대로). 각 `test_dsn<nn>.py`가 "재생성 결과 = 커밋된 목표 파일"을 검사한다.
- 솔루션마다 `tools/apply_dsn<nn>.py`를 만든다. **목표 파일만** 고치고, 두 번 실행해도 결과가 같아야 한다(기존 `apply_fs*.py`와 같은 방식). 제약 번호(C·R)는 목표 파일 안에서 이어 붙인다.
- 목표 파일의 `base_task`는 지금 `schema.json`의 작업 ID(`FS-029a`)다. 설계 기간에 실제 DB가 바뀌면(예: Codex 작업 병합) 목표 파일에도 같은 변경을 넣고 `base_task`를 옮긴다 — 검증기가 다르면 실패시킨다.
- 불변 규칙은 그대로 적용된다: 범위 키 S, 업무 스키마 간 FK 금지, 달력 키 문자열 + CHECK, RESTRICT, 확정 데이터 불변.

### 4-3. 검증 명령 (DSN 작업마다 전부 실행)

```bash
python3 tools/validate_db_design.py --schema docs/db/schema-metadata/schema-target.json   # 설계 검증 → validation-report-target.json
python3 tools/audit_schema_isolation.py --schema docs/db/schema-metadata/schema-target.json  # 격리 R1~R5(새 스키마 자동 포함)
python3 tools/schema_ddl.py --apply      # 빈 DB(factory_studio_target)에 DDL 적용 → 카탈로그 대조 → ddl-report-target.json
python3 tools/build_erd.py --target      # docs/architecture/erd-target/
node tools/build_db_design.mjs --target  # docs/db/DB설계서_목표.xlsx
```

`schema_ddl.py`는 제품 마이그레이션이 아니다. 목표 설계가 PostgreSQL에서 실제로 만들어지는지(문법·FK 대상 유일성·CHECK 식)만 본다. DB 이름이 `_target`으로 끝나야 하고 실행할 때마다 지우고 새로 만든다. 지금 `schema.json`으로 돌리면 실제 DB와 같은 구조(118테이블·FK 270, 오류 0)가 나와 생성기 자체를 검증했다.

## 5. 화면 목록 형식

```
| 화면 | 이름 | 패턴 | 주 테이블 | 기능 ID | 지금 |
|---|---|---|---|---|---|
| E-14 | 분개 미리보기 | L | erp.posting_rule | ERP-F31 | 있음 → 전표 입력으로 대체 |
| E-19 | 전표 입력 | L+FormPanel wide | erp.journal_entry·journal_line | ERP-F31 | 신규 |
```

- 패턴은 공통 UI 규약(UI-02·03)의 D·L·S·P·V·W 중 하나. 새 패턴이 필요하면 결정 질문으로 올린다.
- 화면 ID는 기존 번호를 이어 쓴다. 와이어프레임은 개발 직전에 만든다(D78).

## 6. DSN 작업 하나의 완료 조건

1. 기준표 → 사용자 범위 확인(결정 질문 하나씩).
2. 기능 목록·DB·화면 목록·교차 조회 작성.
3. `apply_dsn<nn>.py` 실행 → 4-3 검증 5개 통과, 실행 결과 수치 기록.
4. 진행 현황·progress·HANDOFF 갱신, 커밋.
5. 미실행 검증(서비스 정책 동작, 화면, 성능)은 "개발 때"로 명시한다.
