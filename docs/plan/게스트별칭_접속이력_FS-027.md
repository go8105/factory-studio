# FS-027 게스트 별칭과 접속 이력

작성일: 2026-09-29 · 상태: **확정 — 사용자 승인 2026-09-29("권장안대로 진행")**
관련: [CORE 모듈 설계](../modules/core/CORE_모듈설계_FS-005f.md) · [API 계약서 FS-010](../architecture/API계약서_FS-010.md) · P-01 진입 · P-07 운영 기록

## 1. 결정

| # | 항목 | 결정 |
|---|---|---|
| D33 | 별칭 입력 | "가입 없이 둘러보기"는 **별칭 필수**(앞뒤 공백 제거 후 2~20자). 서버도 없으면 400 `VALIDATION_FAILED`(`fields.nickname`). 회원 로그인(아이디·비밀번호)은 그대로 |
| D34 | 저장 위치 | 새 테이블·컬럼 없음. 게스트 생성 감사 기록 `guest_session.created`의 `summary`에 `{"nickname": …}`. 헤더에는 표시하지 않는다 |
| D35 | 조회 | P-07 운영 기록에 **"게스트 접속"** 보기(`GET /admin/guest-visits`, ADMIN만): 접속 시각 · 별칭 · 공간 번호 · 상태(사용 중/정리됨) |
| D36 | 보관 | 별칭은 **90일** 뒤 기존 정리 작업(15분 타이머)이 `summary`에서 `nickname` 키만 지운다. 접속 시각·공간 번호는 남는다. `core.audit_event` "일반 런타임 UPDATE/DELETE 금지" 정책에 이 한 가지 예외를 명시한다 |

## 2. 이유와 경계

- 감사 기록은 게스트 공간이 정리돼도 공간 번호 스냅샷과 함께 남으므로(`scope_kind='RETIRED'`) 접속 이력으로 그대로 쓸 수 있다.
- 별칭은 실명이 들어올 수 있는 자유 입력이다. 입력 칸에 "실명 대신 별칭 · 접속 기록 확인용"을 안내하고, 보관 기간을 둔다. IP·브라우저 정보는 수집하지 않는다.
- 멱등: 같은 `Idempotency-Key`로 다른 별칭을 보내면 기존 규약대로 422(요청 digest에 별칭 포함).
- 화면에서만 필수로 하면 API로 우회할 수 있으므로 서버가 강제한다.

## 3. 바뀌는 것

| 대상 | 변경 |
|---|---|
| API | `POST /guest-sessions` 본문 `{nickname}` 필수 · `GET /admin/guest-visits` 신설 |
| 메타데이터 | `core.audit_event` SERVICE 정책 문구에 D36 예외 추가(스키마 변경 없음, Excel 재생성) |
| 화면 | P-01 별칭 칸·안내 · P-07 "게스트 접속" 탭 |
| 테스트 | 게스트를 만드는 백엔드·브라우저 테스트 모두 별칭 전달 |
| 도움말 | P-01·P-07, 공통 이용 안내 |

## 4. 인수 기준 (AC-165~169)

| AC | 기준 |
|---|---|
| 165 | 별칭 없음·공백만·1자·21자 → 400, 공간 생성 0 |
| 166 | 정상 생성 시 `guest_session.created` 요약에 별칭(공백 제거된 값) |
| 167 | 같은 키·다른 별칭 → 422, 같은 키·같은 별칭 → 같은 결과 |
| 168 | `/admin/guest-visits`는 ADMIN만(게스트 404·일반 회원 403), 정리된 공간도 "정리됨"으로 보인다 |
| 169 | 90일 지난 접속 기록은 정리 작업 뒤 별칭만 사라지고 행은 남는다 |
