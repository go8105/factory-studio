# 제조 업무 통합 포털 — 개발 기준 v1.1

> v1.1 개정(2026-09-20, FS-006a): 최종 목적을 포트폴리오로 확정하고, 업무 범위를 판매계획~출하·매출 구간으로 확장했다.
> 구현 모듈은 MES·FEMS·ERP, 준비 중은 QMS·WMS·BEMS다. 요약은 [현재 기획과 진행 현황](현재기획_진행현황.md)을 본다.

작성: 2026-09-20
상태: 제품 방향·설계 원칙·단계별 범위의 기준안 확정. 실제 제품 코드 미착수.
가칭: Factory Studio. 명칭·브랜드·색상은 추후 조정한다.

## 1. 목적과 문서 우선순위
현장 업무가 왜 필요하고, 무엇을 준비하며, 어떤 순서로 처리하고, 결과가 다음 업무에 어떻게 전달되는지 배우는 모듈형 실습 플랫폼이다. 개발자의 실무 경험을 가상 사례로 일반화해 기능과 학습 콘텐츠로 함께 축적한다.

**최종 목적은 이직 시 제출할 포트폴리오다.** 운영 전환은 없으며 실제 운영 데이터는 들어오지 않는다.
성공 기준은 앱 개수가 아니라 한 흐름이 끝까지 동작하고 그 설계 근거를 설명할 수 있는 것이다. 코드, 설정, 예시 데이터는 독립 작성하며 회사 파일·서버를 전제로 하지 않는다.

현재 개발 범위와 순서는 이 문서를 최우선으로 적용한다. 기존 아키텍처의 트랜잭션·보안·정합성 원칙은 유지한다. 기존 16주 로드맵은 작업 ID와 요구사항 추적용으로 보존하며 전체 일정 약속으로 사용하지 않는다. 이전 HTML은 상호작용 참고 자료이며 최종 UI 사양이 아니다.

## 2. 대상 사용자와 진입 방식
- 입문자: 용어와 선행 조건을 확인하고 안내에 따라 하나의 업무를 수행한다.
- 현업 이해를 넓히려는 사용자: 자신의 업무와 앞뒤 부서 업무의 연결을 확인한다.
- 포트폴리오 검토자: 짧은 시연으로 업무 이해·설계·정합성·운영 역량을 확인한다.

두 가지 진입을 제공한다.
1. 가이드 실습: 학습 시작 → 추천 경로 → 준비사항 → 업무 실행 → 결과 확인 → 다음 업무.
2. 자유 탐색: 앱 아이콘 → 해당 업무 → 현재 맥락의 도움말과 연결 업무.

학습 모드와 자유 모드는 같은 업무 화면과 API를 사용한다. 학습용으로 따로 만든 가짜 성공 화면을 두지 않는다.

## 3. UI 방향
최신 Odoo 참고 이미지의 공간 구성처럼 독립된 정사각형 아이콘과 아래 짧은 이름을 넉넉한 간격으로 배치한다. 전체를 감싼 큰 표형 타일과 긴 설명 중심의 홈은 사용하지 않는다. Odoo의 로고나 아이콘 자산을 복사하지 않고 자체 아이콘 체계를 적용한다.

홈: 공통 상단 바(앱 홈, 사업장, 개인 체험 공간, 계정) + 짧은 '학습 이어하기' 안내 + 앱 아이콘 그리드. 첫 공개 아이콘은 학습 시작, MES, FEMS, **ERP**, 프로세스 맵, 통합 대시보드, 모듈 관리이다. **QMS·WMS·BEMS는 준비 중으로 표시**하며, 선택하면 빈 화면이 아니라 해당 모듈의 역할·연결·향후 계획을 설명하는 카드를 보여준다.

가입하지 않은 방문자도 '데모로 둘러보기'로 즉시 진입할 수 있다. 심사자에게 회원가입을 요구하지 않는다.

업무 화면: 앱 전환 → 현재 업무/문서 → 핵심 입력·실행 영역 → 접거나 펼칠 수 있는 학습 도움말 → 결과/다음 업무.
도움말은 목적, 필요한 기준정보, 입력값의 의미, 수행 순서, 주의할 오류, 결과와 다음 단계로 구성한다. 복잡한 설명은 점진적으로 펼친다.

색상, 배경, 아이콘 스타일, 간격은 기능을 만들며 다듬는다. 현재 다크 테마를 최종 디자인으로 고정하지 않는다. 모바일에서는 아이콘을 줄바꿈하고 도움말을 아래로 이동한다. 키보드 접근, 읽을 수 있는 대비, 상태의 텍스트 표현을 기본으로 한다.

## 4. 학습 과정과 완료 판정
기본 사업장은 가상의 **소형 전자부품 양산** 사업장이다(사출→조립→검사 3공정). 생산 방식은 MTS(재고생산)이며 판매계획이 흐름의 기점이다. 상세는 [시드 정의](../architecture/합성데이터_시드정의_FS-005b.md)를 따른다.

학습은 하나의 긴 과정이 아니라 5개 과정으로 나눈다. 전체 흐름 17개 노드의 정의는 [MTS 전체 흐름 노드 정의서](../architecture/MTS_전체흐름_노드정의서_FS-005a.md)에 있다.

| 과정 | 배우는 내용 | 포함 노드 | 완료 근거 |
|---|---|---|---|
| **C0 전체 둘러보기** | 판매계획부터 매출까지 어떤 업무가 어떤 순서로 연결되는가 | 1~17 (읽기) | 노드 카드 열람과 흐름 확인 질문 |
| **C1 생산 한 건** | 작업지시가 실적이 되는 과정 | 작업지시·LOT·공정 실행·실적 확정 | 서버가 검증한 업무 상태와 실적 |
| **C2 계획에서 지시까지** | 계획과 실행의 관계, 계획수량과 생산수량의 차이 | 기준정보·판매계획·생산계획·작업지시 | 계획 확정과 지시 전개 결과 |
| **C3 만든 것을 내보내기** | 포장·재고·출하·매출의 연결. 매출은 출하 시점에 인식된다 | 패킹·입고·수주·출하지시·출하·매출 | 출하 확정과 매출 1건 생성 확인 |
| **C4 생산과 에너지** | kW/kWh, 원단위, 집계 경계 | 공정 실행·실적·FEMS 기준정보 | 계산 결과 조회 및 해석 질문 |

C0은 업무 실행 없이 카드 열람만으로 진행되므로 **게스트의 기본 진입 과정**이며 3분 완주를 목표로 한다. C1~C4는 실제 업무 실행과 서버 검증을 요구하며 각각 10~15분을 목표로 하되 실제 사용자 시험으로 조정한다.

건물 에너지(제조/공용 경계와 잔여분)는 BEMS가 준비 중이므로 학습 과정이 아니라 설명 카드로 제공한다.

학습 화면은 현재 단계와 전체 흐름을 함께 보여준다. 부족한 모듈·기준정보·권한은 이유와 해결 위치를 안내한다. 모듈이나 체험 데이터를 사용자 모르게 변경하지 않는다. 오류 시 틀린 이유와 수정 위치를 안내한다. 화면을 열거나 다음 버튼을 누른 것만으로 실습 완료로 처리하지 않는다.

확장 실습: 생산 0일 때 원단위 계산 불가, 계측 누락, 잘못된 상태 전이, 중복 실적 입력, 수주수량 초과 출하지시, 양품 초과 패킹, 이중 출하. 품질 보류·재고 차단은 QMS/WMS 단계에서 추가한다. 학습 경로의 선행 조건과 업무 모듈 실행 의존성은 별도로 관리한다.

## 5. 실무 경험을 기능으로 만드는 작업 방식
실무 사례 한 건을 다음 순서로 처리한다.

사례 설명 → 업무 카드 → 가상화 → 공통/특화 구분 → 데이터·규칙 설계 → 하나의 작동 흐름 구현 → 실습 안내 → 검증·회고.

업무 카드의 필수 항목:
- 업무명, 목적, 수행자, 시작 조건, 필요한 입력/기준정보
- 정상 순서, 산출물, 다음 업무, 승인 또는 권한 조건
- 자주 발생하는 오류, 수정·취소 방법, 완료 기준
- 모든 제조 현장에 공통인 부분, 업종별 설정, 특정 회사에만 해당하는 부분
- 출처 유형: 사용자 설명 / 공개 자료 / 설계 가정

기본 업무 카드는 이미 작성한 '작업지시 기반 LOT 생산 및 에너지 확인'으로 시작한다. 이후 사용자가 실제로 자주 하는 업무의 개념과 순서를 제공하면 후보 목록에 추가한다. 회사 원본 파일이나 실제 고객·거래 데이터는 필요하지 않다.

공통화 수준:
1. 플랫폼 공통: 인증, 권한, 체험 공간, 감사 기록, 모듈 설정, 학습 진도.
2. 업무 공통: 기준정보 선택, 목록/상세 화면, 단위·시간 표시, 검증 오류, 첨부와 이력 표시.
3. 도메인 공통: MES 상태 전이, 에너지 집계, 재고 원장, 회계 전기 규칙.
4. 업종 설정: 공정명·공정 경로·검사 항목·측정 단위·임계치.

두 개 이상의 실제 사용 사례에서 동일성이 확인된 부분부터 추출한다. 화면이 비슷하다는 이유로 생산실적·재고·회계의 상태와 규칙을 하나의 범용 엔진으로 합치지 않는다. 첫 버전에 노코드 폼 제작기, 범용 워크플로 엔진, 외부 플러그인 마켓을 만들지 않는다.

## 6. 제품 구조
React + TypeScript + Vite / FastAPI / PostgreSQL을 사용하는 모듈형 모놀리스이다. 버전은 착수 시 지원·호환성을 확인해 고정한다. 단일 저장소에서 frontend, backend, migrations, seed, tests, docs를 관리한다. 개발 PC는 MacBook, 로컬 실행은 Docker Compose를 기준으로 한다.

core: 계정·세션·권한, 체험 공간, 사업장·품목·설비·계측기 등록, 앱 등록 및 설정, 감사 기록.
learning: 과정·단계·선행 조건·가이드·검증 조건, 학습 시도와 완료 기록. 첫날부터 설계하고 매 업무 기능과 함께 구현한다.
mes: 작업지시·공정 경로·LOT·공정 실행·생산실적.
fems: 제조 계측 기준정보·집계·생산 원단위. **계측 수집 파이프라인·알람 서버는 만들지 않는다.** 계측값은 seed로 생성한다.
erp: 거래처·판매계획·수주·출하지시·출하·매출 (ERP-1). 매입·채권채무·기초회계·전자세금계산서는 범위 밖이다.
process_map: 전체 흐름 노드·연결·업무 카드. 업무 데이터가 아니라 콘텐츠이므로 세대 축을 갖지 않는다.
qms/wms/bems: 준비 중. bems는 공용 계측·환경 이력·통합 집계 경계를 담당할 예정이다. 설명 카드만 제공하며 활성화할 수 없다. 이전 문서의 책임과 데이터 변경 경계는 그대로 유지한다.

각 모듈은 자기 데이터만 변경한다. 다른 모듈의 변경은 소유 모듈의 업무 함수를 호출한다. 공유 DB의 정합성은 명시적 트랜잭션으로 유지하며 내부 HTTP 호출을 만들지 않는다. 모듈 간 연결도 독립 서비스가 아니라 명시적인 함수 계약으로 시작한다.

## 7. 공통 데이터와 학습 기록 설계 기준
- 업무 행은 체험 공간 ID와 데이터 세대 ID를 갖는다. 고유 키·관계·조회 조건도 범위를 포함해 교차 공간/세대 참조를 막는다.
- API 입력의 공간 ID를 신뢰하지 않고 인증된 접근 범위를 서버에서 확인한다.
- UTC로 저장하고 사업장 시간대(기본 Asia/Seoul)로 표시한다. 수량에는 단위, 계측에는 시간 범위와 품질 상태를 둔다.
- 생산수량·양품·불량을 구분하고 변경 이력을 남긴다. 금액은 부동소수점 대신 Decimal/NUMERIC을 사용한다.
- 계측기 부모/자식 관계, 값의 소유 모듈, 직접 계측/추정, 집계 경계를 명시한다.
- 모듈 설정·대시보드 배치·학습 기록은 체험 데이터 세대와 분리한다.
- 학습 콘텐츠는 안정적인 course_key/step_key와 콘텐츠 버전을 갖는다. 학습 완료는 서버에서 업무 결과 및 해석 응답을 검증해 기록한다.
- 학습 근거는 검증 시점의 요약·과정 버전·검증 결과를 보존한다. 삭제될 업무 행에만 의존하는 FK로 학습 이력을 유지하지 않는다.
- 초기화로 미완료 실습의 대상이 사라지면 '실습 다시 준비'로 안내한다. 과거 완료 기록을 새 데이터의 진행 상태로 오인하지 않는다.
- 상세 ERD, 필드 목록, 트랜잭션 경계는 첫 설계 단계 산출물이다. 본 문서를 DB 구현 완료로 표시하지 않는다.

## 8. 모듈 활성화와 권한
내부 모듈의 코드는 배포 시 등록하고 스키마도 배포 시 마이그레이션한다. 사용자는 자기 체험 공간에서 모듈을 켜고 끈다. 비활성화는 데이터 삭제가 아니다.
core와 learning은 항상 활성이다. FEMS와 BEMS는 독립적으로 동작하며 MES가 함께 활성일 때 생산 연계 기능을 제공한다.
필수 의존성·진행 업무·예약 작업과 충돌하면 비활성화를 거부하고 원인을 안내한다. 모듈 설정 변경으로 품질 보류 등의 기존 업무 제약이 우회되지 않는다.

| 행위 | 학습자 | 플랫폼 관리자 |
|---|---|---|
| 개인 실습·진도 조회 | 본인 범위 | 운영상 필요한 권한 범위 |
| 모듈 선택·배치·수동 초기화 | 본인 공간 | 운영 및 장애 대응 |
| 콘텐츠 수정·게시 | 불가 | 가능, 변경 이력 기록 |
| 다른 사용자의 업무 접근 | 불가 | 기본 미허용; 지원 접근은 별도 명시 권한·감사 필요 |

모듈 활성 상태는 화면, API, 내부 업무 진입, 예약 처리에 적용한다. 학습자의 학습 완료 여부는 업무 권한을 부여하는 수단이 아니다.

## 11. 품질·학습·운영 완료 기준
기능마다 코드·안내·오류 설명·의미 있는 검증을 함께 완료한다.
- 상태 전이, 수량 정합성, 계측 계산은 단위/통합 검증.
- PostgreSQL을 사용해 사용자 격리·중복 요청·트랜잭션·초기화 실패를 검증.
- 핵심 실습 경로는 브라우저 여정으로 검증. 버튼 클릭만으로 성공을 판정하지 않는다.
- 사용자가 안내를 따라 완료하고 다음 업무를 설명할 수 있는지 간단한 사용자 점검을 한다. 모집 전에는 내부 시나리오 검증으로 구분해 기록한다.
- 지표: 단계별 완료·중단 위치, 오류 유형, 도움말 사용, 해석 질문 결과. 익명/집계 위주로 필요한 범위만 기록하고 학습자 개인 순위는 만들지 않는다.
- 초기화는 새 세대 준비→검증→활성 전환이며 실패 시 기존 세대를 유지한다. 주간 월요일 04:00 Asia/Seoul, 누락 주차 따라잡기·중복 실행 방지.
- 로그인·권한·학습·모듈 설정·콘텐츠는 초기화에서 보존한다.
- Linux Compose, 정적 프론트+FastAPI+PostgreSQL. Caddy는 기본안이며 Vultr 기존 구성에 맞춘다. 기존 AI 비서는 변경하지 않는다.
- DB 비공개, HTTPS, 외부 백업, 복원 시험, 제한된 로그, 예약 실패 기록을 배포 완료 조건으로 둔다. Mac에서는 같은 CLI로 수동 검증한다.

## 12. 작업 관리와 기존 ID 매핑
각 작업은 업무 카드/요구사항 ID, 구현 범위, 완료 기준, 검증 결과, 남은 제약을 기록한다. 미구현 화면은 완료로 표시하지 않는다. 의존성이 없는 작업은 진행할 수 있으나 선행 조건이 필요한 업무를 건너뛰지 않는다.
