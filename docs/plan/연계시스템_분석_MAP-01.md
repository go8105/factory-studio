## 2. 누락 시스템별 연결 분석

연결 표기는 우리 규칙을 따른다. 솔루션 간 FK는 두지 않는다. 타 솔루션 값은 **코드 문자열 스냅샷** 또는 **읽기 전용 조회 인터페이스**(`fs/<솔루션>/interface.py`)로만 가져온다. 괄호 안은 `content/flow-map.json`의 노드 id다.

| 시스템 | 무엇을 하나 | 받는 것 (← 우리 시스템) | 주는 것 (→ 우리 시스템) | 분류 |
|---|---|---|---|---|
| **EIP** | SSO·통합 포털 | 각 솔루션 진입·대시보드 | — | **흡수** — 포털(P-01~05)이 EIP다. 레퍼런스 화면에서 포털 = EIP로 표기 |
| **POP** | 현장 작업자 단말 | MES 작업지시(`work_order`) | 실적·불량·투입 스캔 → MES 공정 실행(`operation_run`) | **흡수** — MES의 현장 입력 모드. 별도 스키마 없음 |
| **SPC** | 공정 측정값 관리도·Cpk | MES 공정 실행 측정값(`operation_run`) | 관리 한계 이탈 → QMS 판정·보류(`quality_inspection`) | **QMS 확장 후보** — FS-023 D8이 1차 범위에서 제외 |
| **CMMS** | 예방보전·고장 작업지시 | MES 설비 마스터·가동, **FEMS·BEMS 경보**, WMS 부품 재고 | 보전 중 설비 정지 → MES 설비 가용성 | **구현 후보 1순위(미착수)** — BEMS 경보가 이미 있어 "경보 → 정비" 흐름이 가장 짧다 |
| **SCM** | 공급망 가시성·수요 예측·공급업체 평가 | WMS 입고, QMS 판정, ERP 수주 | 수요 예측 → ERP 판매계획(`sales_plan`) | **설명 카드 유지**(P-04) |
| **TMS** | 배차·운송·운임 | ERP 출하지시(`shipment_order`), WMS 출고(`inventory_move`) | 배송 완료 → ERP 출하(`shipment`) | **설명 카드** — FS-026(트럭 도착·출고 예약)과 경계 겹침, FS-026 확정 후 문구 확정 |
| **PLM** | 설계 BOM·도면·설계 변경(ECO) | — | 품목·BOM 개정 → MES 기준정보·BOM(`master_data`) | **설명 카드** |
| **CRM** | 영업 기회·고객 클레임 | ERP 출하·매출(`sales_record`) | 영업 기회 → ERP 견적·수주(`sales_order`), 클레임 → QMS | **설명 카드** |
| **ELB/MRO** | 간접자재 전자구매 | CMMS 부품 요청, WMS 재고 부족 | 입고 → WMS, 매입 → ERP 매입채무 | **설명 카드** — CMMS가 없으면 받는 쪽이 비어 있음을 카드에 명시 |
| **그룹웨어** | 전자결재·메일·게시판 | ERP 전표 | 결재 결과 | **제외** — 제조 업무 흐름과 관계없음 |
| **RWS** | 영상·AR 원격 지원 | MES·CMMS 이슈 | 작업 기록 | **제외** — 합성 데이터 전시로 보여줄 기능이 없음 |

### 2.1 연결 그림(텍스트)

```
            PLM ─(품목·BOM 개정)─┐                 CRM ─(영업 기회)─┐
                                ▼                                  ▼
 SCM ─(수요 예측)→ ERP 판매계획 → MES 생산계획 → 작업지시 → 공정 실행 ←(현장 입력)─ POP
                                                     │        │
                                         (측정값)→ SPC ─(이탈)→ QMS 판정·보류
                                                     │
                                          실적 → 패킹 → WMS 입고 → 출고 ─→ TMS ─(배송 완료)→ ERP 출하 → 매출
                                                                                      │
                                                                               CRM ←(클레임)─ QMS
 FEMS 경보 ─┐
 BEMS 경보 ─┴→ CMMS 작업지시 ─(부품 요청)→ ELB/MRO ─(입고)→ WMS / (매입)→ ERP 채무
```

굵은 흐름(ERP·MES·QMS·WMS·FEMS·BEMS)은 이미 구현했다. 나머지는 모두 설명용이다.

## 3. 결정과의 충돌 점검

| 항목 | 기존 결정 | 이 분석의 처리 |

| SCM/PLM/CRM 추가 개발 제외 | `개발기획_설계_일정_최종기준.md:159` | **충돌 없음** — 설명 카드·흐름도만. 개발하지 않음 |

## 4. P-03에 붙일 흐름도 2장 설계(구현 대기)

P-03 "전체 업무 흐름" 상단에 보기 전환 3개를 둔다. 폭이 충분하면(≥1200px) 오른쪽에 나란히, 좁으면 탭으로 바꾼다.

| 보기 | 원천 | 우리식 변환 |
|---|---|---|
| ① 전체 업무 흐름 | 기존 `flow-map.json` | 변경 없음 |
| ② 계층 아키텍처 | 레퍼런스 탭 1 | 6계층 × 17시스템. **구현 6개는 실선 박스 + 솔루션 화면 링크**, 설명 카드는 점선, 흡수(EIP·POP)는 "포털/MES에 포함" 부기, 제외(그룹웨어·RWS)는 회색 |
| ③ 시스템 카탈로그 | 레퍼런스 탭 2 | 카드 + 상세 패널 + 연관 시스템 칩. 상세 패널에 **§2 표의 "받는 것/주는 것"** 을 넣는다. 구현 시스템은 "화면으로 이동" 링크 |

- 색: UI 기준(백자·먹색·쪽빛, 저채도 배지). 레퍼런스의 8색 태그는 상태 배지 3종(구현·설명·제외)으로 줄인다.
- 데이터: `content/systems.json`을 새로 만든다(17개: abbr·이름·계층·분류·요약·받는 것·주는 것·연관·route). ②③이 같은 파일을 읽는다. 스키마 파일 `content/systems.schema.json`도 함께 만든다.
- 흐름 맵 ①의 점선 노드: `flow-map.schema.json`의 `card` 대상 enum이 현재 `scm`뿐이다. `tms·plm·crm·elb`를 추가하면 ①에도 점선 노드를 붙일 수 있다(선택).
- 도움말: `content/help/portal/p-03.md`의 "17개 단계" 문구와 "제외한 SCM" 문구를 갱신한다. P-04에 카드 4장(TMS·PLM·CRM·ELB)을 추가한다.
- 테스트: `frontend/src/portal/flow.test.ts`·`content-pages.test.tsx`에 보기 전환, 구현 6개 링크, 설명 카드 표기를 추가한다.

예상 변경 파일: `ContentPages.tsx`, `styles.css`(또는 Home.css), `content/systems.json`(+schema), `p-03.md`, `p-04.md`, 테스트 2개. DB·API 변경 없음.
