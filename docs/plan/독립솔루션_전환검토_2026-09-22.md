# 독립 전문 솔루션 전환 검토

검토일: 2026-09-22. 제품 구현 및 DB/Excel 수정 없음.

## 최신 사용자 의도

하나의 포털에서 MES·ERP·FEMS를 각각 독립적인 전문 솔루션으로 보여주는 포트폴리오다. 각 솔루션의 대시보드·메뉴·업무 흐름이 중심이며, 이전의 학습 과정 중심 통합 플랫폼을 그대로 확장하는 작업이 아니다.

## 확인한 자료

references의 세 Excel을 읽기 전용으로 추출하여 설계규약·목차·테이블 정의·업무 범위를 검토했다. 현황, README, 문서 지도, 모듈 README, FS-005c/005d, 진행 기록 및 기존 개발 기준과 대조했다. 아래 수량은 각 Excel 목차 집계다.

| 솔루션 | 테이블 | 컬럼 | 범위 |
|---|---:|---:|---|
| MES | 22 | 348 | 사용자·권한, 품목·거래처·단위, 재고·원장, 작업장·공정·BOM·작업지시·공정실적 |
| FEMS | 24 | 350 | 계측·집계·배분·목표·원단위, 온실가스 활동자료·산정·인벤토리, ESG·증빙·검증 |
| ERP | 41 | 698 | 견적·수주·구매·재고·채권채무·수금지급·기초회계·수동 세금계산서 발급확인 |

87테이블이라는 합계는 파일별 정의 수의 합이며 통합 DB 테이블 수가 아니다. 같은 이름의 테이블도 솔루션별 소유가 다르다. 기존 schema.json은 v0.4.0, 60테이블·579컬럼으로 이 세 파일과 다른 설계다.

ERP의 00.설계규약은 공통 포털의 역할을 진입과 로그인으로 제한하고 MES/FEMS와 업무 DB/API를 공유하지 않는다고 명시한다. ERP 품목은 MES 품목과 독립이다. FEMS에는 MES 실행을 직접 요구하지 않고 생산량을 보관할 PRODUCTION_DT가 있다.

## 정리해야 할 충돌

1. 현황 첫 문단·개발 기준·루트 README가 여전히 학습 플랫폼 중심이다. 최신 사용자 정의로 변경해야 한다.
2. AGENTS와 FS-005d는 품목·설비·계측기를 core가 독점 소유하도록 하지만 ERP Excel은 업무 마스터 독립을 명시한다. 새 아키텍처 결정으로 대체해야 하며 단순 sub_module 분류로 해결되지 않는다.
3. ERP-1 한정, FEMS 기준정보·조회 한정은 새 Excel 범위보다 좁다. 기능별 첫 공개 범위와 구현 순서를 새로 정해야 한다.
4. 현재 Excel/메타데이터/ERD는 기존 통합 학습 모델이다. 세 독립 DB의 최신 기준으로 표시하면 안 된다. 기존 검사 통과도 새 DB의 검증 증거가 아니다.
5. FEMS 모듈 README와 현황은 FS-005c 반영 완료, FS-005c 본문과 진행 기록은 미반영으로 상충한다.
6. 루트 README에는 이동 전 docs 경로가 남아 있고 references README는 MES 파일만 설명한다.
7. 기존 20~26작업주 일정 및 설계 진행률은 새 범위에 재사용할 근거가 없다.

## 아직 필요한 연결 설계

- MES 파일은 표지에서 기초 골격이라고 명시한다. 현재 전용 정의에는 판매/생산계획, BOX/PALLET 구성, 출하지시·출하, 독립 검사·바코드 발행 이력 테이블이 없다. 기존 요구 유지 여부와 기존 통합 설계에서 가져올 내용을 정해야 한다. 테이블 부재가 곧 기능 구현 불가능이라는 뜻은 아니다.
- MES 사용자에는 비밀번호 해시가 있으나 ERP는 공통 인증 subject만 사용한다. 공통 인증과 각 솔루션 업무 권한의 경계를 맞춰야 한다.
- 게스트 체험, 사용자별 격리·초기화 정책은 기존 workspace/generation 모델을 그대로 강제하지 말고 각 솔루션의 회사/사업장 범위와 대조해야 한다.
- FEMS 파일의 대상 에너지원·산정/공시 범위·생산량 입력 방식은 첫 데모 범위와 대응시켜야 한다. 실제 수집·외부 연동은 파일에 언급됐다는 이유만으로 구현 승인으로 보지 않는다.

## 제안하는 다음 작업

먼저 독립 솔루션 전환 아키텍처와 범위 문서를 작성한다. 포털/공통 인증/각 솔루션 업무 권한과 데이터 소유를 구분하고 세 Excel을 각각 설계 입력으로 지정한다. 논리 독립과 서버/프로세스의 물리 분리는 별도 결정이다.

그다음 각 솔루션의 메뉴→업무 흐름→화면→API→DB를 대응시키고 누락만 보완한다. 새 기준에 맞춘 모듈별 ERD와 구현 일정은 그 결과로 갱신한다. 전체 설계 확인 후 개발 원칙은 유지한다.

확인할 질문은 두 가지다. (1) 세 솔루션은 공통 인증만 공유하고 업무 DB/API/마스터는 독립으로 둘 것인가? ERP 파일에는 그렇게 명시돼 있다. (2) 학습 기능은 도움말·업무 안내로 남길 것인가, 별도 과정/진도까지 유지할 것인가?

이번 검토는 문서 범위·경계 대조다. 모든 FK/CHECK의 정합성, 회계·온실가스 산정의 법규/표준 적합성, 실제 PostgreSQL 적용 및 동시성 시험을 인증하지 않는다.
