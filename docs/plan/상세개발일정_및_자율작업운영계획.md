# Factory Studio 상세 개발 일정 및 자율 작업 운영 계획

## 1. 작업 위임 범위
사용자가 요청한 범위 안에서 다음 작업을 개발 담당 에이전트가 수행한다.
- 신규 프로젝트 구성, 구현 방식 결정, 일반적인 오류 수정과 리팩터링.
- 새 프로젝트의 PostgreSQL 테이블·컬럼·키·제약·인덱스 설계 및 변경.
- 마이그레이션 작성·검증·적용, 가상 기준정보와 실습 데이터 생성·등록.
- Excel DB 설계서 작성 및 모든 스키마 변경과 동기화.
- 단위·DB 통합·브라우저 테스트, 결과 기록, 관련 문서 갱신.
- 로컬 AI 비서 프로젝트의 구조·운영 경험 참조.

스키마의 실제 상태는 마이그레이션과 적용된 DB로 검증한다. Excel은 사람이 검토하는 설계 산출물이며 SQL 실행 도구로 사용하지 않는다.
새 프로젝트의 로컬/테스트 DB에서 일반적인 변경과 합성 데이터 재생성은 반복 확인 없이 진행한다. 기존 secretary 프로젝트·DB·서비스는 변경 대상이 아니다. 운영 데이터 파괴, 기존 서비스 영향, 유료 서버 변경, 외부 공개 설정은 구체적인 영향과 실행안을 준비한 뒤 해당 단계에서 처리한다.
작업은 활성 개발 세션에서 순차 진행한다. 대화 밖 상시 자동 개발이나 주간 작업 예약을 설정한 것은 아니다. 제품의 주간 데이터 초기화와 개발 일정은 별개다.

- README와 파일 목록을 읽기 전용으로 확인했다.

- 아직 전체 코드 감사, 기존 테스트 실행, 서버 SSH 접속, 실제 서비스 상태 검증은 하지 않았다.

### 새로 작성할 항목

## 3. 환경 및 서버 전제
사용자 제공 정보: Vultr 서울, Ubuntu 24.04 LTS, vc2-1c-1gb. 기존 secretary API는 8000 사용, PostgreSQL은 로컬 접근 전용. 메모리 1GB 및 swap 사용 이력은 현재 측정값이 아니다.

개발 기본안:
- 새 저장소/폴더명: factory-studio.
- 프로젝트 경로는 `/Users/hwang-kyoungho/projects/factory-studio`로 확정했다.
- 개발 DB: factory_studio_dev, 테스트 DB: factory_studio_test.
- 배포 DB: factory_studio. 환경별 전용 계정, 런타임 계정과 마이그레이션 권한을 구분한다.
- 기존 secretary DB와 postgres 슈퍼유저를 새 앱의 런타임 연결에 사용하지 않는다.
- 로컬 개발 포트 후보: frontend 5173, API 8001, Compose DB는 필요한 경우 loopback 5433. 실제 사용 여부 확인 후 확정한다.
- Compose 프로젝트명, 볼륨명, systemd 작업 이름은 factory-studio 접두어로 분리한다.
- 운영 API는 기존 프록시에서 접근하는 loopback/내부 네트워크만 사용한다. 8001을 외부에 공개하는 것을 기본으로 삼지 않는다.

별도 DB라도 같은 PostgreSQL 인스턴스/서버를 사용하면 CPU·메모리·I/O는 공유한다. DB 분리만으로 자원 간섭과 모든 락 문제가 없어지는 것은 아니다. 마이그레이션에는 lock_timeout/statement_timeout을 두고 장시간 대기를 실패로 기록한다.

서버 배포 판단은 실제 메모리·swap·디스크·부하·포트·Nginx·PostgreSQL 구성 확인 후 한다. 1GB 서버에 신규 서비스를 즉시 추가하지 않는다. 별도 인스턴스와 기존 인스턴스 증설을 비교하되, 2GB로 충분하다고 미리 확정하지 않는다. 같은 서버라면 기존 Nginx를 먼저 검토하고 80/443에서 Caddy를 중복 실행하지 않는다. 별도 서버라면 기존 Caddy 기본안을 사용할 수 있다.

비밀번호·토큰을 출력하는 grep 명령은 실행하지 않는다. 추후 접속에 필요한 비밀값은 출력·로그·문서·Git에 남기지 않는 방식으로 환경에 주입한다. 공개 GitHub 문서에는 실제 서버 IP·접속 계정·내부 운영 경로 대신 변수 예시를 사용한다.

## 5. Excel DB 설계서 관리
### 시트 구성
| 시트 | 주요 항목 |
|---|---|
| 개요 | 환경, 설계/마이그레이션 revision, 갱신일, 검증일, 책임 기준 |
| 테이블 목록 | 스키마, 테이블, 한글명, 목적, 소유 모듈, 격리·초기화 정책 |
| 컬럼 정의 | 순서, 컬럼, 설명, 타입·길이·정밀도, NULL, 기본값, PK/FK, 가상 예시 |
| 관계 | 참조 양쪽, 복합 키, 관계 의미, 삭제/수정 정책 |
| 제약·인덱스 | UNIQUE/CHECK/index, 컬럼 순서, 조건, 도입 이유 |
| 코드·상태 | 허용값, 전이, 취소/역처리, 담당 모듈 |
| 보존·초기화 | 계정/학습/설정/업무 구분, 세대 범위, 보존 규칙 |
| 변경 이력 | 작업 ID, revision, 변경 전후, 이유, 적용 환경, 검증 결과 |

### 갱신 시점
최초 ERD 작성 시 초안을 만들고, 테이블·컬럼·관계·제약·인덱스를 변경하는 매 작업에서 갱신한다. 스키마 변경이 없는 작업에는 불필요하게 버전을 올리지 않는다. 매 단계 종료 시 실제 DB 카탈로그와 대사한다.

### 변경 절차
요구사항/업무 카드 → 데이터 소유권 검토 → 모델과 마이그레이션 → 임시 테스트 DB에 적용 → DB 카탈로그 대사 → Excel 생성/갱신 → 설명·레이아웃 확인 → 통합 테스트 → 개발 DB 적용 → 결과 기록.
초기 설계안과 실제 적용 상태를 명확히 구분한다. 부분 실패 시 완료로 표시하지 않는다. 문서 변경과 마이그레이션은 같은 변경 묶음으로 관리한다. Excel 생성은 메타데이터+실제 스키마 정보를 조합해 반복 가능하게 만들며 외래 키·기본값·인덱스의 누락을 검사한다.

이미 공유/적용한 migration은 수정하지 않고 새 revision을 추가한다. 삭제·타입 변경 등 데이터 영향이 큰 변경은 영향 분석과 복구 수단을 준비한다. 운영 복구는 이미지 복귀와 DB 복원을 구분한다.

주차별 모든 DB 변경에는 5절의 Excel 갱신과 마이그레이션 검증이 포함된다. FS-007 한 번으로 문서 작업을 끝내지 않는다. S2/M1 이전에도 기능별 검증을 즉시 수행하며 마지막 주에 테스트를 몰지 않는다.
배포 대상이나 인프라 변경이 미확정이면 로컬 완료와 배포 미완료를 분리 기록한다. 상태가 확정되지 않은 외부 작업 때문에 로컬 학습 기능을 중단하지 않는다.

## 7. 데이터 등록 및 테스트 원칙
합성 사업장, 사용자별 체험 공간, 품목·공정·설비·LOT·계측·학습 콘텐츠를 코드로 재생성한다. 테스트 DB와 개발 DB를 분리하고 destructive reset은 명시적으로 허용된 체험 환경에만 적용한다.

필수 데이터 묶음: 정상 생산, 불량 포함 생산, 잘못된 상태 전이, 중복 요청, 생산 0, 계측 누락/리셋, 부모 계측 중복 합산 위험, 초기화 직전/직후 요청, 비활성 모듈, 사용자 간 동일 업무번호.

필수 검증 층:
- 함수/규칙: 수량·상태·단위·계산.
- 실제 PostgreSQL: FK/UNIQUE/CHECK, 격리, 동시성, 트랜잭션, migrations.
- API: 세션·CSRF·권한·모듈 설정·세대 검사.
- 브라우저: 앱 홈→학습→업무 실행→결과→다음 단계.
- 운영: 백업/복원, 초기화 실패·중복·따라잡기, 포트 비공개, 리소스.

테스트를 실행하지 못한 경우 미실행과 이유를 기록한다. 화면 시제품이나 문법 검사만으로 실제 동작 검증 완료라고 표시하지 않는다.
