# FS-009 실행 기반 구축·검증 보고

작성일: 2026-09-23. 상태: **완료, 사용자 결과 확인 대기**. 브랜치: `fs-009-runtime-base`.

## [기획 의도 검토]

FS-012의 실행 기반·Docker PostgreSQL 18·첫 Alembic 마이그레이션을 구현했다. FS-011 B안에 따라 최초 리비전은 수기로 작성한 고정 테이블·제약 정의이며 실행 시 schema.json을 읽지 않는다. 메타데이터에서 DDL을 생성하는 도구를 추가하지 않았다. 별도 대조 검사기가 실제 DB 카탈로그를 기준본과 비교한다.

가장 먼저 `.python-version=3.14`, `.nvmrc=24`, backend `requires-python`, root/frontend Node engines, Compose `postgres:18`을 고정했다. 이후 검증은 아래 런타임에서 수행했다.

| 대상 | 실제 환경 |
|---|---|
| 호스트 | macOS arm64, Factory Studio 전용 Colima 프로필 |
| Python | **3.14.7**, uv 설치·backend/.venv |
| Node | **24.21.0**, Homebrew node@24 별도 PATH |
| PostgreSQL 서버 | **18.6**, Docker postgres:18 |
| psql / pg_dump | **18.6 / 18.6**, 모두 컨테이너 내부 |
| Docker Compose | 5.5.1 |
| Colima | factory-studio 프로필, 2 CPU / 4GB 메모리 / 20GB 디스크 |

기존 Python 3.9.6 / Node 26.7.0 검사와 비교해 기존 회귀 44개 통과·정적 오류 0은 동일하다. 호스트 psql 16.15는 서버 검사와 덤프에 사용하지 않았다. 시스템 Node 기본 링크를 바꾸지 않고 검증 PATH에 Node 24를 지정했다.

### DB 대조 결과

기준: schema.json **v0.9.1**, SHA256 **`7e97937e7bd0df6fdae97b309444dbfdac584dd2efae71ad4f0bad7eed2d5e44`**.

| 항목 | 설계 | DB | 판정 |
|---|---:|---:|---|
| core / mes / erp / fems 테이블 | 10 / 21 / 27 / 13 | 동일 | 일치 |
| 전체 업무 테이블 | 71 | 71 | 일치 |
| 컬럼 | 712 | 712 | 일치 |
| FK | 161 | 161 | 일치 |
| PK | 71 | 71 | 일치 |
| UK | 166 | 166 | 일치 |
| CHECK | 163 | 163 | 일치 |
| 일반 인덱스 | 38 | 38 | 일치 |
| 유니크 인덱스 | UK_PARTIAL 6 + UNIQUE_INDEX 2 | 8 | 일치 |
| SERVICE/DB_POLICY | 80 | DB 제약으로 생성하지 않음 | 서비스 후속 구현 |

526개 제약·정책 = 물리 제약/인덱스 446개 + SERVICE/DB_POLICY 80개다. FK 161개는 relations 배열로 별도 집계한다. `public.alembic_version`은 Alembic 이력 관리용이며 업무 테이블 71개에 포함하지 않는다. 기존 public 스키마를 업무 스키마로 세지 않는다.

단순 수량 외에 테이블 집합·컬럼 순서·타입·nullable·default·identity, PK/UK 컬럼, CHECK 식, 인덱스 컬럼/조건/unique 여부, FK 범위·대상·RESTRICT를 대조했다. CHECK/default/predicate는 PostgreSQL이 임시 객체에서 정규화한 결과끼리 비교한다. 업무 데이터는 읽지 않으며 임시 객체와 검증 트랜잭션은 롤백한다. 대조 검사기는 마이그레이션 모듈을 import하지 않는다.

원문 CHECK 163개는 PostgreSQL에서 모두 생성됐다. 식 오류를 고친 사례는 없으며 메타데이터도 수정하지 않았다. CHECK 이름 `c<number>_check`의 번호는 schema.json constraints 배열의 **0-based 인덱스**다. 향후 오류에는 번호·테이블·원문·DB 오류가 함께 나온다.

## [예상 문제점/제약]

- schema.json을 수정하지 말라는 이번 사용자 지시가 FS-011의 migration_revision 기입 문구보다 우선한다. 따라서 `migration_revision=null`을 유지하고 실제 적용은 Alembic `7e97937e7bd0`으로 추적한다.
- 원본 schema·Excel·ERD·UI/prototypes 총 16개 파일을 HEAD 바이트와 대조해 변경 없음을 확인했다(exit 0). Excel·ERD 재생성은 스키마 변경이 없어서 이번 작업에서 실행하지 않았다.
- 다운그레이드는 소유 FK를 먼저 제거한 뒤 소유 테이블과 스키마를 제거한다. CASCADE를 쓰지 않아 외부 객체까지 강제 삭제하지 않는다. 소유 테이블의 데이터는 삭제되므로 검증용 DB 전용이다.
- 기존 ExcelJS/uuid 경로에 npm audit **moderate 2건**이 남아 있다. 제시된 수정은 ExcelJS 주버전을 바꾸므로 적용하지 않았다. 신규 frontend 의존성 audit은 0건이다.
- 개발 중 Prettier를 잘못된 실행 디렉터리에서 호출해 exit 2, Ruff 스타일 검사에서 exit 1이 발생했다. 경로·스타일을 수정한 뒤 최종 검증은 모두 통과했다. npm 설치 시 기존 문서 도구의 deprecated 경고와 macOS 선택 의존성 fsevents 설치 스크립트 경고도 있었다. frontend 빌드에는 영향이 없었다.
- 빈 패키지 디렉터리 상태에서 최초 uv sync를 먼저 실행해 로컬 editable 설치에 fs 패키지가 누락됐다(import 검사 exit 1). 파일 작성 후 `uv sync --project backend --python 3.14 --locked --reinstall-package factory-studio-backend`로 재설치(exit 0)하고 앱 import·업무 라우트 0개를 확인했다(exit 0). CI에도 import 검사를 추가했다.
- 원격 CI는 설정만 작성했으며 GitHub 실행은 하지 않았다. 로컬에서 동일 핵심 명령들을 실행했다.
- 시드 실제 INSERT·SERVICE 정책·인증/세션·멱등·동시성·성능·업무 API/화면·배포 검증은 하지 않았다. DB 제약 생성 성공을 해당 기능의 완료로 보지 않는다.
- Colima와 개발 DB는 실행 상태로 남겨 두었다. 필요하면 `docker compose stop`, `colima stop --profile factory-studio`로 중지할 수 있다. 원격 생성·push·force push·mirror push·Git 커밋은 하지 않았다.

### 실제 실행한 최종 검증

전체 명령 배열·stdout/stderr·exit code는 [FS-009_검증실행.json](FS-009_검증실행.json)에 보존했다. 최종 **21명령 모두 exit 0**이다. 별도 의존성 감사 `npm audit --json`은 moderate 2건으로 **exit 1**이며 [원문](FS-009_의존성감사.json)에 남겼다. FastAPI import 및 업무 라우트 0개 확인도 exit 0이었다.

|---|---:|---|

최초 빈 DB에 `upgrade head` 적용 성공(exit 0)을 확인한 뒤 위 되돌리기/재적용 검증을 실행했다. `docker compose up -d --wait`, Python 설치·의존성 설치, npm ci(root/frontend), uv sync --locked도 exit 0이었다. 새 검사 테스트는 원상태 통과 1건과 CHECK 식·nullable·default·type·FK 삭제 동작·UK 컬럼·부분 인덱스 조건·추가 테이블 변조 감지 8건이다. 각 테스트는 DB 변경을 롤백한다.

정적 검사 결과 `validation-report.json`은 기존 정적 범위를 유지한다. 실제 DB 결과는 [ddl-verification-report.json](../db/ddl-verification-report.json)을 사용한다.

구현 시 참조: [PostgreSQL 공식 Docker 이미지의 18 데이터 경로](https://hub.docker.com/_/postgres), [Alembic 트랜잭션 DDL 안내](https://alembic.sqlalchemy.org/en/latest/tutorial.html). Compose는 PostgreSQL 18의 상위 볼륨 경로 `/var/lib/postgresql`을 사용한다.
