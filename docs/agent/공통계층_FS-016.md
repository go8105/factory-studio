## 구현 결과

- 단일 인증 해석기가 `g_`/`m_` 접두어로 저장소를 먼저 선택하고 `AuthContext`를 만든다. 두 저장소를 차례로 조회하지 않는다.
- 회원 세션은 `core.auth_session`, 게스트 세션은 `core.workspace.guest_session_key`에 SHA256 해시만 저장한다. 원문 토큰은 Secure·HttpOnly·SameSite=Lax 쿠키로만 전달한다.
- 회원 CSRF는 세션별 파생값의 해시를 `auth_session.csrf_token_hash`에 저장한다. 게스트 CSRF는 서버 비밀과 세션 원문의 HMAC 파생값이며 별도 DB 컬럼을 만들지 않는다. 검증 헤더는 모두 `X-CSRF-Token`이다.
- 게스트 종료는 `guest_session_key`를 `revoked_` 접두어의 새 난수 해시로 교체한다. 이전 쿠키와 토큰 종류를 바꿔 보낸 쿠키는 거부한다.
- `guest_pool` advisory lock 안에서 상한 20개를 확인하고 FS-015 `copy_template`을 호출한다. 게스트 생성·복사·감사는 한 트랜잭션이다.
- 세대 초기화는 FS-015 복사기를 기존 공간용으로 확장했다. 새 세대를 `preparing`으로 복사한 뒤 기존 세대를 `retired`, 새 세대를 `active`로 바꾸고 활성 포인터를 함께 갱신한다. 공간 모듈 설정은 유지한다.
- 만료 게스트 정리는 `guest_pool → workspace` advisory lock 순서로 재확인한다. 업무 FK 그래프의 자식부터 삭제하고 감사·job은 공간 스냅샷으로 분리한 뒤 세대와 공간을 삭제한다.
- `request_receipt` 멱등 처리는 생성·로그인·모듈 변경·세대 초기화에 적용했다. 동일 키·동일 본문은 기존 결과, 다른 본문 또는 24시간이 지난 키는 422다.
- 요청 로그에는 메서드·경로·상태·소요 시간만 기록한다. 토큰·쿠키·해시와 요청 본문은 기록하지 않는다.
- 포털 최소 API는 게스트/회원 세션, 현재 세션, 로그아웃, 공간, 모듈 조회·변경, 세대 초기화, 관리자 job/audit 목록이다. 게스트의 관리자 경로는 404다. MES·ERP·FEMS 업무 API는 만들지 않았다.

## FS-010 정정

FS-010 2.1을 “회원과 같은 쿠키 속성·검증 흐름, 저장소는 게스트=`workspace.guest_session_key`, 회원=`auth_session`”으로 고쳤다. 근거는 FS-006b의 계정 없는 GUEST 주체 계약, 게스트 세션 부분 유니크, `guest_actor_key` 기반 감사·멱등 정책이다. schema.json과 Alembic 리비전은 변경하지 않았다.

## 통합 검증

`backend/tests/test_common.py`가 실제 PostgreSQL 18에서 다음을 한 흐름으로 검증한다.

1. 템플릿 7,469행 생성, 게스트 2개 순차 진입, 각 공간에 복사 결과 7,467행 확인
2. 같은 멱등 키의 세션 생성·모듈 변경·세대 초기화 결과 동일, 다른 본문 422
3. 다른 게스트의 모듈·공간이 변하지 않는 범위 격리
4. 게스트 토큰을 회원 형식으로, 회원 토큰을 게스트 형식으로 바꾼 요청 401
5. 회원·게스트 CSRF 누락·불일치 403
6. 게스트 종료 뒤 이전 쿠키 401, 만료 쿠키 410
7. 종료·만료 공간의 업무·세대·공간 정리와 보존 감사 분리
8. 요청 로그·`audit_event`·`request_receipt`에 원문 토큰과 그 SHA256이 없음
9. ADMIN 로그인·세션과 관리자 목록 접근, 게스트 관리자 접근 404
