## 그대로 옮기지 않을 구현과 이유
1. api_server.py에는 API와 DB 쿼리, 외부 업무 처리가 모여 있다. 신규 코드는 core/learning/업무 모듈의 router·service·model로 나눈다. 같은 프로세스 안에서 명시적 서비스 함수를 호출한다.
2. 승인 함수는 SELECT/선택적 INSERT 후 외부 초안 저장을 수행하고 마지막에 commit한다. 기본 psycopg 트랜잭션 방식이라면 외부 호출을 기다리는 동안 트랜잭션이 열린 구조다. 신규 외부 전송은 업무 저장과 outbox 등록을 한 트랜잭션으로 끝낸 뒤 별도 처리한다. MES 첫 버전에 필요하지 않은 외부 전송 엔진까지 선구현하지는 않는다.
3. feedback_sample 저장 예외를 잡은 뒤 같은 연결에서 다음 SQL을 수행한다. DB 오류 종류에 따라 트랜잭션이 실패 상태일 수 있으므로 예외 무시만으로 복구됐다고 간주할 수 없다. 신규 코드는 트랜잭션 범위와 rollback을 명시하고, 독립적으로 실패를 허용해야 하는 작업은 savepoint 또는 분리 경계를 검토한다.
4. 기존 draft ID 확인은 이미 저장된 요청의 반복 방지에는 도움이 되지만 동시 요청 전체의 원자성을 보장하는 설계로 간주하지 않는다. 신규 실적 저장은 DB 제약·잠금/상태 재검증과 idempotency 정책을 함께 검증한다.
5. api_server.py CORS는 개발용 전체 허용이다. 신규 공개 앱은 동일 출처를 기본으로 하고 개발 교차 출처는 명시된 주소만 허용한다. CORS를 인증/권한 대체물로 사용하지 않는다. 기존 서비스의 실제 노출·보안 수준은 이번 부분 검토로 판정하지 않는다.
6. 기존 SQL 파일과 수동 ALTER 절차는 신규 프로젝트의 변경 관리로 채택하지 않는다. Alembic revision으로 재현하고 Excel DB 설계서·실제 카탈로그를 함께 대사한다.
7. chat_history/poll_state의 단일 서비스 상태는 사용자별 학습 기록으로 그대로 재사용할 수 없다. 학습자·과정 버전·실습 세대를 구분하고 보존 정책을 따로 둔다.
8. 현재 상시 APScheduler 프로세스를 신규 플랫폼에 복제하지 않는다. 기획대로 CLI+systemd timer, DB 실행 키·잠금·따라잡기를 구현한다. 예외 기록 후 종료 코드는 작업 실패를 반영해야 한다.

## 문서와 코드 차이
scheduler.py의 텔레그램 작업은 minutes=1이지만 인근 주석과 시작 로그는 30분이라고 설명한다. README 일부도 이전 expense_bot 구성을 설명한다. 실제 서버의 배포 버전은 확인하지 않았으므로 운영 주기를 단정하지 않는다.
신규 프로젝트는 실행 주기를 설정 한 곳에서 관리하고 로그/문서/테스트와 일치 여부를 점검한다. 문서 자체를 현재 런타임의 증거로 대신하지 않는다.

README에는 ALTER TABLE 장시간 대기 사고가 기록되어 있다. 당시의 실제 락·세션 정보는 확인하지 않았으므로 문서의 원인 설명을 검증된 원인으로 확정하지 않는다. 신규 배포는 장기 트랜잭션 점검, lock/statement timeout, 영향 범위에 맞는 정지 또는 호환 가능한 단계적 변경, 복구 방법을 갖춘다. 모든 스키마 변경에 전체 서비스 중단이 필수라고 일반화하지 않는다.
