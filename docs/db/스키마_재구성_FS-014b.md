# FS-014b ERP 회계 A·B층 설계

작성일: 2026-09-22. 기준: FS-013 D7, FS-014 v0.7.0, 사용자 확정 업무 규칙 및 추가 결정.
대상은 메타데이터 v0.8.0이다. migration_revision=null, 물리 DB·제품 코드 미적용.

## 1. 범위와 집계

| 스키마 | FS-014 | FS-014b | 증가 |
|---|---:|---:|---:|
| core | 11 | 11 | 0 |
| mes | 21 | 21 | 0 |
| erp | 16 | 27 | 11 |
| fems | 13 | 13 | 0 |
| 전체 | 61 | 72 | 11 |

FS-013 §5의 72와 일치한다. 아래 11개 외에 전표·총계정원장·분개 이력·세금계산서 명세는 만들지 않는다.
회계 결과는 저장하지 않고 A층 거래와 B층 규칙에서 조회 계산한다.

| 테이블 | 역할 |

| `erp.receivable` | 확정 매출에서 파생하는 채권 원금 |

FS-014 변환 및 테스트의 기준 목록은 기존 61개로 유지한다.

## 2. 공통 키·금액 설계

모든 신설 테이블은 bigint identity id, NOT NULL workspace_id/generation_id, created_at을 갖는다.
PK(id), UK(S,id), (workspace_id,generation_id)→core.data_generation(workspace_id,id).
모든 업무 FK는 S를 포함하고 삭제·갱신 모두 RESTRICT다. 다른 업무 스키마 FK는 없다.
계정·규칙 마스터도 사용자 공간·세대 소유이며 R5 예외를 만들지 않는다.

금액은 기존 매출의 numeric(18,2), 단가는 numeric(18,4), 수량은 numeric(18,3)을 따른다.
금액 보유 테이블에는 currency varchar(3) NOT NULL DEFAULT 'KRW'와 CHECK(currency='KRW')를 둔다.
차변·대변 미리보기의 통화는 원천 거래에서 가져온다. 계정·규칙은 금액을 저장하지 않는다.
일자는 date, 시각은 timestamptz다. 새 연·월 컬럼은 만들지 않는다. 기존 달력 문자열 CHECK는 유지한다.

채권·채무는 원천 거래 ID + partner_id + currency를 복합 FK로 참조한다.
소명도 양쪽 부모에 (S, 부모ID, partner_id, currency)로 참조한다.
따라서 공간·세대·거래처·통화 불일치는 FK로 거부한다. 부모에는 대응 UK를 둔다.
원금과 원천 total_amount의 일치, 원천 확정·취소 상태는 SERVICE 정책으로 검사한다.

## 3. 생성·잔액·상태

- 매출은 기존 TX-09에서 INSERT되는 순간 인식·확정된다. 별도 draft 매출 상태를 추가하지 않는다.
  출하 확정·sales_record·receivable 생성은 한 트랜잭션이다. 원천당 UK로 채권 중복 생성을 막는다.
- 매입은 draft→confirmed 때 헤더·명세 합계를 검증하고 payable을 한 트랜잭션에서 생성한다.
- 수기 채권·채무 등록 경로는 없다. 원금 amount는 원천 total_amount와 일치하는 불변 스냅샷이다.
- 확정 원금·금액·거래처·통화·근거를 수정하지 않는다. 원천 취소도 금액을 0이나 음수로 덮어쓰지 않는다.
- receivable/payable에는 status, balance, 잔액 합계·캐시 컬럼을 두지 않는다.

유효 원천의 잔액 = 원금 amount − COALESCE(SUM(소명.amount),0).
상태: 잔액 0이면 CLOSED, 0<잔액<원금이면 PARTIAL, 잔액=양의 원금이면 OPEN.
기존 매출의 0원 거래를 임의로 금지하지 않는다. 원금 0은 OPEN/CLOSED 조건이 겹치므로 CLOSED를 우선한다.
수금·지급 및 소명액은 양수다. 원금 0에는 양수 소명을 할 수 없다.
원천 취소 거래는 유효 채권·채무 조회에서 제외하고 취소 원천 조회에서 확인한다.
취소 상태를 채권에 저장하거나 OPEN/CLOSED에 섞지 않는다.

## 4. 소명과 동시성 — SERVICE/DB_POLICY

### 4.1 잠금 순서

FS-006a 8단계에서 폐기된 학습 7단계를 다음으로 교체한다.

**7. 채권·채무 → 수금·지급 → 소명**

수금: receivable.id 오름차순 → receipt.id 오름차순 → receipt_apply.id 오름차순.
지급: payable.id 오름차순 → payment.id 오름차순 → payment_apply.id 오름차순.
혼합 경로의 고정 테이블 순서: receivable → payable → receipt → payment → receipt_apply → payment_apply.
각 테이블 내부는 id 오름차순이다. workspace(1)·generation(2) 및 관련 원천 거래(6)를 먼저 잠그고,
자식 잠금 이후 부모를 얻지 않는다. 매입 헤더→명세와 매출→세금계산서도 원천 거래 6단계에서 잠근다.
감사·요청 결과는 8단계다. 현재 공간 쓰기 직렬화 정책을 유지한다.

### 4.2 등록·취소 계약

1. 소명 대상 ID를 확인하고 공간·세대·관련 원천·7단계 부모를 정해진 순서로 잠근다.
2. 잠금 획득 후 새 조회로 합계를 계산한다. READ COMMITTED 실행 시 잠금 대기 전 집계 스냅샷을 재사용하지 않는다.
3. SUM(소명액)≤수금/지급액 **및** SUM(소명액)≤채권/채무 원금을 모두 검사한다.
4. 범위·거래처·통화, 수금/지급 confirmed, 원천 미취소를 다시 확인한다.
5. 등록 또는 물리 DELETE와 감사·멱등 결과 기록을 같은 트랜잭션에서 처리한다. 하나라도 실패하면 전체 롤백한다.

수금·지급 확정은 금액 확정이다. **확정 후에도 소명 추가와 취소는 계속 허용한다.**
소명 UPDATE는 금지하고 변경은 취소 후 새 요청으로 등록한다.
같은 수금↔채권 쌍에 서로 다른 소명 행을 여러 번 넣을 수 있다. 요청 키가 같은 재전송만 차단한다.

소명 취소는 cancelled_at/status를 쓰지 않는 **물리 DELETE**다.
core.audit_event.summary에 S·양쪽 부모 ID·소명 ID·요청 키·금액·통화·사유를 남긴다.
core→ERP FK를 만들지 않으므로 삭제 이력은 독립 스냅샷으로 보존된다.

apply_key의 UK는 존재하는 행의 중복을 막는다. **삭제된 행의 재등록 방지는 UK만으로 불가능**하다.
core.request_receipt로 성공한 요청을 재사용하지 않으며, 소명 취소 이후 옛 등록 요청을 재실행하지 않는다.
멱등 결과 보존 기간과 재시도 허용 기간을 일치시키고 만료 키 재사용을 거부하는 계약이 필요하다.
이 정책의 API 구현·만료 키 검증 방식은 FS-010/011에서 구체화한다. 이번에 새 이력 테이블을 만들지 않는다.

과입금은 금지하지 않는다. 미소명 잔여=수금/지급액−SUM(소명액), 별도 캐시·선수금 계정 없음.
FIFO는 화면 기본 제안값이며 메타데이터 규칙·컬럼으로 구현하지 않는다.

### 4.3 DB 제약과의 구분

CHECK는 현재 행의 양수 금액·KRW·필드 조합만 검사한다. 여러 행 합계나 확정 후 변경 여부는 검사하지 않는다.
PostgreSQL은 다른 행을 참조하는 CHECK의 지속적인 정합성을 지원하지 않는다.
트리거는 별도 구현 방법이지만 이번 작업은 물리 DDL·트리거 구현 범위가 아니다.
위 정책은 **향후 구현할 SERVICE 계약**이며 직접 DB 쓰기는 이 정책으로 보호되지 않는다.

근거: [PostgreSQL CHECK 제약](https://www.postgresql.org/docs/current/ddl-constraints.html#DDL-CONSTRAINTS-CHECK-CONSTRAINTS),
[명시적 행 잠금](https://www.postgresql.org/docs/current/explicit-locking.html#LOCKING-ROWS).

## 5. 취소와 세금계산서

매출은 cancelled_at/cancel_reason을 추가해 취소를 표시한다. 인식된 금액과 채권 원금은 보존한다.
매입 헤더는 draft/confirmed/cancelled, confirmed_at·cancelled_at·cancel_reason을 갖는다.
취소 후 재확정과 음수 역분개는 지원하지 않는다. 매출 인식 취소는 출하 물류 되돌림이 아니다.

| 상위 거래 | 조건 | 처리 |
|---|---|---|
| 매출 | 소명 행 존재 | 취소 거부. 먼저 소명 물리 삭제 |
| 매출 | 소명 없음, tax_invoice 없음 | 취소 허용 |
| 매출 | 소명 없음, 발급대기 | 발급대기 행을 같은 트랜잭션에서 삭제하고 취소 |
| 매출 | 발급완료 | 취소 거부 |
| 매입 | 소명 행 존재 | 취소 거부. 먼저 소명 물리 삭제 |
| 매입 | 소명 없음 | 취소 허용. tax_invoice와 무관 |

세금계산서는 이미 인식된 미취소 sales_record에만 선택적으로 생성한다.
FK+UK로 매출당 최대 1개(0..1)를 보장한다. 없음 상태가 허용되므로 반드시 1개 존재하는 것은 SERVICE 요구가 아니다.
명세·월합계는 없다. 금액·품목 원천은 해당 매출이며 tax_invoice에 금액을 중복 저장하지 않는다.
상태는 pending(발급대기)/issued(발급완료) 두 가지다. issued에는 승인번호·발급일이 필수다.
발급일은 인식 시각의 Asia/Seoul 기준 날짜 이상이어야 한다(SERVICE 검사).
수기 승인번호의 실제 유효성·국세청 연동·세금계산서 법정 적합성은 검증하지 않는다.

## 6. B층 고정 계정·분개 규칙

계정은 AR(외상매출금), PRODUCT_SALES(제품매출), VAT_PAYABLE(부가세예수금), BANK(보통예금),
RAW_MATERIAL(원재료), VAT_RECEIVABLE(부가세대급금), AP(외상매입금)의 **7개**다.
허용 코드·명칭 CHECK와 코드 UK로 범위를 제한한다. 정의는 메타데이터에 두되 seed 행은 생성하지 않는다.

posting_rule 1행은 아래 표시 규칙 1줄이다. UK(S,transaction_kind,line_no),
(S,account_id,account_code) FK와 허용 조합 CHECK로 다음 10개 조합만 허용한다.

| 거래 유형 | 순서 | 차대 | 계정 | 금액 원천 |
|---|---:|---|---|---|
| SALE | 1 | 차 | 외상매출금 | TOTAL |
| SALE | 2 | 대 | 제품매출 | SUPPLY |
| SALE | 3 | 대 | 부가세예수금 | TAX |
| RECEIPT | 1 | 차 | 보통예금 | APPLY |
| RECEIPT | 2 | 대 | 외상매출금 | APPLY |
| PURCHASE | 1 | 차 | 원재료 | SUPPLY |
| PURCHASE | 2 | 차 | 부가세대급금 | TAX |
| PURCHASE | 3 | 대 | 외상매입금 | TOTAL |
| PAYMENT | 1 | 차 | 외상매입금 | APPLY |
| PAYMENT | 2 | 대 | 보통예금 | APPLY |

미리보기 단위: SALE은 미취소 매출 1행, PURCHASE는 confirmed 매입 1행,
**RECEIPT는 receipt_apply 1행, PAYMENT는 payment_apply 1행**이다.
소명 100원은 차·대 각 100원이며, 수금 120원의 미소명 20원 안내는 분개 표 밖에 표시한다.
소명 삭제 시 그 분개 미리보기는 사라진다. 삭제 이력에서 분개를 복원해 저장하지 않는다.
규칙이 빠졌으면 계산 불가로 표시하며 차·대 합계를 대조한다. 결과·전표·총계정원장은 저장하지 않는다.
전체 7계정·10규칙의 존재는 CHECK가 보장하지 않으므로 초기화/조회 SERVICE에서 완비 여부를 검사한다.
일반 사용자에게 계정·규칙 편집 경로를 제공하지 않는다. 조건식·JSON 분기 엔진은 없다.

## 7. 실행 및 검증 계획

`python3 tools/apply_fs014b.py --check`: 쓰기 없이 입력·후보 검증.
`python3 tools/apply_fs014b.py`: v0.7.0/FS-014와 구조 검증 후 원본 SHA256 백업 및 원자적 교체.
유효한 v0.8.0/FS-014b에 재실행하면 파일·mtime·백업·변경이력 불변.
잘못된 버전·부분 적용·검증 오류·DB 적용 메타데이터는 중단한다.

검증 대상: 72개 집계·격리·복합 FK·KRW·원천당 UK·잔액/상태 컬럼 부재·물리 삭제 모델·SERVICE와 CHECK 구분,
오류 입력 원본 보존·멱등·백업·생성 산출물 일치. SERVICE 정책의 실제 동시성 보장은 실행 기반 구축 후 검증한다.

## 8. 미구현·후속

물리 DDL·마이그레이션·PostgreSQL·seed·제품 코드·API·화면은 작성하지 않는다.
결산·재무제표·원가·고정자산·예산·대손·역분개·선수금·외화·구매발주·입고검수·국세청 연동은 제외한다.
세율·반올림은 기존 단일 정책 계약을 따르며 이번 메타데이터로 법정 세무·회계 적합성을 보장하지 않는다.
업무 규칙의 허용 사례·거부 사례는 설계 검증용으로 대조하며 실제 DB·서비스 실행 결과와 구분한다.
