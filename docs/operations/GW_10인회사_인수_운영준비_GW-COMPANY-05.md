# GW 10인 회사 인수·운영 준비 · GW-COMPANY-05

2026-10-18. 사용자 지정 **회사 1개·부서 1개·총10명**을 기준으로 한다. 창업 전 준비용이며 실제 직원 계정·회사를 생성하거나 운영 정책을 확정한 문서가 아니다. [기술 검증 결과](../agent/GW_WMS통합_인수검증_GW-COMPANY-05.md)와 [승인된 회사 계약](../modules/gw/회사인증_권한_통합설계_GW-COMPANY-01.md)을 함께 읽는다.

## 최소 구성

| 항목 | 구성 |
|---|---|
| 회사/부서 | 회사1개, 초기 부서1개(회사 운영팀, 실제 이름은 창업 시 결정) |
| 사용자 | 관리자1명 + 직원9명, 각자 별도 로그인 |
| 초기 관리자 | 대표 또는 운영 담당1명이 회사 OWNER·HR ADMIN·GW 관리 역할을 겸함 |
| GW 명시 역할 | 초기 관리자에게 조직·결재선·전결·공지·보안 관리5개. 일반 직원9명은 관리 역할 없음 |
| 인수 담당 | 초기 관리자가 업무 인수를 겸함. 실명·연락처는 운영 준비 시 비공개 운영 기록에 지정 |
| 보안 사건 조회 | 초기 보안 관리자가 조회. 별도 감사 담당자를 자동 생성하지 않음 |
| 동시 사용 시험 | 최악의 초기 조건으로10개 계정 동시 사용을 시험. 직원 수10명을 운영 최대 용량 보장으로 표현하지 않음 |
| 최소 대표 업무 | 일반 기안→상신→다른 직원 결재→기록/댓글, 회사 공지·일정 참석·참여 채팅 |

회사 OWNER/HR ADMIN/GW 관리 역할은 서로 다른 권한이다. 최소 인원이라 같은 사람이 겸할 수 있어도 직원에게 자동 승격하지 않는다. 기안자가 자기 문서를 승인하지 않도록 최소2명의 업무 참여자가 필요하다. 아이디 `admin`의 총 관리자 계정은 회사의 직원 계정을 대신하지 않는다. 비밀번호·토큰·실제 개인정보는 문서에 적지 않는다.

관리자1명 구성은 그 계정의 정지/분실 시 업무 관리가 멈출 수 있다. 마지막 활성 보안 관리자 제거를 막지만, 총 관리자에 의한 긴급 계정 정지는 가능하다. 자동 승격·대신 로그인·DB 비밀번호 덮어쓰기로 복구하지 않는다. 출시 전 복구 책임자/본인 확인 절차를 정하고 실제 검증해야 한다. 추후 운영 여건이 생기면 기존 직원 중 두 번째 보안 관리자를 명시적으로 정하는 방안을 검토한다(총원 증가 필수 아님).

## 지금 확인된 것과 출시 전 조건

기존 P0 문서의 신규 TEAM 공간 가정은 GW-COMPANY-01의 현재 core.company/COMPANY·HR 직원 읽기 계약으로 대체한다. **MFA·복구·보존·운영 인수 요구는 계속 유효하다.** 문서에 등장한 deployment_mode·추가 인증 어댑터가 현재 제품에 구현됐다는 뜻은 아니다.

따라서 판정은 **통합·합성 기술 검증 완료 / 실제 회사 시범·운영 인수 미완료**다. 개발 검증 수치를 운영 응답시간 약속·RPO/RTO 충족으로 표시하지 않는다. 이 작업은 MFA/SSO 공급자 선택이나 보존 정책을 임의 개발하지 않는다.

## 실제 직원 준비 순서

1. 전용 운영 환경과 위P0 항목을 먼저 인수한다. 공개 합성 체험 환경에 실데이터를 넣지 않는다.
2. 기존 회사 관리 절차로 회사1개·부서1개와 관리자1명/직원9명을 준비한다. 실제 계정은 각자 확인하고 비밀번호는 문서/메신저 공유 기록에 남기지 않는다.
3. OWNER 본인이 GW 최초 설정을 한다. 조직 관리자가 HR 직원9명을 명시적으로 가져와 각각 연결 요청을 만든다. 직원9명은 자기 로그인에서 사번·이름·조직을 확인해 본인 동의한다.
4. 결재선 담당자를 정하고 일반 기안1건을 작성→상신→다른 직원이 결재한다. 비참여 직원은 초안/비공개 문서를 읽을 수 없어야 한다. 원본과 처리 기록을 보존한다.
5. 공지·일정 참석·채팅을 확인한다. 권한 정지 후 재조회/재시도가 원문을 되돌려주지 않는지 확인한다. HR 퇴사 표시만으로 GW 접근이 자동 회수됐다고 가정하지 않는다.
6. 관리자/직원의 실제 기기에서 로그아웃·세션 만료·연결 회수·복귀를 확인하고 담당자가 인수한다.390px 데스크톱 브라우저는 실휴대폰 확인의 대체가 아니다.

## 변경·복구 절차

배포 전 코드 commit·`gw_wms_merge` head·schema0.27.0·백업 실행 ID·설정/키 참조·책임자를 함께 기록한다. 비밀 값은 넣지 않는다. 운영 DB의 현재 head를 먼저 확인하고 백업/복원 리허설을 마친 뒤 신규 migration을 적용한다. 이미 적용한 `w2b1_wms`·`gw_company_identity`를 수정하거나 한쪽만 stamp해 건너뛰지 않는다.

통합 지점은 부모가2개다. `alembic downgrade -1`은 모호하며 운영 복구 명령으로 사용하지 않는다. 특정 부모로 돌아가면 다른 분기의 표를 삭제할 수 있다. 회사 보안 이력이 있으면 기존 GW downgrade가 거부하는 것이 정상이다. 문제가 생기면 원인을 확인한 새 forward fix 또는 검증된 백업 복원 절차를 택한다.

복원은 다음 순서로 폐쇄 환경에서 수행한다.

1. 사용자 접속과 외부 발송·worker를 막고 DB/관련 저장소·키·설정을 같은 복구 기준으로 준비한다.
2. 원장·GW 연결/역할/사건·FK·문서와 파일 지문·최종 순번·migration head를 대조한다.
3. 복원된 기존 인증 세션을 모두 무효화한다. 예전 세션이 다시 살아나 접근하면 안 된다.
4. 백업 이후 별도 보관한 정지·권한 회수 내역을 책임자가 대조하고, 허가된 API/운영 절차로 재적용한다. 본문을 수동 수정하거나 누락된 회수를 추측하지 않는다.
5. 새 로그인2개 이상으로 관리자 업무·직원 접근·회수 계정 거부를 확인한다. 실제 복구 시간과 손실 구간을 기록하고 담당자 확인 전에는 접속을 열지 않는다.

이번 합성 시험은210표 행 지문 일치·이전 세션10개401·회수 재적용 후 직원403·관리자 정상 접근을 확인했다. 첨부/객체 저장소·MFA 공급자·실운영 장애 전환·보존 정책까지 검증한 결과는 아니다.
