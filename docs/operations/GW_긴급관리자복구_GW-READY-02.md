# GW 관리자 긴급 복구 운영 절차

개발 브랜치 구현 기준. 실회사 인수 완료가 아니다. 일반 직원 대신 로그인하거나 GW 역할을 새로 부여하는 도구가 아니다.

## 준비와 범위

현재 활성 회사·세대의 직원 연결과 SECURITY_ADMIN 역할을 가진 본인이 운영 준비 화면에서 미리 발급한 긴급 문서가 필요하다. 본인 비밀번호, 서버 DB·인증 암호화 키 접근도 각각 필요하다. CLI는 실제 OS 유효 UID를 감사 기록에 남기며 독립된 두 사람의 승인을 보장하지 않는다. 업무 원문·인증 비밀은 감사 기록에 넣지 않는다.

긴급 문서 파일은 소유자만 읽고 쓰는 0600, 상위 디렉터리는 본인 소유이며 그룹·전체 쓰기가 없어야 한다. 심볼릭 링크는 거부한다. 비밀을 명령행·메일·Git·스크린샷에 넣지 않는다. 서버의 기존 비밀 주입 방식을 사용한다.

## 승인 파일 발급

대상 회사·계정 ID를 별도로 확인한 후 저장소에서 실행한다. 아래는 실제 비밀이 없는 자리표시자다.

```sh
uv run --project backend python tools/gw_emergency_recovery.py \
  --kit-file /private/recovery/kit.json \
  --output /private/recovery/approval.json \
  --company-id COMPANY_ID --user-id USER_ID \
  --reason '본인 확인 후 인증 수단 분실 복구'
```

PUBLIC_DEMO에서는 실행하지 않는다. 기존 출력 파일을 덮어쓰지 않으며 새 파일은 0600으로 생성한다. 승인 유효기간은 15분, 한 번만 사용할 수 있다. 발급 시점에 회사·계정·직원 연결·현재 보안 역할·보안 버전·문서 해시와 만료를 검사한다. 틀린 문서 비밀은 누적 5회 후 잠긴다. 승인만으로 현재 업무 세션은 회수하지 않는다.

출력 파일을 쓴 뒤 DB commit 결과가 불명확한 경우 파일을 보존한다. 자동 재발급하지 말고 감사 기록과 문서/승인 상태를 확인한다. 출력 파일을 쓰기 전 실패한 빈 파일은 제거한다. 원문은 서버 화면이나 재시도로 다시 조회하지 못한다.

## 본인 사용과 사후 확인

승인 파일은 대상 본인에게 안전한 경로로 전달한다. 본인은 기존 비밀번호 로그인 뒤 분실 복구 메뉴에서 파일을 선택한다. 다른 계정의 로그인 요청과 혼용할 수 없다. 현재 권한을 다시 검사하고 승인·로그인 요청을 한 번만 소비한다. 이후 기존 앱·코드·세션을 모두 회수하고 15분 제한 복구 세션만 발급한다. 새 앱 등록·코드 보관·재로그인을 완료해야 업무에 돌아갈 수 있다.

새 긴급 문서 발급은 이전 문서와 대기 승인을 무효로 한다. 보안 버전이 바뀌거나 365일이 지나도 기존 문서는 무효다. 재등록 후 새 문서를 준비하고 사용한 로컬 승인 파일은 조직의 비밀 폐기 절차로 처리한다. 비밀번호/DB 값을 수동 덮어쓰거나 역할을 승격해 우회하지 않는다.

## 확인 범위

합성 PostgreSQL의 일회성·동시 승인·역할 회수·만료·재등록·제한 업무 차단·CSRF·발급량과 CLI 파일 권한을 검사했다. 파일 선택부터 새 앱 등록까지 실제 브라우저 통합, 서버 운영자 인수·실제 휴대폰·운영 도메인 검증은 후속이다. [사용자 도움말](../../content/help/portal/account-security.md), [진행 기록](../agent/GW_실사용구현_GW-READY-02.md).
