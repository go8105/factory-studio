# GW 직원 연결·역할 변경 기록 · GW-READY-02

2026-10-18 개발 브랜치 구현, 7차 회사 업무 공통 경로/DB 대조에 이어 8차에서 공통 인증·HR 사용자 관리 수집을 확장했다. 전체 회수 기록 수집이나 운영 인수를 완료한 상태는 아니다. 기존 [암호화 백업·격리 복원](GW_암호화백업_격리복원_GW-READY-02.md)의 PARTIAL·접속 제한·ready=false를 유지한다.

## 이번에 기록하는 범위

`company_identity.execute`를 통과한 회사 최초 설정, 직원 연결 요청·본인 수락·취소·정지·재개, 명시 역할 변경을 기록한다. 현재 권한·최근 인증·입력 검사를 통과해 실제 변경한 경우에만 저장한다. 이미 처리한 같은 요청의 재조회는 새 기록을 만들지 않으며, 재조회도 현재 권한 검사를 먼저 통과해야 한다.

추가로 `company.action`을 통과하는 회사 직원·조직·결재선·전결·위임·문서/열람자·게시글·댓글·채팅·일정·운영 기준·보관 검토의 변경 요청도 기록한다. 회사별 SQL 조건으로 직원·연결·역할·열람자 상태와 관련 테이블별 지문을 수집한다. 지문에는 원문 자체를 저장하지 않는다. 업무 요청 전체에 기록을 연결했으므로 보안 역할 편집 이외의 저장도 기록 오류 시 취소된다. 공통 경로 밖의 직접 SQL은 포함하지 않는다. 인증·HR 소유 경로는 아래 8차 수집 표를 따른다.

각 기록에는 작업 종류와 공간·세대, **그 회사·세대**의 직원 ID/활성 상태/조직 ID, 계정 연결 ID/직원 ID/계정 ID/연결 상태, 역할 ID/직원 ID/역할명/활성 상태가 들어간다. 이름·사번·비밀번호·인증 번호·복구 코드·원문·처리 사유는 이 별도 기록에 담지 않는다. 제품의 기존 보안 감사 이력은 유지한다.

암호화 파일은 DB 트랜잭션 확정 **전**에 동기화한다. 파일 저장·기존 기록 검사에 실패하면 `SECURITY_JOURNAL_UNAVAILABLE`(503)을 반환하고 DB 변경과 멱등 영수증을 함께 취소한다. 실패한 연결 회수는 적용되지 않았으므로 현재 연결 상태를 확인하고 운영 담당자가 저장소를 복구한 뒤 재시도한다. 완료 안내를 임의로 만들어서는 안 된다.

반대로 기록 저장 뒤 DB 확정이 실패하면 파일만 남을 수 있다. 이 파일은 **변경 의도**이며 확정 사실·현재 권한·복원 적용 명령이 아니다. 자동으로 권한을 부여하지 않는다. 9차에서는 이 의도로 제한할 대상만 격리 복원에 반영한다. 기록에는 확정 시각이나 성공 사실을 가장한 값도 넣지 않는다. 새 기록은 `gw.company.intent.v2`이며, 암호화 봉투 지문을 같은 DB 트랜잭션의 `core.audit_event`에 `gw.security.journal-confirmation`으로 기록한다. 표를 추가하지 않고 기존 감사 기록을 이용한다.

## 별도 운영 환경에서 설정

실제 서버에는 아직 설치하거나 설정하지 않았다. 다음 두 환경 값을 앱 프로세스에 함께 제공할 때만 자동 기록한다.

| 환경 변수 | 준비할 값 |
|---|---|
| `FS_GW_IDENTITY_JOURNAL_DIR` | 운영 계정 소유의 기존 0700 폴더. DB 백업·키와 다른 폴더이며 이 기록 전용으로 사용 |
| `FS_GW_IDENTITY_JOURNAL_KEY_FILE` | 같은 운영 계정 소유의 별도 0600 일반 파일. 무작위 AES 키 원시 32바이트 |

둘 다 없으면 기존 회사 동작은 유지하지만 기록 수집을 확인한 것으로 인정하지 않는다. 하나만 있으면 설정 오류로 변경을 거부한다. 키 파일이나 다른 파일을 기록 폴더에 넣지 않는다. 공개 체험과 실제 회사 환경의 키·폴더를 공유하지 않는다. 문서에는 실제 경로·키 값을 기록하지 않는다.

다중 프로세스는 같은 로컬 POSIX 파일시스템 폴더의 `flock`을 공유해야 한다. 서버마다 다른 로컬 폴더를 쓰는 다중 호스트 구성과 NFS·객체 저장소의 잠금/내구성은 검증하지 않았다. 하나의 폴더와 키를 임의로 바꾸거나 과거 파일을 편집·삭제하지 않는다. 키 교체·보관 기간별 정리·연속 보관 묶음 교체는 아직 자동화하지 않았다.

## 기록 검사와 최신 지문

파일은 0600, 연속 번호 `0000000001.json`부터 생성한다. AES-256-GCM 인증과 이전 파일 SHA-256 연결을 함께 검사한다. 첫 번호 누락·중간 번호 누락·변조·부분 파일·잘못된 키·알 수 없는 파일이 있으면 다음 기록 저장도 거부한다. 저장 중 실패한 부분 파일은 보존한다. 임의로 지우고 정상으로 간주하지 말고 운영 진단 자료로 취급한다.

연속 파일 검사는 **끝부분 전체 삭제 또는 폴더 전체 과거 되돌림을 독자적으로 판별하지 못한다**. 운영자가 최신 지문을 다른 신뢰 위치에 보관하고 대조해야 한다. 아래 검사는 이 지문을 필수 입력으로 받으며 키·복호화 내용을 출력하지 않는다. 환경 변수와 지문은 먼저 별도 비공개 운영 절차로 제공한다.

```sh
PYTHONPATH=backend/src uv run --project backend python tools/gw_identity_journal.py --expected-head "$GW_JOURNAL_EXPECTED_HEAD"
```

기본 결과는 `records`, `head`, `coverage`와 `completenessConfirmed=false`, `commitsConfirmed=false`다. coverage는 단일 형식이면 해당 형식명, 구/신 형식이 섞이면 `mixed`, 빈 폴더는 `empty`다. 기본 모드의 종료 코드 0은 **제공한 최신 지문과 암호화 체인이 일치함**만 뜻한다. 불일치·누락·설정 오류는 종료 코드 1이다. 최초 빈 체인의 지문은 64자리 0이며, 이미 기록한 환경에 이 값을 사용해 초기화해서는 안 된다. 최신 지문 외부 자동 전달·서명된 외부 확인은 미구현이다.

### DB 반영 대조

서버 운영 담당자가 `DATABASE_URL`로 점검할 원본 또는 격리 DB를 비공개 환경에서 지정한 후 실행한다. 도구는 REPEATABLE READ 읽기 전용 트랜잭션에서 암호화 봉투 지문·공간·세대·작업 종류가 모두 맞는 감사 기록을 찾는다. 개인 원문이나 복호화된 기록을 화면에 출력하지 않는다.

```sh
PYTHONPATH=backend/src uv run --project backend python tools/gw_identity_journal.py --expected-head "$GW_JOURNAL_EXPECTED_HEAD" --check-database
```

- `matchedRecords`: 같은 DB 감사 기록과 일치한 새 기록 수.
- `legacyRecords`: DB 대조 표식을 남기지 않았던 `gw.company_identity.intent.v1` 기록 수. 새 core/HR의 v1 형식과 구분한다. 기존 파일을 v2로 고쳐 쓰지 않는다.
- `unconfirmedRecords`: 전체 기록 중 DB 반영을 확인하지 못한 수. 확정 전·롤백·다른 DB·감사 보존 기한 경과·기록 누락 모두 가능하므로 **실패/회수 완료로 단정하지 않는다**.
- 하나 이상 존재하는 모든 기록이 일치할 때만 `commitsConfirmed=true`, 종료 코드 0이다. 미확인·구형 GW v1·빈 체인은 종료 코드 3이다. DB 연결/설정 오류·체인 오류는 종료 코드 1이다.

`commitsConfirmed=true`는 **지정한 지문의 기록 묶음이 조회한 DB 스냅샷에 반영됐음**만 뜻한다. 현재 권한의 안전성·공통 인증 전체 수집·최신 지문의 외부 신뢰성·원본 서버 물리 식별·복원 완료 증거가 아니다. 과거 지문을 입력한 정상 결과가 이후 기록을 보장하지도 않는다. DB 감사 기록의 임의 변경·운영자 공격을 별도 신뢰 없이 판별하지 못한다. `completenessConfirmed`와 운영 ready는 계속 false다.

한 기록은 암호화 봉투 기준 최대 4MiB, 폴더는 최대 10,000건이다. 저장 때 기존 체인 전체를 재검사하므로 대규모 사용 성능을 보장하지 않는다. 현재 10인 준비 범위의 제한 구현이며 운영량·보존 정책에 맞는 확장은 별도 검증해야 한다.

## 남은 경로와 복원 판정

아래 8차 경로까지 자동 수집한다. 직접 SQL·다른 프로세스·오프라인 시드/복원 재적용·아직 없는 SSO 연결 변경은 대상이 아니다. 전체 DB 변경을 자동 감시하는 구조가 아니며 회사/세대 재설정과 임의 멤버십·총 관리자 역할 변경까지 전수 수집했다고 인정하지 않는다. 백업/대조 파일과 연속 기록 연결·복원 시 제한 적용은 아래 9차를 따른다. 미확인 의도의 최종 판정·안전한 제한 해제·전경로 완전성은 후속이다.

따라서 체인이 정상이더라도 `checkpointCompletenessConfirmed`, 전체 `revocationsReapplied`, `ready`를 true로 올리지 않는다. 기존 복원 도구에는 성공 전환이나 운영 DB 개방 옵션을 추가하지 않았다.

## 확인한 결과

- 암호화 평문 비노출·파일 권한·변조/중간 삭제/최신 지문과 끝 삭제 대조·잘못된 키·부분 파일·20개 동시 쓰기 검사.
- SQLite 실제 트랜잭션에서 저장 실패 시 직원 상태 변경 취소 및 동일 요청 재조회 중복 방지.
- 소유 격리 PostgreSQL18/합성 회사 HTTP에서 최초 설정→직원 연결 요청→본인 수락→연결 정지 기록, 저장소 권한 오류503/DB 상태·버전 보존→같은 키 재시도 성공→중복 기록 없음.
- 실제 회사·외부 저장소·파일시스템 장애/전원 차단·다중 호스트·대규모 사용·새 브라우저 화면 검증은 미실행이다. 화면 구조 변경은 없다.

제품 도움말: **회사 운영 안내 → 운영 준비 → 도움말**의 [운영 안내](../../content/help/gw/operations.md). 전체 진행/검증 기록은 [구현 기록](../agent/GW_실사용구현_GW-READY-02.md)을 따른다.

7차 검증 보강: 회사 공통 경로를 사용한 일반 기안 작성→상신→승인과 회사 범위 ACL 지문, DB 감사 지문 일치/다른 세대 불일치, DB 롤백 후 의도만 남음, 운영 CLI의 일치0/미확인3, 구형/빈 기록의 미확인 처리를 검사한다. 실제 브라우저와 운영 DB에는 적용하지 않았다. 실행 수치와 최종 결과는 구현 기록의 7차를 따른다.

## 8차 공통 인증·HR 사용자 관리

기존 `FS_GW_IDENTITY_JOURNAL_DIR`/`FS_GW_IDENTITY_JOURNAL_KEY_FILE` 설정을 그대로 공통으로 사용한다. 이름은 호환을 위해 유지하며, 새 설정값을 운영 환경에 임의 설치하지 않는다. 하나라도 설정하면 인증·HR 경로에도 적용되므로 기록 저장소 장애는 해당 인증/계정 변경을 막을 수 있다. 둘 다 없으면 기존 동작은 유지되지만 자동 수집을 인정하지 않는다.

| 소유 경로 | 기록할 시점과 상태 |
|---|---|
| core.security.service.audit | MFA 등록 완료·번호 로그인·복구 코드 사용·추가 본인 확인·코드 재발급·다른 세션 종료·긴급 제한 복구 등 기존 보안 감사 처리 뒤 |
| MFA 등록 시작 | 기존 대기 등록 회수/새 대기 등록 뒤. 새 비밀과 QR 주소는 기록하지 않음 |
| 인증 시도·발급 카운터 | 변경된 제한 행의 ID·시간 창·횟수·잠금 상태. 계정 이름·IP·bucket_hash는 기록하지 않음 |
| 정상/제한 복구 로그아웃 | 회원 세션 회수 뒤. 게스트 로그아웃은 대상 밖 |
| 긴급 문서/서버 승인 감사 | 발급/교체·승인/거부 등 시스템 감사 뒤. 실제 운영자 정보는 기존 감사 기록을 따름 |
| HR users의 회사/직원 생성·password/login-id/role/disable | 해당 회사·세대·대상 계정의 HR 활성/역할 상태와 인증 소유 상태. 멱등 재조회는 중복 기록하지 않음 |

인증 소유 스냅샷은 대상 사용자 한 명의 상태/보안 버전·명시 역할·회사 멤버십 상태·인증 요소 상태/버전/사용 step·복구 코드 ID와 사용/회수 여부·세션 ID/상태·중간 인증 요청 ID/상태·기존 SSO 상태를 읽는다. HR은 자기 회사 범위의 계정/직원 ID·업무 역할/활성 상태만 읽고 인증 소유 함수의 결과를 합친다. 이름·아이디 문자열·비밀번호/해시·암호화된 TOTP 비밀·복구 코드/해시·토큰/해시·IP·처리 사유는 이 별도 스냅샷에 넣지 않는다. 새 역할이나 세션을 허용하는 재생 기능은 없다.

새 형식은 `core.security.intent.v1`/`hr.users.intent.v1`이다. 같은 체인에 GW v2와 함께 저장할 수 있다. core의 기존 감사 표에 `action=security.journal.confirmation`, `entity_kind=security_journal`, `entity_key=봉투 SHA256`, `summary.subject=형식·작업·대상 사용자·해당 시 공간/세대`를 같은 트랜잭션으로 남긴다. 카운터 변경처럼 대상 사용자를 직접 기록하지 않는 경우 userId는 null이고 SYSTEM 표식이다. 인증의 사용자 범위는 공통 계정 전체이며 회사의 업무 원문을 읽지 않는다.

기존 점검 CLI의 `--check-database`가 GW v2와 두 새 형식을 함께 대조한다. 모든 비어 있지 않은 기록이 DB에서 일치할 때만 commitsConfirmed=true다. GW v1은 여전히 미확인이며, 형식이 혼합되어도 전체 완전성/운영 ready를 true로 올리지 않는다. 여기서 확인하는 것은 해당 스냅샷 기록의 DB 반영이며 현재 권한 전체나 백업 이후 누락 없음이 아니다.

카운터·발급량 변경도 기록하므로 10,000건/폴더와 매번 전체 체인 검사라는 기존 제한에 더 빨리 도달할 수 있다. 보관 묶음 교체·최신 지문 외부 보관·성능/장애 인수는 아직 남아 있다. 이 파일만으로 새 제한 창의 인증 대상 매핑을 복원할 수 없으며 현재 checkpoint의 전체 대조나 복원 후 모든 세션/미완료 인증 회수를 대체하지 않는다.


## 9차 백업 기준·격리 복원 연결

[백업/복원 절차의 9차](GW_암호화백업_격리복원_GW-READY-02.md)를 따른다. 백업 DB에 반영된 지문 목록을 기준으로 미확인/이후 기록을 묶어 대조하고, 서명·암호화 대조 파일의 제한 대상만 격리 복원 DB에 적용한다. 미확인 의도는 자동 제외/성공 처리하지 않는다. `FS_GW_JOURNAL_EXPECTED_HEAD`를 새 백업·checkpoint·restore 때 독립 위치에서 제공하며, 잘못된 지문/끊긴 기준/설정 변경은 거부한다. core/HR 사용 중지·GW 회사 연결 정지/보존 중지를 적용할 수 있으나 원본을 변경하거나 권한을 부여하지 않는다. 전체 완전성·미확인 최종 판정·외부 최신성/보관·운영 준비는 여전히 미완료다.

## 10차 거래 취소 근거 대조 (2026-10-19)

선택 설정 `FS_GW_JOURNAL_TX_PROOF=true`는 새 암호화 기록에 원본 DB 식별 지문·WAL 타임라인·최상위 거래 ID를 함께 남긴다. 기본값은 `false`이며 과거 기록에 근거를 소급하지 않는다. PostgreSQL 원본 primary에서 사용하며 `pg_control_system()` 조회 권한을 사전 확인해야 한다. 권한 부여나 실서버 설정은 이번 작업에서 수행하지 않았다. 설정 오류·근거 저장 실패는 해당 변경을 취소한다.

`uv run --project backend python tools/gw_identity_journal.py --expected-head <독립_최신지문> --classify-transactions`로 집계만 확인한다. 기존 기록 경로·키 환경 설정도 필요하다. 개별 거래 ID·계정·복호화 내용은 출력하지 않는다. 조회는 읽기 전용 거래이지만 대조 상한을 확보하기 위해 조회 거래 자신의 ID 한 개를 할당한다. 업무 행을 변경하지 않으며 standby에서 수행하는 절차가 아니다.

| 판정 | 의미와 처리 |
|---|---|
| AUDIT_CONFIRMED | 같은 거래의 감사 표식이 일치 |
| ABORT_CONFIRMED | 같은 원본·타임라인의 전체 거래 취소가 DB에서 확인됨. 새 checkpoint의 제한 후보에서만 제외 |
| PENDING | 아직 처리 중. 제한 유지 |
| COMMITTED_WITHOUT_AUDIT | 거래는 확정됐지만 표식 없음. 저장점 취소도 이 상태일 수 있으므로 제한 유지 |
| SOURCE_MISMATCH | 다른 DB 또는 타임라인. 제한 유지 |
| UNKNOWN | 과거 기록·조회 기간 경과·미래 ID 등 근거 부족. 제한 유지 |

[PostgreSQL 18 공식 거래 정보 문서](https://www.postgresql.org/docs/18/functions-info.html)에 따라 최상위 거래 상태만 판정한다. 감사 행이 없다는 사실만으로 취소로 간주하지 않는다. 저장점 취소는 최상위 거래 취소와 구분한다. 오래된 거래 상태가 폐기되면 UNKNOWN으로 남는다.

분류 모드 종료값 0은 비어 있지 않은 기록이 AUDIT_CONFIRMED/ABORT_CONFIRMED로 모두 판정됐다는 뜻이다. 취소 건이 있으면 `commitsConfirmed=false`인 채로 0일 수 있다. 미판정은 3, 오류는 1이다. 기존 `--check-database`의 DB 반영 확인 의미는 유지한다. `allTransactionsSettled`와 전체 누락 없음은 다르며 `completenessConfirmed=false`·복원 PARTIAL·운영 ready=false를 유지한다.

## 11차 미확인 기록 인수 보고 (2026-10-19)

운영자는 기존 점검 명령에 `--review-report <새_비공개_JSON_경로>`를 추가한다. 이 옵션은 `--classify-transactions`를 함께 수행하며 종료값 의미도 동일하다. 부모 폴더는 운영자 소유 0700이어야 하고 새 파일은 0600으로 생성한다. 기존 파일·심볼릭 링크는 덮어쓰지 않는다. 기록 키/파일/지문 또는 DB 조회 실패 시 정상 보고를 인정하지 않는다.

보고에는 지정한 최신 지문·조회 시각·기록별 암호화 봉투 지문·6종 판정·한국어 후속 확인과 운영자 점검 목록만 담는다. 계정 식별자·원본 DB 지문·거래 ID·복호화 스냅샷은 넣지 않는다. 콘솔에는 기존 집계만 출력한다. 이 파일은 서명된 실행 증거나 checkpoint 입력이 아닌 진단 문서다. `releaseAuthorized=false`, `checkpointInput=false`, `completenessConfirmed=false`이며 수동 승인 판정을 입력받지 않는다. 이후 변경이 생기면 최신 지문으로 새 보고를 만든다.

과거 미확인 기록의 인수 기준:

1. 담당자는 조회 지문·시각과 근거의 보관 위치를 운영 기록에 남긴다. 실제 비밀번호·개인정보는 첨부하지 않는다.
2. UNKNOWN·SOURCE_MISMATCH·COMMITTED_WITHOUT_AUDIT는 확인 불가/추가 조사로 기록한다. 검토를 마쳤다는 사실을 DB 반영이나 전체 거래 취소로 바꾸지 않는다. 관련 계정·회사 제한을 유지한다.
3. PENDING은 원본 거래 종료 후 재조회한다. 저장점 취소는 전체 거래 취소로 간주하지 않는다.
4. 원본 감사·복구 이력·누락 경로를 조사한다. 수집 누락을 고치더라도 과거 암호화 기록을 수정하거나 새 근거를 소급 작성하지 않는다.
5. 새 checkpoint·새 격리 복원 결과, 관리자/직원 업무·회수 계정 거부, 외부 사본·복구 조건을 별도로 인수한다. 미확인 해소 근거가 없으면 운영 전환을 완료로 기록하지 않는다.

현재 구현은 조사와 차단 기준을 제공한다. 과거 근거를 되살리거나 운영자 확인만으로 제한을 해제하는 기능은 없다. 전체 회수 경로 완전성·외부 보관·운영 전환 게이트는 후속이다.

## 12차 암호화 기록 묶음 내보내기·독립 지문 대조 (2026-10-19)

원본 체인을 보존하면서 지정 지문까지의 암호화 파일을 새 묶음으로 복사한다. 기존 기록 키 환경 설정을 사용하며 키를 묶음에 넣지 않는다. 원본 기록 폴더와 별도인 운영자 소유 0700 부모 폴더를 미리 준비한다. 실환경 경로나 역할 권한을 이번 작업에서 변경하지 않았다.

```sh
PYTHONPATH=backend/src uv run --project backend python tools/gw_journal_bundle.py export --expected-head <독립_최신지문> --bundle <새_비공개_묶음폴더>
PYTHONPATH=backend/src uv run --project backend python tools/gw_journal_bundle.py verify --expected-head <독립_최신지문> --bundle <복사받은_묶음폴더>
```

1. 원본과 독립된 운영 기록에서 최신 지문을 확보한다. 묶음 안의 명세나 내보내기 콘솔만 읽어 독립 지문을 대신하지 않는다. 원본이 그 사이 진행됐으면 새 최신 지문으로 재시도한다.
2. export는 원본 잠금 안에서 체인 인증·지문 확인 후 파일을 복사하고 복사본을 다시 인증한다. 복사 중에는 해당 기록 작성이 대기하므로 작업 시간·용량을 확보한다. 각 파일과 폴더를 동기화한 뒤 manifest.json을 마지막에 기록한다.
3. 새 묶음에는 암호화 records/와 건수/지문 명세만 있다. 파일은 0600, 새 폴더는 0700이다. 기존 경로·심볼릭 링크를 덮어쓰지 않는다. 실패한 폴더는 조사용으로 남고 재사용하지 않는다. 새 이름으로 재시도한다.
4. 복사받은 환경에서 별도 키와 독립 지문으로 verify를 수행한다. DB 연결이나 원본 폴더는 필요 없다. 빠진 파일·변조·다른 키·명세 불일치·미완료 묶음은 거부한다. 원본에서 기록이 늘어난 뒤에도 과거 지문으로 과거 묶음을 확인할 수 있지만, 최신 지문으로는 거부한다.
5. 성공 종료 0은 그 위치에서 지정 기록을 인증했다는 뜻이다. 오류는 1이다. `bundleVerified=true`여도 `sourceRotated=false`, `externalDurabilityConfirmed=false`, `releaseAuthorized=false`·전체 완전성false다. 실제 독립 저장 장치/서비스의 장애 내구성은 별도로 검증한다.

12차 시점에는 별도 보관 위치에 쓸 수 있는 복사·검증 도구까지 구현했다. 기록 폴더 교체의 최신 절차는 아래 13차가 우선한다. 네트워크 전송·독립 지문 자동 전달·외부 저장 서비스 설정·자동 예약은 설치하지 않았다. **원본 삭제/초기화·10,000건 한도 리셋·새 체인 교체는 수행하지 않는다.** 기존 백업의 앞부분 연속성 조건을 깨뜨리지 않기 위해 묶음 교체와 다중 묶음 백업/복원 연결은 후속으로 남긴다. 같은 디스크의 별도 폴더를 외부 장애 복구 사본으로 인정하지 않는다. 보관 기간이 지났다는 이유만으로 원본을 비우지 않는다.

## 13차 기존 백업 연결을 유지하는 기록 폴더 교체 (2026-10-19)

12차의 사본 생성에 더해 `rollover`는 기존 기록을 새 폴더의 `.history/`에 보존하고 `.history.json`으로 끝 지문/건수를 연결한다. 새 기록은 새 폴더 최상위에 기존 번호 다음부터 작성한다. 암호화 원본 바이트·번호·이전 지문을 바꾸지 않으므로 과거 백업의 기준 지문/확인 목록과 연결된다. 기존 평면 폴더도 계속 읽고 쓴다. 새 형식은 이번 버전의 서버·도구가 필요하다.

```sh
PYTHONPATH=backend/src uv run --project backend python tools/gw_journal_bundle.py rollover --expected-head <독립_최신지문> --bundle <새_기록폴더>
PYTHONPATH=backend/src uv run --project backend python tools/gw_journal_bundle.py check-switch --expected-head <동일_지문> --bundle <새_기록폴더>
```

운영 담당자의 전환 순서:

1. 별도 검증 환경에서 새 서버/도구 버전과 이전 백업의 격리 복원을 먼저 확인한다. 새 형식은 이전 버전에서 읽을 수 없으므로 구버전 프로세스를 섞지 않는다.
2. 실제 전환 때 인증·직원관리·GW 변경 기록을 쓰는 **모든 앱/worker/운영 도구를 중지**한다. 기록 환경 설정을 끄거나 원본 폴더를 비우는 방법은 사용하지 않는다.
3. 독립 최신 지문을 확보하고 rollover로 새 비공개 폴더를 만든다. 원본은 그대로 둔다. 실패한 새 폴더는 재사용하지 않고 조사 후 새 이름으로 재시도한다.
4. 작성 경로를 멈춘 상태에서 check-switch로 원본과 새 폴더를 같은 독립 지문으로 재검증한다. 원본이 진행됐으면 실패한다. 새 지문으로 새 폴더를 다시 만들어야 한다. 이 명령은 설정 변경/프로세스 중지를 대신하지 않는다.
5. 모든 작성 경로의 `FS_GW_IDENTITY_JOURNAL_DIR`를 새 폴더로 함께 변경하고 동일한 기록 키를 유지한 뒤 새 버전으로 재시작한다. 이번 개발 작업에서는 실제 환경 설정이나 프로세스를 변경하지 않았다.
6. 새 기록의 지문/DB 반영과 새 checkpoint·접속 제한 격리 복원을 확인한다. 새 폴더에서 기록을 시작했다면 과거 원본을 다시 활성화하지 않는다. 서로 갈라진 체인을 임의 병합하지 말고 운영을 멈춰 조사한다.

rollover/check-switch 성공은 `successorPrepared=true`, 실제 설정 변경은 하지 않아 `sourceRotated=false`다. check-switch는 `switchCheckOnly=true`다. 운영 재개/외부 내구성/전체 완전성은 계속 인정하지 않는다. 새 폴더는 일반 `gw_identity_journal.py --expected-head ...`로 점검할 수 있다. 교체 후 사본 export/verify도 보존 영역과 활성 기록을 함께 인증한다.

한도는 **활성 기록 10,000건, 보존+활성 전체 100,000건**이다. 교체하면 활성 기록 건수만 다시 확보하며 전체 기록은 버리지 않는다. 전체 한도에서는 append와 추가 rollover를 거부한다. 무제한 보관/자동 삭제를 제공하지 않는다. 매 변경마다 전체 체인을 확인하므로 이 한도는 성능 인수 수치가 아니다. 교체·export는 전체 사본 용량과 잠금 시간을 요구한다. 장기 보관 성능과 외부 저장소 인수는 남아 있다.

`.history/`·명세 누락/변조·중간 번호 누락·다른 키/지문·복사 중 실패는 기록 작성과 대조를 차단한다. 새 폴더의 보존 영역은 복원에 필요한 원본 일부이므로 별도 보관 사본처럼 삭제하지 않는다. 이 도구는 원본 삭제, 실서버 자동 전환, 지문 자동 전달 또는 외부 네트워크 전송을 수행하지 않는다.

## 14차 전달 확인 기록과 자동 지문 입력 (2026-10-19)

원본 기록, 사본 폴더, 전달 확인 폴더를 서로 겹치지 않는 운영자 소유0700 경로로 준비한다. 기록 암호화 키와 다른32바이트 전달 확인 키를 별도0600 파일로 관리한다. 키 값은 명령 인자/문서/로그에 넣지 않는다. 실제 외부 저장 위치와 자격 증명을 이번 작업에서 설정하지 않았다.

| 환경 설정 | 용도 |
|---|---|
| FS_GW_JOURNAL_WITNESS_DIR | 전달 확인 기록 전용 폴더 |
| FS_GW_JOURNAL_WITNESS_KEY_FILE | 별도32바이트 인증MAC 키 파일 |
| FS_GW_JOURNAL_WITNESS_MAX_AGE_SECONDS | 확인 기록 허용 나이. 기본1800, 1~86400초 |
| FS_GW_JOURNAL_WITNESS_MIN_SEQUENCE | 독립 운영 기록에서 요구하는 최소 전달 순번. 기본1 |
| FS_GW_JOURNAL_BUNDLE_ROOT | 실행 템플릿의 사본 폴더 |

첫 전달은 독립 위치에서 확보한 지문을 지정한다. 이후 `--advance`는 기존 확인 기록이 있을 때만 원본을 읽고 그 접두 기록에서 이어지는지 검사한다.

```sh
PYTHONPATH=backend/src uv run --project backend python tools/gw_journal_delivery.py publish --expected-head <독립_최신지문> --bundles <사본_폴더>
PYTHONPATH=backend/src uv run --project backend python tools/gw_journal_delivery.py publish --advance --bundles <사본_폴더>
PYTHONPATH=backend/src uv run --project backend python tools/gw_journal_delivery.py check
```

publish는 새 사본을 생성하고 전체 인증을 다시 수행한 뒤에만 확인 기록을 남긴다. 확인 기록은 순번·이전 확인 지문·기록 끝 지문/건수·검증 시각과 별도 키의 HMAC으로 연결한다. DB/계정/복호화 원문은 넣지 않는다. 첫 전달의 지문을 원본에서 임의 추정해 자동 초기화하지 않는다. 원본이 복사 도중 진행하면 실패할 수 있으므로 최신 상태로 재실행한다.

백업/checkpoint/restore는 두 WITNESS 경로 설정이 있으면 인증된 최신 확인 기록을 자동으로 읽어 지문 입력에 사용한다. 수동 FS_GW_JOURNAL_EXPECTED_HEAD도 있으면 반드시 같아야 한다. 기록이 오래됨/미래 시각/인증 실패/최소 순번 미달/원본 진행으로 지문 불일치 시 거부한다. 두 설정이 모두 없으면 기존 수동 지문 방식, 일부만 있으면 오류다. 기록 작성 경로 자체는 이 전달 설정을 소비하지 않으며 전달 실패를 회사 업무의 성공 증거로 사용하지 않는다.

`tools/run_gw_journal_delivery.sh`는 bootstrap 이후 반복 전달용 템플릿이다. 이번에는 예약 실행을 설치하지 않았다. 전달을 백업보다 먼저 수행해야 하며, 원본이 이후 진행되면 다시 전달해야 한다. 확인 기록은 최대10,000개이며 자동 삭제/교체하지 않는다. 실패한 사본은 조사용으로 남을 수 있다. 확인 파일이 생기기 전 실패했다면 새 사본 부모 폴더를 준비해 재시도하고, 부분 확인 파일이 남았다면 운영을 멈춰 원인을 조사한다. 오래된 확인 기록을 정상인 것처럼 덮어쓰지 않는다.

외부 보관 인수는 별도다. 경로가 다른 것만으로 다른 장치/장애 영역임을 증명하지 않는다. 실제 마운트·접근 권한·네트워크/장치 단절·외부 사본으로 복구·키 분리 보관을 운영자가 검증해야 한다. `externalDurabilityConfirmed=false`, `releaseAuthorized=false`, 복원PARTIAL/ready=false를 유지한다. HMAC은 키 보유자의 재작성이나 저장소 전체의 과거 복귀를 자체 방지하지 않는다. 독립적으로 보관한 최소 순번을 갱신하고 실제 저장소의 변경 방지 정책을 인수해야 한다. 허용 시간 안의 전체 저장소 복귀를 최소 순번 없이 완전히 탐지한다고 주장하지 않는다. 이번 검증은 합성 로컬 폴더 전달/실제 PG 백업 연결이며 실제 외부 서비스의 장애 내구성 검증은 아니다.
