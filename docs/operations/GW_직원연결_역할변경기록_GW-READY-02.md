# GW 직원 연결·역할 변경 기록 · GW-READY-02

2026-10-18 개발 브랜치 구현. 전체 회수 기록 수집이나 운영 인수를 완료한 상태는 아니다. 기존 [암호화 백업·격리 복원](GW_암호화백업_격리복원_GW-READY-02.md)의 PARTIAL·접속 제한·ready=false를 유지한다.

## 이번에 기록하는 범위

`company_identity.execute`를 통과한 회사 최초 설정, 직원 연결 요청·본인 수락·취소·정지·재개, 명시 역할 변경을 기록한다. 현재 권한·최근 인증·입력 검사를 통과해 실제 변경한 경우에만 저장한다. 이미 처리한 같은 요청의 재조회는 새 기록을 만들지 않으며, 재조회도 현재 권한 검사를 먼저 통과해야 한다.

각 기록에는 작업 종류와 공간·세대, **그 회사·세대**의 직원 ID/활성 상태/조직 ID, 계정 연결 ID/직원 ID/계정 ID/연결 상태, 역할 ID/직원 ID/역할명/활성 상태가 들어간다. 이름·사번·비밀번호·인증 번호·복구 코드·원문·처리 사유는 이 별도 기록에 담지 않는다. 제품의 기존 보안 감사 이력은 유지한다.

암호화 파일은 DB 트랜잭션 확정 **전**에 동기화한다. 파일 저장·기존 기록 검사에 실패하면 `SECURITY_JOURNAL_UNAVAILABLE`(503)을 반환하고 DB 변경과 멱등 영수증을 함께 취소한다. 실패한 연결 회수는 적용되지 않았으므로 현재 연결 상태를 확인하고 운영 담당자가 저장소를 복구한 뒤 재시도한다. 완료 안내를 임의로 만들어서는 안 된다.

반대로 기록 저장 뒤 DB 확정이 실패하면 파일만 남을 수 있다. 이 파일은 **변경 의도**이며 확정 사실·현재 권한·복원 적용 명령이 아니다. 자동으로 권한을 부여하거나 복원에 재생하지 않는다. 기록에는 확정 시각이나 성공 사실을 가장한 값도 넣지 않는다.

## 별도 운영 환경에서 설정

실제 서버에는 아직 설치하거나 설정하지 않았다. 다음 두 환경 값을 앱 프로세스에 함께 제공할 때만 자동 기록한다.

| 환경 변수 | 준비할 값 |
|---|---|
| `FS_GW_IDENTITY_JOURNAL_DIR` | 운영 계정 소유의 기존 0700 폴더. DB 백업·키와 다른 폴더이며 이 기록 전용으로 사용 |
| `FS_GW_IDENTITY_JOURNAL_KEY_FILE` | 같은 운영 계정 소유의 별도 0600 일반 파일. 무작위 AES 키 원시 32바이트 |

둘 다 없으면 기존 회사 동작은 유지하지만 기록 수집을 확인한 것으로 인정하지 않는다. 하나만 있으면 설정 오류로 변경을 거부한다. 키 파일이나 다른 파일을 기록 폴더에 넣지 않는다. 공개 체험과 실제 회사 환경의 키·폴더를 공유하지 않는다. 문서에는 실제 경로·키 값을 기록하지 않는다.

다중 프로세스는 같은 로컬 POSIX 파일시스템 폴더의 `flock`을 공유해야 한다. 서버마다 다른 로컬 폴더를 쓰는 다중 호스트 구성과 NFS·객체 저장소의 잠금/내구성은 검증하지 않았다. 하나의 폴더와 키를 임의로 바꾸거나 과거 파일을 편집·삭제하지 않는다. 키 교체·보관 기간별 정리·연속 보관 묶음 교체는 아직 자동화하지 않았다.

## 기록 검사와 최신 지문

파일은 0600, 연속 번호 `0000000001.json`부터 생성한다. AES-256-GCM 인증과 이전 파일 SHA-256 연결을 함께 검사한다. 첫 번호 누락·중간 번호 누락·변조·부분 파일·잘못된 키·알 수 없는 파일이 있으면 다음 기록 저장도 거부한다. 저장 중 실패한 부분 파일은 보존한다. 임의로 지우고 정상으로 간주하지 말고 운영 진단 자료로 취급한다.

연속 파일 검사는 **끝부분 전체 삭제 또는 폴더 전체 과거 되돌림을 독자적으로 판별하지 못한다**. 운영자가 최신 지문을 다른 신뢰 위치에 보관하고 대조해야 한다. 아래 검사는 이 지문을 필수 입력으로 받으며 키·복호화 내용을 출력하지 않는다. 환경 변수와 지문은 먼저 별도 비공개 운영 절차로 제공한다.

```sh
PYTHONPATH=backend/src uv run --project backend python tools/gw_identity_journal.py --expected-head "$GW_JOURNAL_EXPECTED_HEAD"
```

결과는 `records`, `head`, `coverage=gw.company_identity.intent.v1`와 `completenessConfirmed=false`, `commitsConfirmed=false`다. 종료 코드 0은 **제공한 최신 지문과 암호화 체인이 일치함**만 뜻한다. 불일치·누락·설정 오류는 종료 코드 1이다. 최초 빈 체인의 지문은 64자리 0이며, 이미 기록한 환경에 이 값을 사용해 초기화해서는 안 된다. 최신 지문 외부 자동 전달·서명된 외부 확인은 미구현이다.

한 기록은 암호화 봉투 기준 최대 4MiB, 폴더는 최대 10,000건이다. 저장 때 기존 체인 전체를 재검사하므로 대규모 사용 성능을 보장하지 않는다. 현재 10인 준비 범위의 제한 구현이며 운영량·보존 정책에 맞는 확장은 별도 검증해야 한다.

## 남은 경로와 복원 판정

현재 자동 기록 범위 밖: 공통 인증의 계정 정지·비밀번호·MFA·복구 코드·SSO·멤버십, HR 사용자 관리, GW의 별도 직원 표시/활성 변경·문서 열람자·조직·전결·위임·채팅/일정 ACL·보존 중지 등. 직접 SQL·다른 프로세스 변경도 수집하지 않는다. 변경 전 범위 추적·DB 확정 확인·백업/대조 파일과 연속 기록 연결·복원 시 제한 전용 재적용은 후속이다.

따라서 체인이 정상이더라도 `checkpointCompletenessConfirmed`, 전체 `revocationsReapplied`, `ready`를 true로 올리지 않는다. 기존 복원 도구에는 성공 전환이나 운영 DB 개방 옵션을 추가하지 않았다.

## 확인한 결과

- 암호화 평문 비노출·파일 권한·변조/중간 삭제/최신 지문과 끝 삭제 대조·잘못된 키·부분 파일·20개 동시 쓰기 검사.
- SQLite 실제 트랜잭션에서 저장 실패 시 직원 상태 변경 취소 및 동일 요청 재조회 중복 방지.
- 소유 격리 PostgreSQL18/합성 회사 HTTP에서 최초 설정→직원 연결 요청→본인 수락→연결 정지 기록, 저장소 권한 오류503/DB 상태·버전 보존→같은 키 재시도 성공→중복 기록 없음.
- 실제 회사·외부 저장소·파일시스템 장애/전원 차단·다중 호스트·대규모 사용·새 브라우저 화면 검증은 미실행이다. 화면 구조 변경은 없다.
