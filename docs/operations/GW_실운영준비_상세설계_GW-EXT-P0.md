# GW-EXT-P0 — 실운영 준비 상세 설계 r1

2026-10-18 최신 인수 상태: [GW-COMPANY-05 10인 운영 준비](GW_10인회사_인수_운영준비_GW-COMPANY-05.md). 회사1/부서1/총10명 최소 구성으로 통합·합성 복원/부하 검증을 마쳤다. 아래 신규 TEAM 가정은 GW-COMPANY-01의 현재 core.company/COMPANY 계약이 우선한다. MFA·복구·보존/RPO·RTO·실회사 인수는 계속 미완료다.

2026-10-05 · **설계 확인 대상 / 미구현 / 운영 적합성 미검증**.
범위 결정: [GW-EXT-01](../plan/GW확장_협업플랫폼_결정초안_GW-EXT-01.md). 사용자 “상세 설계 진행해줘”로 확장 방향·순서 승인, 실제 도입 목표 확정. 이번은 P0+A 설계 묶음이며 B~F 상세 설계까지 완료한 것이 아니다. FS-030c 구현은 별도 잔여 작업이다.

## 1. 환경과 출시 단계

| 환경 | 데이터/접근 | 허용 기능 |
|---|---|---|
| PUBLIC_DEMO | 합성 데이터, 기존 개인/게스트 | 기존 체험만. TEAM 생성·외부 발송·실회사 데이터 반입 금지 |
| TEAM_TEST | 합성 데이터, 등록한 테스트 계정 | 공유 권한/API/경합/복구 시험. mock 인증/알림 사용 시 UI·감사에 표시 |
| COMPANY | 별도 DB·저장소·키·도메인, 승인된 회사 계정 | 출시 게이트를 통과한 모듈만. 게스트·공개 가입·역할 체험·시드/초기화 API 차단 |

서버 설정 `deployment_mode`를 환경마다 고정하고 클라이언트/DB 행으로 모드를 승격할 수 없게 한다. workspace_kind의 MEMBER/GUEST 이름은 호환성을 위해 유지하고 TEAM만 추가한다. PERSONAL은 기획 명칭이며 새 enum으로 만들지 않는다. COMPANY의 계정 기본 공간은 준비용 MEMBER가 될 수 있으나 업무 모듈은 모두 꺼져 있고 시드 복사를 하지 않는다. 업무는 TEAM에서만 실행한다.

PUBLIC_DEMO 자격 증명으로 COMPANY에 로그인할 수 없도록 인증 설정·계정 저장소를 분리한다. 회사별 SaaS 다중 테넌트 운영은 초기 출시 대상이 아니며, 첫 배포는 한 회사 전용 환경이다. TEAM_TEST도 공개 데모의 서버/DB와 분리한다.

| OP-02 | 월 기안/게시 건수·문서 크기·파일 증가 GB | 업무/IT | 보존 기간을 포함한 저장량 산정 |

응답시간 SLO, 백업 주기/보관 개수, 사용자·파일 한도는 OP 값을 받아 배포 설정에 기록한다. 개발용 부하 수치를 운영 용량이라고 광고하지 않는다.

## 3. 인증·계정 복구 계약

현재 비밀번호 인증을 계속 이용할 수 있도록 분리된 추가 인증 인터페이스를 설계한다. COMPANY에서는 운영 관리자 및 초대·권한 변경·직원 바인딩·공간 생성·소유자 이전에 **MFA와 5분 이내 추가 인증**을 요구한다(5분은 제안 기본값). 일반 승인에도 회사 정책으로 추가 인증을 요구할 수 있게 action별 정책 키를 둔다.

`verify_assurance(session, action, now)`는 verifiedSubject, assuranceLevel, verifiedAt, expiresAt, provider를 반환한다. 브라우저가 보낸 amr/인증시각을 신뢰하지 않고 검증한 서버 결과만 사용한다. MFA 공급자/SSO 프로토콜 선택과 등록·복구 UI 상세는 OP-04 확정 후 인증 부속 설계에 추가한다. 미구현 어댑터는 COMPANY에서 실패로 처리하고 플래그로 건너뛰지 않는다. 이 부속 설계/실제 검증 전 실운영 인증이 완성됐다고 표시하지 않는다.

TEAM_TEST의 모의 assurance는 서버 배포 모드가 TEST일 때만 허용하며 감사에 MOCK 기록. 계정 복구는 기존 인증 수단 확인 또는 회사가 승인한 복구 절차를 필요로 한다. 운영자가 DB 비밀번호를 임의 변경해 본인으로 가장하는 우회 절차를 제공하지 않는다. 복구 성공 시 모든 기존 세션/추가 인증 무효화·감사·사용자 통보를 요구한다.

공간 관리자는 전사 계정 정지 권한을 자동으로 갖지 않는다. 팀 정지/탈퇴와 계정 전체 정지는 별개다. 회사 계정 정지 연동은 인증/프로비저닝 운영자의 책임이며 통합 시험에서 검증한다.

## 4. 보존·감사·데이터 반입

| 분류 | 필수 최소값 | 정책 |
|---|---|---|
| 인증 | subject, 세션 해시, 인증 수준 | 평문 token·비밀번호·초대 비밀 로깅 금지 |
| 직원 | 사번 코드·표시명·조직·활성·인증 바인딩 | 주민번호/급여/건강정보 A에 없음 |
| 기안/게시 | 본문·결재선·사건·ACL | 관리자 역할이 본문 열람 권한을 자동 부여하지 않음 |
| 감사 | 실제 주체·대상 코드·행위·이전/이후 상태·시각·correlationId | 본문/초대 token 중복 저장 금지, 추가 전용 API |
| 첨부(B) | 비공개 객체 키·크기/hash·검사 상태 | 보존 대상 원문과 함께 복구, 검사 전 열람 금지 |

반입 전 합성 샘플로 필드/권한/오류를 검증하고 회사가 승인한 데이터만 전용 운영 환경으로 넣는다. 실제 데이터/백업을 Git·테스트 fixture·공개 demo에 넣지 않는다. 법정 기간/법적 전자서명 효력은 본 문서에서 정하지 않으며 담당자 확인 항목으로 둔다.

퇴사 후 활성 바인딩/멤버십을 회수하고 과거 사건은 당시 subject와 표시명 스냅샷으로 보존한다. 삭제 요청과 증빙 보존이 충돌하면 자동 삭제하지 않고 회사의 승인된 정책을 적용한다. 정책이 미정이면 출시 차단이며 무기한 보관을 기본 정책으로 확정하지 않는다.

## 5. 백업·복구 실행 설계

1. 백업 실행 ID, 코드 commit, migration head, DB 복원 기준점, 파일 manifest/객체 버전, 암호화 키 참조·설정 버전을 하나의 복구 manifest로 기록한다. 비밀 값은 넣지 않는다.
2. DB 백업/로그와 파일 버전 수명은 RPO와 문서 참조 일관성을 만족하도록 운영 환경에서 확정한다. 동일 시각 폴더 복사만으로 일관 백업이라고 부르지 않는다.
3. 복구 시험은 별도 네트워크/DB/객체 저장소에 수행하고 **메일/알림/서명 worker는 정지**한다. 운영 callback 주소로 발송하지 않는다.
4. 스키마/head 확인→복구된 GW 행·FK·최종 사건/순번·권한·첨부 hash 대조→2계정 업무 흐름→복구 소요 시간/손실 범위 기록. 누락 파일은 발견 건수와 영향 문서를 표시한다.
5. 운영 전환 전에 세션·초대·추가 인증·진행 job lease를 무효화한다. 복원으로 되살아난 권한 회수는 독립 보관한 변경 이력과 대조하여 재적용한다. 확인될 때까지 사용자 접속을 열지 않는다.
6. 중복 발송 방지를 위해 외부 공급자 결과/발송 receipt를 대사한 후 worker를 연다. 성공 여부 불명인 요청을 자동 성공/자동 재발송으로 단정하지 않는다.

인수 결과: restoreRunId, 시작/종료, 목표/실측 RPO·RTO, 대조 건수/실패, 재적용 회수 목록, 시험자·확인자. 백업 성공 로그만으로 통과하지 않는다.

## 6. 출시·장애·관측

배포 manifest: commit·설계 revision·migration head·기능 모드·인수 보고·복구 보고·운영 담당. TEAM 기능이 비활성일 때 기존 개인/게스트 회귀가 유지되어야 한다. 새 migration은 과거 적용본 수정 없이 추가한다. 데이터가 쓰인 새 스키마는 자동 downgrade하지 않고 원인에 맞춘 forward fix 또는 검증된 복원 계획을 선택한다.

관측: 성공/실패 요청 수·응답시간·DB 잠금 대기·401/403/권한 변경·큐 길이/실패·백업 나이·저장소 여유. 지표 라벨에 문서 제목/이름/본문을 넣지 않는다. 경고 임계값은 OP-01~07과 시험으로 확정한다.

장애 절차: 탐지→영향 범위 확인→위험 명령/발송 중지→증거 보존→복구/재처리→사용자 검증→재개·사후 기록. 결재 처리 결과가 불명일 때 재로그인/현재 서버 상태 조회 후 동일 멱등키 재시도, 수동 DB 행 수정은 일반 복구 수단으로 제공하지 않는다.
