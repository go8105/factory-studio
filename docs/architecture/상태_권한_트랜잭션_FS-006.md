## 1. 상태 코드와 전이
상태는 소문자 코드+한글 표시명으로 관리한다. 배포 코드의 허용 목록과 DB CHECK를 일치시키며 관리자 화면에서 상태를 임의 추가하지 않는다. 일반 분류/불량사유의 확장과 업무 상태 전이를 구분한다.

### 작업지시
| 현재 | 동작 | 다음 | 허용 조건·같이 기록할 결과 |
|---|---|---|---|
| 없음 | 등록 | draft | 활성 품목, 양의 수량·단위, 유효한 경로 선택 |
| draft | 수정 | draft | 본인 공간, 아직 미발행 |
| draft | 취소 | cancelled | 사유와 변경 이력 보존 |
| draft | 발행 | released | 게시된 경로·품목 일치, 적용 경로 버전·계획·단위 고정 |
| released | 첫 공정 시작 | in_progress | LOT 존재, 첫 단계·허용 설비 유효, 시작시각 |
| in_progress | 마지막 공정 완료 | completed | 모든 선행 결과 정합, LOT 완료와 같은 트랜잭션 |

cancelled/completed는 종결 상태다. released 이후 취소·직접 계획 수정·상태 되돌리기는 첫 버전에서 지원하지 않는다. 발행 후 LOT 생성 전도 미종결 업무로 본다.

### LOT·공정
| 대상 | 전이 | 조건 |
|---|---|---|
| LOT | 없음→ready | released 지시에 1개만 생성, 같은 S/경로 버전 |
| LOT | ready→in_progress | 첫 공정 시작 시 지시와 함께 변경 |
| LOT | in_progress→completed | 마지막 결과 확정 시 지시와 함께 변경 |
| 실행 | 없음→running | 해당 단계 미실행, 지시/LOT 유효, 직전 공정 완료 |
| 실행 | running→completed | 실적 검증 통과, 확정 result 1개와 종료시각 생성 |

대기 단계는 '실행 행 없음'으로 표현한다. 완료 실적을 0으로 미리 생성하지 않는다. 같은 LOT/경로 단계 재실행·분할·병합·재작업·보류 처리는 후속 QMS/확장 범위다.
첫 공정 투입은 LOT 계획 수량, 이후 투입은 직전 양품으로 서버에서 산출한다. 사용자 제출 투입은 서버 산출값과 일치해야 한다. EA는 정수, 수량≥0, 완료 시 투입=산출=양품+불량, 불량>0이면 사유 필수. 시작·종료의 권위 있는 시각은 서버가 기록한다. 임의 과거시각 입력은 첫 UI에 제공하지 않는다.

전량 불량 경계: 중간 공정의 양품이 0이면 후행 0투입 실행을 만들지 않는다. 해당 LOT/지시는 completed와 종료사유 all_defective로 종결하며 후행 단계는 '투입 없음으로 미실행'으로 표시한다. 최종 양품=0, 누적 불량=초기 투입으로 대사한다. 지정 수량을 요구하는 학습 과제는 미완료이며 재체험을 안내한다. 종료사유 필드는 FS-007에서 추가한다.

### 학습·콘텐츠·세대
| 대상 | 전이/정책 |
|---|---|
| 학습 시도 | 없음→in_progress→completed. 초기화 시 미완료만 needs_restart. needs_restart를 기존 행에서 되돌리지 않고 새 시도 생성 |
| 단계 진도 | not_started→in_progress→completed. 업무 결과와 답안을 서버가 검증. 조회/화면 이동만으로 완료 불가 |
| 과정/경로 버전 | draft→published→retired. 게시 내용은 불변. 수정은 새 버전. retired는 신규 선택 제외, 기존 참조와 시도는 유지 |
| 데이터 세대 | preparing→ready→active→retired→purged. 준비/검증 실패는 failed. purged도 메타데이터 행은 보존 |
| 예약 실행 | running→succeeded/failed. 중단된 실행은 락 재획득 후 실제 적용 상태를 확인해 복구 |

게시 버전 하위 행(단계·질문·정답/경로 단계)도 수정/삭제 금지다. 부모만 막고 자식 수정을 허용하지 않는다. 마이그레이션 계정과 정리 CLI를 제외한 일반 쓰기는 게시 보호 검사와 DB 보호 장치를 통과해야 한다.

## 2. 권한과 검사 순서
기본 원칙: 거부 우선. UI 역할 체험은 서버 역할 변경이 아니다. runtime 계정은 앱 전용이며 DDL/슈퍼유저 권한을 갖지 않는다. 사용자 계정과 PostgreSQL 접속 역할은 별개다.

| action | 학습자 | 콘텐츠 관리자 | 운영 관리자 |
|---|---|---|---|
| workspace.read / learning.practice | 본인 공간 | 본인 학습자 권한이 별도로 있을 때 | 동일 |
| mes.order.create/release/cancel_draft | 본인 공간 | 권한 자동 부여 안 함 | 권한 자동 부여 안 함 |
| mes.execution.start/complete | 본인 공간 | 자동 부여 안 함 | 자동 부여 안 함 |
| modules.configure / dashboard.edit | 본인 공간 | 자동 부여 안 함 | 자동 부여 안 함 |
| workspace.reset | 본인 공간, 초기화 범위 안내 후 명시 요청 | 자동 부여 안 함 | 대상 공간의 운영 초기화 권한·사유·감사 필요 |
| content.draft/edit/publish/retire | 불가 | 허용 | 별도 콘텐츠 역할 필요 |
| operations.inspect/retry | 불가 | 불가 | 허용, 운영 메타데이터 중심 |
| 다른 사용자 업무/답안 조회·수정 | 불가 | 불가 | 기본 불가 |

주간 초기화는 예약 실행 전용 주체가 수행한다. 운영 초기화 권한은 타 사용자의 업무 열람/수정 권한을 뜻하지 않는다. audit의 actor는 사용자 또는 명시적인 서비스 주체이며 actor_user_id가 NULL이면 system actor 식별과 실행 ID를 기록한다.

요청 검사: 인증/세션→변경 요청 CSRF→action 권한→대상 공간 소유/운영 범위→공간 잠금→요청 세대·설정 버전 재검증→모듈 활성→업무 상태/입력 규칙→저장. 타인의 식별자로 요청하면 존재 여부를 드러내지 않는 응답을 사용한다. 내부 서비스 호출과 CLI도 정해진 정책 문맥을 전달한다.
권한은 요청 시 서버에서 조회한다. 권한 철회 후 시작되는 요청부터 반영하고 이미 권한검사를 통과해 처리 중인 짧은 요청은 완료될 수 있다. 강제 동시 취소를 보장한다고 표시하지 않는다.

## 3. 모듈과 기능 의존성
| 모듈/기능 | 필수 | 선택 연결 |
|---|---|---|
| core / learning | 항상 활성 | 없음 |
| MES | core | 학습 가이드 |
| FEMS | core | MES가 켜졌을 때 생산 원단위 |
| BEMS | core | FEMS가 켜졌을 때 사업장 통합 대사 |
| 통합 에너지 대사 | FEMS+BEMS | MES 생산 분석 |
| ERP | core | MES가 켜졌을 때 출하 연결(패킹 단위 참조). 구현 대상 |
| QMS/WMS/BEMS | 준비 중 | 현재 활성화 불가. 설명 카드만 제공 |

활성화/비활성화는 DB 테이블 설치/제거와 분리한다. 상태 변경은 workspace.config_version을 증가시킨다. 클라이언트는 세대와 설정 버전을 함께 보내며 오래된 설정은 새로고침을 안내한다.

비활성화 조건:
- MES: released/in_progress 지시 또는 ready/in_progress LOT/running 실행이 있으면 거부. draft는 보존 가능. 미완료 학습만 있고 생산 미종결 업무가 없으면 비활성화 가능하며 해당 단계에 모듈 필요 표시.
- FEMS/BEMS: 해당 공간에 처리 중 수집·집계·배분 작업이 있으면 작업 종료 후 변경. 이전 관측/배분 결과는 보존.
- 공통: 필수 의존 기능이 있으면 거부하고 이유를 보여준다. 자동 연쇄 비활성화 금지. 위젯 선호는 보존하되 필요 모듈 없는 위젯은 숨긴다.
- 초기화 CLI는 비활성 모듈의 과거 데이터도 세대 단위로 정리할 수 있다. 일반 업무 우회 권한으로 사용하지 않는다.

FEMS/BEMS 관측 등록은 소유 모듈을 검사한다. 모듈 off 상태에서는 신규 업무 수집/분석 변경을 하지 않는다. 합성 후보 세대 준비는 별도 관리 경로이며 사용자 업무 요청으로 취급하지 않는다.

## 4. 공통 락과 트랜잭션 계약
초기 버전은 복잡한 병렬 처리보다 같은 개인 공간의 짧은 쓰기를 직렬화한다. 일반 업무/학습/설정 쓰기는 READ COMMITTED 트랜잭션에서 workspace 행을 SELECT FOR UPDATE로 가장 먼저 잠근다. 공간이 다른 사용자는 서로 다른 행을 잠근다. 무거운 계산·네트워크·사용자 입력 대기는 락 밖에서 수행한다.

이 정책은 프로젝트의 설계 선택이다. PostgreSQL 행 잠금과 격리 동작 근거는 문서 말미의 공식 자료를 참조한다. 모든 코드 경로가 같은 규칙을 따르는지 실제 통합 테스트가 필요하다.

명시 잠금 순서:
1. 공간(workspace_id 오름차순, 원칙적으로 한 요청 한 공간)
2. 세대/모듈 설정
3. 작업지시→LOT→공정 실행 (같은 종류는 id 오름차순)
4. 학습 시도→단계 진도
5. 실행 결과/요청 결과/감사 삽입

후행 자식을 잠근 뒤 부모 잠금을 역으로 얻지 않는다. 글로벌 콘텐츠 편집은 부모 버전→자식 순서를 사용하며 공간 잠금과 혼합하지 않는다. 게시 완료 콘텐츠를 업무에서 읽을 때는 immutable 버전을 사용한다.

일반 조회는 쓰기 잠금을 기본 사용하지 않는다. 한 응답에서 세대를 섞지 않도록 읽기 전용 REPEATABLE READ 트랜잭션에서 active_generation_id를 한 번 읽고 모든 조회에 같은 S를 적용한다. 응답에 세대/설정 버전을 반환한다. 조회 직후 초기화가 일어나도 화면이 최신이라고 보장하지 않으며 이후 쓰기의 세대 검사로 차단한다.

### TX-01 지시 등록/발행/LOT 생성/공정 시작
공간 잠금→권한/세대/모듈 재확인→요청 키 처리→부모/선행 상태 확인→업무 행과 필요한 상태/감사/요청 결과 함께 저장→commit. 초기 LOT 1개와 공정 1회 정책은 DB UNIQUE로도 강제한다.

### TX-02 공정 완료
공간·부모·실행 잠금→기존 요청 키 우선 확인→running 확인→단위/수량/선행 양품/사유 검증→result INSERT→실행 completed→필요 시 LOT/지시 completed→감사/요청 결과→commit. 어느 단계든 실패하면 모두 rollback.
완료된 실행에서 동일 키 재시도는 기존 성공 반환, 다른 키 새 완료는 상태 충돌이다. 이미 completed이므로 무조건 거부해 정상 재시도까지 실패시키지 않도록 순서를 지킨다.

### TX-03 학습 검증
업무 commit 후 별도 트랜잭션: 공간 잠금→세대/시도/콘텐츠 버전→live binding 실제 업무→답안/검증→단계/시도 결과와 근거 요약 저장. 생산 성공과 학습 검증 성공을 구분한다. 학습 저장 실패는 생산을 취소하거나 재실행시키지 않고 이어하기에서 재검증한다.
사용자 답안은 submission_key와 본문 동일성을 검사한다. 동일 키 재전송은 재시도 횟수를 늘리지 않는다. 답안 본문 해시 또는 정규화된 기존 답안 비교를 FS-007에 반영한다.

### TX-04 모듈 설정
공간 잠금→expected_config_version 확인→필수 의존/미종결 업무/실행 작업 검사→설정 변경+config_version 증가+감사→commit. 업무 시작도 같은 공간 잠금을 사용하므로 검사 직후 실행이 끼어드는 경합을 방지한다.

### TX-05 초기화
A. 중복 실행 조정: DB의 공간별 세션 advisory lock을 전용 연결로 획득한다. 수동·예약 초기화 모두 같은 키 체계를 사용한다. 락 해제는 finally, 프로세스 종료 시 연결 종료. 장시간 트랜잭션을 붙잡는 방식과 구분한다.
B. 준비: job_run 실행 기록과 후보 generation 생성, 배치 단위 seed/검증. 사용자 현재 세대는 유지. 준비 중 오류는 별도 트랜잭션으로 failed 기록.
C. 전환(짧은 단일 트랜잭션): workspace 잠금→초기화 작업 소유/후보 ready 재확인→구세대 retired/신세대 active→active_generation_id 전환 및 config_version 증가→구세대 미완료 시도 needs_restart→전환 감사와 job succeeded→commit.
D. 정리: 별도 작업으로 retired 데이터 자식부터 정리, generation 메타 유지. 정리 실패는 이미 성공한 전환을 실패라고 뒤집지 않고 cleanup_pending으로 별도 기록한다.

초기화와 완료가 겹치면 공간 잠금을 먼저 획득한 쪽이 완료된다. 업무가 먼저 commit하면 그 결과 후 초기화가 전환된다. 초기화가 먼저면 구세대 업무 쓰기는 거부한다. 주간 초기화는 진행 업무도 교체하는 제품 정책이며 모듈 비활성화의 진행 업무 보호와 구분한다.
동일 예약 실행 키의 succeeded가 있으면 재전환하지 않는다. 프로세스 재시작 후 job 상태와 전환 기록을 함께 확인한다. 동일 키의 시도 UNIQUE만으로 중복 실행이 방지된다고 간주하지 않는다.

### TX-06 에너지 계산
집계/배분은 세대·관측 revision·방법 버전을 고정해 락 밖에서 계산한다. 시작 기록과 결과 반영은 각각 짧은 공간 잠금 트랜잭션이다. 반영 전 활성 세대·모듈·입력 revision을 재검증하고 달라졌으면 버리고 재계산한다.
FS-007에 공간별 energy_input_revision, job 소유/heartbeat·만료 및 cleanup 상태를 반영한다. 관측/계측 경계·계산 입력 변경은 같은 revision을 증가시킨다. 초기에는 수정이 드문 합성 데이터용 보수적 전략이다.
같은 계측 범위·기간에서 현재 방법 버전 하나만 기본 결과로 조회한다. 다른 방법 버전의 결과를 함께 합산하지 않는다. 실행별 배분 합계는 원천 소비량을 초과하지 않으며 잔여를 별도로 표시한다. 단순 UNIQUE만으로 구간 중첩/이중 배분이 방지된다고 보지 않고 겹치는 구간을 포함한 검증을 수행한다.

## 5. 재시도·타임아웃·보호 장치
- MES 요청 결과는 업무와 같은 트랜잭션에 저장한다. 결과 미존재가 곧 실패를 의미하지 않는다. 응답 불명 시 동일 키로 조회/재요청한다.
- request_hash는 작업 유형·대상·S·정규화 본문을 포함한다. 인증/권한/세대/모듈 검사는 기존 결과 반환에도 선행한다. 구세대 결과를 현재 화면 성공으로 반환하지 않는다.
- 일반 쓰기 기본값 후보: lock_timeout 3초, statement_timeout 10초. 구현/측정 후 조정하며 DDL·seed·정리 작업에는 별도 유한 제한을 둔다.
- deadlock/serialization 실패는 전체 트랜잭션 rollback 후 멱등한 요청만 최대 2회 추가 재시도. 외부 HTTP를 같은 트랜잭션에 넣지 않는다. 락 대기 초과는 재시도 가능 오류로 반환하며 무한 반복하지 않는다.
- 수량/시각 CHECK, UNIQUE, 공간·경로·과정 버전 복합 FK는 DB에서 강제한다. 선행 단계/권한/허용설비/전이 검증은 서비스에서 잠금 안에 수행한다.
- 확정 result와 audit는 일반 런타임 UPDATE/DELETE를 금지한다. 세대 정리 전용 역할은 해당 업무 데이터에만 필요한 DELETE를 가진다. 보존 audit·학습·계정은 세대 정리 대상이 아니다.
- 콘텐츠/경로의 게시 후 변경은 서비스와 DB 보호 검사로 차단한다. 모든 변경은 마이그레이션으로 배포한다.

## 6. 오류 응답 계약
형식: code, message, field_errors(필요 시), retryable, correlation_id. 내부 SQL/스택/비밀정보는 응답에서 제외한다.

| HTTP | code | 사용자 대응 |
|---|---|---|
| 401 | AUTH_REQUIRED | 로그인 후 저장 결과 확인 |
| 403 | ACTION_FORBIDDEN / CSRF_REJECTED | 권한 안내 또는 화면 갱신 |
| 404 | RESOURCE_NOT_FOUND | 없음/접근 불가를 동일하게 표시 |
| 409 | GENERATION_STALE / CONFIG_STALE | 새로고침, 초기화 후 실습 다시 준비 |
| 409 | MODULE_DISABLED / DEPENDENCY_CONFLICT | 모듈 설정·필수 기능 안내 |
| 409 | STATE_CONFLICT / PREDECESSOR_INCOMPLETE | 현재 상태/선행 업무 확인 |
| 409 | REQUEST_KEY_CONFLICT | 같은 키의 다른 요청임을 알림, 임의 재처리 금지 |
| 422 | VALIDATION_FAILED | 해당 필드와 수량/단위/사유 수정 |
| 503 | WORKSPACE_BUSY / TEMPORARY_FAILURE | 성공을 단정하지 않고 결과 조회·제한된 재시도 |

트랜잭션이 실패하면 실패 감사/운영 기록은 rollback 후 별도 제한된 기록 경로로 남긴다. 기록 실패가 원래 오류를 성공으로 바꾸지 않는다. 타 사용자 리소스 내용과 비밀값을 로그에 기록하지 않는다.

## 7. 추가 수용 기준 — 실행 전
기존 AC-01~34는 유지하며 아래를 추가한다.

| ID | 상황 | 기대 결과 |
|---|---|---|
| AC-35 | 업무 완료와 초기화 동시 실행, 순서 양쪽 시험 | 앞선 commit만 해당 세대에 유효, 구세대 변경 없음 |
| AC-36 | 모듈 off와 작업 시작 동시 실행 | off 후 시작 거부 또는 시작 후 off 거부, 양쪽 성공 금지 |
| AC-37 | 다른 키로 같은 공정을 동시 완료 | result 1개·수량 1회·종결 이력 1회 |
| AC-38 | 초기화 준비 중 종료/전환 직후 종료 | 실패 후보가 active가 되지 않음, 전환 성공 키는 재실행 안 함 |
| AC-39 | 전환 성공 후 정리 실패 | 신규 세대 사용 가능, 보존 기록 유지, 정리만 재시도 |
| AC-40 | 중간 공정 전량 불량 | 양품 0·불량 전체 대사, 후행 0투입 실행 없음, 과제 미완료 안내 |
| AC-41 | 게시 콘텐츠/경로의 자식 수정 시도 | 변경 거부, 과거 시도/지시 내용 불변 |
| AC-42 | 배분 계산 도중 관측값·세대 변경 | 낡은 결과 반영 거부, 다른 방법 결과 중복 합산 없음 |
| AC-43 | 잠금 시간 초과·deadlock 오류 주입 | 유한 대기/재시도, 부분 저장 없음, 실제 실패 표시 |
| AC-44 | 동일 답안 키 재전송/다른 답안으로 재사용 | 동일 답안 1회 처리, 다른 답안 충돌, 횟수 중복 없음 |
