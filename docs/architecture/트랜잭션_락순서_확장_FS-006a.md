## 1. 락 순서 확장

### 1.1 먼저 정정할 것

FS-005a 논의 과정에서 "출하 확정 시 락 순서를 지키지 않으면 패킹 경합에서 데드락이 난다"고 표현했으나, **정확하지 않다.**

FS-006의 정책상 모든 업무 쓰기는 **workspace 행을 가장 먼저 `SELECT FOR UPDATE`로 잠근다.** 한 공간의 쓰기는 이미 직렬화되므로, 같은 공간 안에서 서로 다른 객체를 엇갈려 잠그는 데드락은 구조적으로 발생하지 않는다.

그렇다면 락 순서는 왜 필요한가. 세 가지 경로 때문이다.

| 경로 | 이유 |
|---|---|
| 세대 정리 CLI | 공간 잠금 없이 여러 공간의 데이터를 자식→부모 순으로 지운다 |
| 게스트 회수 작업 | 만료 공간을 배치로 회수한다. 진행 중 요청과 겹칠 수 있다 |
| 향후 공간 잠금 완화 | 성능 문제로 공간 단위 직렬화를 풀 때 순서가 유일한 방어선이 된다 |

즉 **락 순서는 지금 당장의 데드락 방어가 아니라 정리 경로의 정합성과 미래 완화의 전제다.** 이 구분을 문서에 남긴다.

### 1.2 확장된 명시 잠금 순서

FS-006 4장의 5단계를 8단계로 확장한다. 번호가 작은 것부터 잠그고, 자식을 잠근 뒤 부모를 역으로 얻지 않는다.

| 순서 | 대상 |
|---|---|
| 1 | 공간 (workspace_id 오름차순, 원칙적으로 한 요청 한 공간) |
| 2 | 세대 / 모듈 설정 |
| 3 | **판매계획 → 생산계획** (헤더 → 라인) |
| 4 | 작업지시 → LOT → 공정 실행 |
| 5 | **패킹 단위 → 패킹 구성 → 완제품 입고** |
| 6 | **수주 → 출하지시 → 출하 → 매출** |
| 7 | **채권·채무 → 수금·지급 → 소명** (FS-014b, 폐기 학습 단계 대체) |
| 8 | 실행 결과 / 요청 결과 / 감사 삽입 |

FS-014b 회계 7단계: 수금 경로는 **receivable.id 오름차순 → receipt.id 오름차순 → receipt_apply.id 오름차순**,
지급 경로는 payable.id → payment.id → payment_apply.id 오름차순이다.
혼합 경로는 receivable → payable → receipt → payment → receipt_apply → payment_apply 순서이며 각 테이블 id 오름차순이다.
매입 헤더→명세와 매출→세금계산서는 원천 거래인 6단계에서 잠근다. 감사·요청 결과 기록은 8단계다.
소명 추가·물리 삭제는 부모 잠금 후 양쪽 합계를 새로 계산하며, 취소와 발급완료 확인도 동일 순서를 따른다.
[FS-014b 회계 계약](../db/스키마_재구성_FS-014b.md)이 회계의 상세 기준이다.

같은 순서 안에서는 id 오름차순이다. 패킹 단위의 자기참조(BOX → PALLET)는 **상위(PALLET)를 먼저** 잠근다. 부모 우선 규칙을 자기참조에도 동일하게 적용한다.

`learning`·`process_map`은 FS-013에서 폐기됐다. 도움말·맵은 정적 파일이며 DB 잠금 단계가 없다.

### 1.3 세대 정리 순서

세대 교체 후 구세대를 지울 때의 삭제 순서다. 참조 삭제가 RESTRICT이므로 순서를 틀리면 정리가 실패한다.

```
수금 소명 / 지급 소명 → 수금 / 지급 → 채권 / 채무
  → 세금계산서 → 매출 / 매입 명세 → 매입 전표
  → 분개 규칙 → 계정과목
  → 출하 명세 → 출하 → 출하지시 명세 → 출하지시 → 수주 명세 → 수주
  → 완제품 입고 → 패킹 구성 → 패킹 단위(BOX 먼저, PALLET 나중)
  → 공정 결과 → 공정 실행 → LOT → 작업지시
  → 생산계획 라인 → 생산계획 → 판매계획 라인 → 판매계획
  → 거래처 → 기준정보(품목·설비·경로 등)
```

패킹 단위는 자기참조가 있으므로 **BOX를 먼저 지우고 PALLET을 나중에** 지운다. 잠금 순서(상위 먼저)와 삭제 순서(하위 먼저)가 반대라는 점에 주의한다.

## 2. 트랜잭션 계약

### TX-07 출하지시 생성

공간 잠금 → 권한/세대/모듈 재확인 → 요청 키 처리 → 수주·수주 명세 잠금 → **수주 라인별 `Σ 지시수량 + 신규 지시수량 ≤ order_qty` 검증** → 출하지시·명세 INSERT → 수주 상태 갱신(open → shipping) → 감사/요청 결과 → commit.

누계 검증은 반드시 수주 명세를 잠근 뒤에 한다. 잠그지 않고 합계를 읽으면 동시 지시가 각각 통과해 합계가 수주수량을 넘는다. 공간 잠금이 이미 이를 막지만, 검증 순서를 코드에 명시해 공간 잠금 완화 시에도 성립하게 한다.

초과 지시는 `STATE_CONFLICT`로 거부한다. 부분 지시는 허용한다.

### TX-08 출하 확정

공간 잠금 → 권한/세대/모듈 재확인 → 요청 키 처리 → **패킹 단위 잠금(순서 5)** → 출하지시·명세 잠금(순서 6) → 검증 → 출하·출하 명세 INSERT → 패킹 단위 상태 received → shipped → 출하지시 상태 shipped → **TX-09 실행** → 감사/요청 결과 → commit.

검증 항목:

| 항목 | 위반 시 |
|---|---|
| 패킹 단위가 완제품 입고 완료(received) 상태 | `STATE_CONFLICT` |
| 해당 패킹 단위가 다른 출하에 사용되지 않음 | `STATE_CONFLICT`. `erp.shipment_line`의 `(S, packing_unit_id)` UNIQUE로도 강제 |
| 출하수량이 지시수량 이하 | `VALIDATION_FAILED` |
| 출하지시가 open 상태 | `STATE_CONFLICT` |

패킹 단위를 출하지시보다 **먼저** 잠근다. 순서 5가 순서 6보다 앞이기 때문이다.

### TX-09 매출 인식

**독립 트랜잭션이 아니다. TX-08 안에서 실행된다.**

출하 명세와 수주 명세의 단가로 공급가액을 계산 → 세액 계산 정책 함수 적용 → `erp.sales_record` INSERT 1건.

`(S, shipment_id)` UNIQUE가 중복 인식을 막는다. 요청 재전송으로 매출이 2건 생기지 않는다. 매출 생성이 실패하면 출하 확정 전체가 rollback된다. **출하는 됐는데 매출이 없는 상태를 만들지 않는다.**

금액은 NUMERIC으로 계산한다. 세율·반올림은 단일 정책 함수에서만 처리하고 호출부에서 재계산하지 않는다.

### TX-10 패킹

공간 잠금 → 권한/세대/모듈 재확인 → 요청 키 처리 → **LOT 잠금(순서 4)** → 패킹 단위 잠금(순서 5) → 검증 → 패킹 단위/구성 INSERT 또는 구성 추가 → 감사/요청 결과 → commit.

검증 항목:

| 항목 | 내용 |
|---|---|
| 양품 초과 | `Σ packing_member.packed_qty ≤ 해당 LOT의 확정 양품수량` |
| 확정 실적 존재 | 확정 결과가 없는 LOT은 패킹 불가 |
| 전량 불량 LOT | 양품 0이므로 패킹 불가 (AC-40과 연결) |
| 계층 | BOX의 상위는 PALLET만. PALLET에 상위 지정 거부 |
| 순환 | 상위 체인을 따라가며 자기 자신 도달 여부 검사 |
| 상태 | closed 이후 구성 변경 거부 |

LOT을 패킹 단위보다 먼저 잠근다. 양품 잔여 계산이 LOT 실적에 의존하므로, 계산 근거를 먼저 고정해야 한다.

### TX-11 완제품 입고

공간 잠금 → 권한/세대/모듈 재확인 → 요청 키 처리 → 패킹 단위 잠금(PALLET 먼저, 하위 BOX 나중) → 검증 → 입고 INSERT → 패킹 단위 상태 closed → received → 감사/요청 결과 → commit.

검증 항목:

- PALLET 입고 시 **하위 BOX가 모두 closed 상태**여야 한다.
- 이미 입고된 패킹 단위의 재입고를 거부한다. `(S, packing_unit_id)` UNIQUE.
- **입고 후 구성 변경을 거부한다.** 입고는 구성 확정 시점이다.

입고 취소는 해당 패킹 단위가 출하되지 않은 경우에만 허용한다.

### TX-12 게스트 공간 생성과 회수

FS-005a의 게스트 체험과 FS-005b의 템플릿 복사를 트랜잭션 계약으로 정리한다.

**A. 생성**

1. 동시 게스트 공간 수 확인. 상한 초과 시 이미 만료되고 세션이 종료된 회수 가능 공간을 먼저 회수하고, 그래도 초과면 생성을 거부한다 (AC-49).
2. 단일 트랜잭션: workspace(kind=GUEST, guest_session_key, expires_at) INSERT → 세대 preparing 생성 → **템플릿 세대를 `INSERT ... SELECT`로 복사**(시간축은 기준일 T로 재계산) → 검증 → 세대 active 전환 → commit.
3. 실패 시 전부 rollback. 부분 생성물을 남기지 않는다 (AC-46).

FS-006 TX-05의 세대 전환 계약을 재사용하되, 게스트는 구세대가 없으므로 전환 단계가 단순하다. 복사량 상한은 FS-005b의 약 6,840행이다.

**B. 회수**

`core.job_run`에 `job_kind = 'guest_cleanup'`으로 기록한다. 실행 키는 정리 대상 일자다. 새 테이블을 만들지 않는다.

- 만료됐으며 세션이 종료되고 진행 중 요청이 없는 공간을 배치로 선택 → 공간별로 1.3의 삭제 순서를 따라 자식부터 정리 → workspace 삭제.
- 정리 실패는 개별 공간 단위로 기록하고 다른 공간의 정리를 중단하지 않는다.
- **FS-008b: expires_at 도달만으로 작업 중 세션을 종료하거나 회수하지 않는다.** guest_pool→공간 잠금 안에서 만료·세션 종료·진행 요청 부재를 재확인한 뒤 회수한다. 활성 세션이면 건너뛴다. 만료 공간의 신규 세션 재개는 거부한다. 세션 생존 판정은 서비스 책임이며 상세 인증·종료 계약은 FS-010에서 정의한다. 삭제 순서·작업 기록·실패 처리는 기존 TX-12를 따른다.
- 같은 일자 실행 키의 succeeded가 있으면 재실행하지 않는다.

**C. 승격 없음**

게스트가 회원 가입해도 데이터를 이관하지 않는다. 새 공간을 만든다. 공간·세대 재바인딩과 학습 근거 이전 비용이 가치에 비해 크다. 화면에서 이 점을 미리 안내한다.

## 3. 계획 확정 처리

판매계획·생산계획 확정은 별도 TX 번호를 부여하지 않는다. TX-01과 같은 형태의 단순 상태 전이다.

공간 잠금 → 권한/세대/모듈 → 계획 헤더 잠금 → 라인 존재 확인 → status draft → confirmed, confirmed_at 기록 → 감사 → commit.

확정 이후 라인 변경은 서비스에서 거부한다. 생산계획은 근거 판매계획이 confirmed일 때만 확정할 수 있다.

## 4. 수용 기준 순증 (AC-59 ~ AC-64)

FS-005a의 AC-45~58에 이어서 부여한다.

| ID | 상황 | 기대 결과 |
|---|---|---|
| AC-59 | 같은 LOT에 대해 서로 다른 키로 동시 패킹 요청 | 양품 잔여를 초과하는 쪽이 거부. 합계가 확정 양품을 넘지 않음 |
| AC-60 | 같은 패킹 단위로 동시 출하 확정 | 1건만 성공. 나머지는 상태 충돌. 매출도 1건 |
| AC-61 | 출하 확정 중 매출 생성 실패 주입 | 출하 전체 rollback. 출하만 있고 매출 없는 상태가 생기지 않음 |
| AC-62 | 게스트 공간 생성 중 복사 실패 주입 | 부분 생성물 없음. 공간·세대 모두 남지 않음 |
| AC-63 | 게스트 회수와 진행 중 업무 요청이 겹침 | 양쪽 성공 금지. 회수 후 요청은 만료 안내 |
| AC-64 | 세대 정리 시 출하·매출이 있는 세대 | 삭제 순서대로 정리 성공. RESTRICT 위반 없음 |

AC-59·AC-60은 공간 잠금이 이미 막지만, **공간 잠금이 없다고 가정한 상태에서도 통과해야 한다.** 검증 순서와 UNIQUE 제약이 실제 방어선인지 확인하는 것이 시험 목적이다.

## 5. 검토 한계

- 정적 설계 검토만 수행했다. 실제 DB 락 실험, 동시성 주입 시험, 성능 측정은 모두 미실행이다.
- 락 타임아웃 값(lock_timeout 3초, statement_timeout 10초)은 FS-006 값을 그대로 쓴다. 게스트 공간 복사는 6,840행 단일 트랜잭션이므로 **statement_timeout 10초로는 부족할 수 있다.** 복사 작업에 별도의 더 긴 제한을 둔다. 실측 후 조정한다.
- 세대 정리 순서는 FS-007a 메타데이터의 FK 목록과 대조해 도출했으나, 실제 DDL 적용 후 재확인이 필요하다.
- TX-12의 템플릿 복사는 배포 시 템플릿 세대가 존재한다는 전제에 의존한다. 마이그레이션과 템플릿 생성의 순서는 FS-009에서 정한다.
