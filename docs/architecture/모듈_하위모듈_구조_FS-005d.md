# FS-005d 모듈 · 하위 모듈 구조 정의

> FS-008b 후속 결정: core.dashboard_layout은 삭제됐다. 아래 당시 목록은 이력이며 현재 엔티티·배분 quantity/unit·소유 모듈 정리는 [v0.9.0 설계](../db/스키마_재구성_FS-008b.md)를 따른다.

작성일: 2026-09-21. 상태: 정의 확정, 메타데이터 반영 대기.
기준: 2026-09-21 사용자 확인 — 하위 모듈 분해 승인, 스키마 분리 없이 `sub_module` 속성으로 표현.
성격: 스키마·테이블·컬럼을 **변경하지 않는다.** 분류 축을 하나 더하는 작업이다.

---

## 1. 왜 필요한가

현재 구조는 `모듈 → 테이블` 2단이다. 사용자가 기대하는 구조는 `모듈 → 하위 업무 모듈 → 테이블` 3단이다. 중간 계층이 설계에 없어서 60개 테이블이 7개 스키마에 평평하게 흩어져 보인다.

특히 `core`가 19개(32%)를 가져가면서 **각 모듈이 알맹이 없이 보인다.**

| 모듈 | 테이블 | 그 안에 없는 것 |
|---|---:|---|
| CORE | 19 | — |
| MES | 14 | 작업장·설비·품목 (core 소유) |
| ERP | 10 | 품목 (core 소유) |
| FEMS | 6 | 계측기·계측 채널·에너지원 (core 소유) |
| LEARN | 6 | — |
| MAP | 3 | — |
| BEMS | 2 | 준비 중 |

이건 잘못된 설계가 아니라 **분류 축이 하나 부족한 것**이다. 공유 마스터를 모듈마다 복제하는 것이 제조 시스템에서 가장 흔한 실패이므로 소유 구조는 그대로 둔다.

## 2. 왜 스키마를 쪼개지 않는가

| | 스키마 분리 | `sub_module` 속성 |
|---|---|---|
| 화면에 보이는 결과 | 같음 | 같음 |
| FK·권한 | 스키마를 넘나든다. 권한 부여 20배 | 변화 없음 |
| 트랜잭션 규칙 | "모듈은 자기 데이터만 변경" 규칙이 무너진다 | 유지 |
| 되돌리기 | 매우 비쌈 | 값 하나 수정 |

보이는 결과가 같은데 한쪽만 되돌리기 비싸면 싼 쪽을 고른다. 나중에 정말 쪼개야 할 이유가 생기면 그때 쪼갠다.

## 3. 모듈 경계 규칙 — 독립 솔루션을 성립시키는 조건

각 모듈은 **다른 모듈을 꺼도 자기 업무가 돌아가야 한다.** 그러려면 참조를 두 종류로 구분해야 한다.

| 구분 | 대상 | 의존 방식 |
|---|---|---|
| **공유 기준정보** | core 소유 — 품목, 거래처, 설비, 사업장, 작업장, 계측기, 에너지원 | **필수 참조 허용.** 없으면 어느 모듈도 성립하지 않는다 |
| **타 모듈 업무 데이터** | MES 패킹 단위·LOT, ERP 판매계획 등 | **필수 의존 금지.** nullable 선택 참조만 허용한다 |

판정 기준은 하나다. **그 모듈을 꺼도 이 모듈의 업무가 성립하는가.** 꺼지면 칸이 비어 있을 뿐, 업무는 돌아가야 한다.

선택 참조는 값이 있을 때만 제약을 적용한다. 값이 없으면 계산 불가로 표시하고 오류로 처리하지 않는다.

### 3.1 이 규칙으로 점검한 결과

| 연결 | 판정 |
|---|---|
| `mes.production_plan.sales_plan_id` → ERP 판매계획 | 통과. 이미 nullable |
| `erp.shipment_line.packing_unit_id` → MES 패킹 단위 | **위반.** 필수라 MES 없이 출하 불가 → FS-005e에서 수정 |
| FEMS 원단위 ← MES 생산량 | 부분 위반. 에너지 조회는 독립 성립, 원단위는 계산 불가 표시로 처리 |
| `fems.*` → `core.equipment` | 통과. core 마스터 |
| `mes.learning_binding` → 학습 | 통과. 학습은 별도 축 |

전체 FK는 `tools/audit_module_boundary.py`로 점검한다. 새 테이블을 추가할 때마다 다시 돌린다.

## 4. 세 가지 표시 구분

각 하위 모듈 화면에서 테이블은 셋 중 하나로 표시된다. 이 구분이 "MES에 설비가 없다"는 위화감을 없애면서 데이터 중복을 막는다.

| 표시 | 뜻 |
|---|---|
| **소유** | 이 하위 모듈이 생성·변경한다 |
| **참조** | 화면에 보이지만 다른 모듈이 소유한다. 여기서 변경할 수 없다 |
| **준비 중** | 설명 카드만 제공한다. 테이블이 없거나 활성화할 수 없다 |

## 4. 하위 모듈 정의

### CORE — 공통 기반

| 하위 모듈 | 소유 테이블 |
|---|---|
| `account` 계정·권한 | app_user, auth_session, role, user_role |
| `workspace` 공간·세대 | workspace, data_generation, workspace_module, dashboard_layout |
| `factory_master` 공장 기준정보 | site, location, equipment |
| `item_master` 품목 기준정보 | item, item_unit_conversion |
| `metering_master` 계측 기준정보 | meter, meter_channel, energy_source |
| `ops` 운영 | job_run, audit_event, request_receipt |

`factory_master`는 MES·FEMS가, `item_master`는 MES·ERP·FEMS가, `metering_master`는 FEMS·BEMS가 참조한다.

### MES — 생산 관리

| 하위 모듈 | 소유 | 참조 |
|---|---|---|
| `mes_master` 기준정보 | 공정, 공정-설비 허용 | 설비, 작업장, 품목 |
| `routing` 표준공정 | 경로 버전, 경로 단계 | 품목, 공정 |
| `production_plan` 생산계획 | 생산계획, 생산계획 라인 | 품목, 판매계획 |
| `work_order` 작업지시 | 작업지시, LOT | 품목, 경로 버전 |
| `execution` 생산실행 | 공정 실행, 공정 실적 | 설비, 경로 단계 |
| `learning_link` 학습 연결 | 학습 바인딩 | 학습 단계, 업무 결과 |
| `packing` 포장·입고 | 패킹 단위, 패킹 구성, 완제품 입고 | LOT |

### ERP — 판매·출하

| 하위 모듈 | 소유 | 참조 |
|---|---|---|
| `erp_master` 기준정보 | 거래처 | 품목 |
| `sales_plan` 판매계획 | 판매계획, 판매계획 라인 | 품목 |
| `sales_order` 수주 | 수주, 수주 명세 | 거래처, 품목 |
| `shipping` 출하 | 출하지시, 출하지시 명세, 출하, 출하 명세 | 패킹 단위, 완제품 입고 |
| `revenue` 매출 | 매출 | 출하, 거래처 |

### FEMS — 에너지 관리

| 하위 모듈 | 소유 | 참조 |
|---|---|---|
| `fems_master` 분석 기준정보 | 환산·배출 계수, 요금제 | 에너지원 |
| `energy_reading` 계측·조회 | 계측 이력, 설비 배분 | 계측 채널, 설비 |
| `energy_goal` 목표·원단위 | 에너지 목표, 원단위 기준선 | 설비, 품목, 에너지원 |

계측기·채널·에너지원은 core 소유이며 FEMS 화면에서는 참조로 표시한다. BEMS도 같은 마스터를 쓴다.

### LEARN · MAP

| 모듈 | 하위 모듈 | 내용 |
|---|---|---|
| LEARN | `course` 콘텐츠 / `progress` 진도 | 과정·단계·질문 / 시도·진도·답안 |
| MAP | `process_map` 프로세스 맵 | 맵 버전·노드·연결 |

`mes.learning_binding`은 업무 결과와 학습 단계를 이어주는 다리다. 생산실행에 넣지 않고 `learning_link` 로 따로 둔다. 성격이 다른 테이블을 업무 하위 모듈에 넣으면 화면 구성이 탁해진다.

### 준비 중 모듈

| 모듈 | 하위 모듈 (이름만) | 테이블 |
|---|---|---|
| QMS | `inspection` 품질검사, `hold` 보류 관리 | 없음 |
| WMS | `warehouse` 창고·위치, `inventory` 재고 이동 | 없음 |
| BEMS | `common_metering` 공용 계측, `environment` 환경 관측 | 2개 (예약) |

하위 모듈 이름은 미리 정해 둔다. 화면 메뉴와 프로세스 맵 설명 카드가 같은 이름을 쓴다.

## 5. 메타데이터 반영

각 테이블에 `sub_module` 문자열을 추가한다. 컬럼·제약·관계는 건드리지 않는다.

```
"name": "mes.work_order",
"sub_module": "work_order",
```

참조 관계는 테이블 속성이 아니라 **화면 정의**이므로 메타데이터에 넣지 않는다. 위 4장의 "참조" 열이 화면 설계(FS-008a)의 입력이다.

## 6. 검증

- 모든 테이블이 하위 모듈을 하나씩 가진다. 누락이 있으면 반영 스크립트가 중단한다.
- 하나의 테이블이 두 하위 모듈에 속하지 않는다.
- 하위 모듈 이름은 모듈 안에서 유일하다.
