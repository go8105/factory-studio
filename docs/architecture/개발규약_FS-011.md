# FS-011 개발 규약

작성일: 2026-09-23
전제: 스키마 v0.9.0 / FS-008b (71테이블) · [FS-010 API 계약서](API계약서_FS-010.md)
성격: **구현 전 규약.** 코드는 아직 한 줄도 없다. 이 문서가 FS-009 착수 조건을 채운다.

## 1. 런타임 버전 확정

오래 미뤄둔 "착수 전 결정"이다. 정하지 않으면 구현자가 임의 버전으로 환경을 잡고 그게 확정이 된다.

| 대상 | 버전 | 근거 |
|---|---|---|
| **Python** | **3.14** | 현재 권장 프로덕션 버전(3.14.7, 2026-08). EOL 2030-10 |
| **PostgreSQL** | **18** | 현재 안정 메이저(18.6, 2026-08). EOL 2030-11 |
| **Node.js** | **24 LTS** | Active LTS. EOL 2028-04 |

### 왜 최신이 아닌가

- **Python 3.15**는 2026-10-01 출시 예정이다. 출시 직후에는 주요 패키지의 휠이 아직 안 올라온다. 지금 잡으면 설치부터 막힌다.
- **PostgreSQL 19**는 현재 베타 3다. 베타를 프로덕션 기준으로 삼지 않는다.
- **Node 26**은 2026-05 출시된 Current이며 **2026-10-28에 Active LTS가 된다.** 그때 24는 Maintenance로 내려간다. 다만 24의 EOL은 2028-04라 이 프로젝트 기간에는 문제가 없다.

### 업그레이드 기준

Node 26이 Active LTS가 된 뒤(2026-11 이후) 여유가 있으면 올린다. **개발 중에 올리지 않는다.** Python 3.15와 PostgreSQL 19는 이 프로젝트에서 올리지 않는다.

### 고정 방법

| 대상 | 파일 |
|---|---|
| Python | `.python-version` (3.14) + `pyproject.toml`의 `requires-python = ">=3.14,<3.15"` |
| Node | `.nvmrc` (24) + `package.json`의 `engines.node` |
| PostgreSQL | `docker-compose.yml`의 이미지 태그 `postgres:18` |

**메이저만 고정하고 패치는 락파일에 맡긴다.** `postgres:18.6`처럼 패치까지 박으면 보안 패치를 수동으로 따라가야 한다.

### 해소되는 기존 제약

현황 문서의 "Python 3.9에서 `build_erd.py`가 실패한다"는 제약은 3.14 고정으로 사라진다.

## 2. 기술 스택

| 계층 | 선택 |
|---|---|
| 백엔드 | Python 3.14 · FastAPI · SQLAlchemy · Alembic |
| 프론트엔드 | React · TypeScript · Vite |
| DB | PostgreSQL 18 |
| 실행 | Docker Compose (개발·배포 공통) |

**Node는 프론트엔드 빌드와 문서 생성 도구(`build_db_design.mjs`)에만 쓴다.** 백엔드 런타임이 아니다. 따라서 Node 버전 결정의 위험도가 낮다.

라이브러리 버전은 **여기서 숫자를 적지 않는다.** 스캐폴딩 시점에 설치하고 락파일(`uv.lock` / `package-lock.json`)로 고정한다. 문서에 박아두면 락파일과 어긋나고, 어긋나면 문서가 거짓말이 된다.

## 3. 저장소 구조

단일 저장소다. 솔루션별로 저장소를 쪼개지 않는다. 독립은 **소유권과 참조 규칙의 독립**이지 저장소 분리가 아니다(FS-013 D2).

```
factory-studio/
├─ AGENTS.md
├─ docker-compose.yml
├─ docs/                     설계 문서 (현재 구조 유지)
├─ tools/                    메타데이터·Excel·ERD 생성기 (현재 유지)
├─ backend/
│  ├─ pyproject.toml
│  ├─ alembic/
│  │  └─ versions/
│  ├─ src/fs/
│  │  ├─ main.py             앱 조립·라우터 등록
│  │  ├─ common/             설정·DB세션·인증·오류·멱등·페이지
│  │  ├─ core/               포털
│  │  ├─ mes/
│  │  ├─ erp/
│  │  └─ fems/
│  ├─ seed/
│  └─ tests/
├─ frontend/
│  ├─ package.json
│  └─ src/
│     ├─ app/                라우팅·레이아웃·전역 상태
│     ├─ shared/             공통 컴포넌트·API 클라이언트·디자인 토큰
│     ├─ portal/
│     ├─ mes/
│     ├─ erp/
│     └─ fems/
└─ content/                  정적 콘텐츠 (4장)
```

### 솔루션 디렉터리 안의 구조

```
erp/
├─ router.py        엔드포인트
├─ schema.py        요청·응답 모델 (Pydantic)
├─ service.py       업무 규칙·트랜잭션
├─ repository.py    질의
└─ models.py        ORM 매핑
```

**규칙: `erp/`가 `mes/`를 import 하지 않는다.** 스키마 간 FK 0건(FS-013 R1)의 코드 계층 대응물이다. `common/`만 공통으로 쓴다.

`core/`도 업무 모듈을 import 하지 않는다. 방향은 항상 `업무 → common`, `업무 → core(읽기 전용 세션 정보)` 한 방향이다.

### 계층 규칙

| 계층 | 할 수 있는 것 | 금지 |
|---|---|---|
| router | 입력 검증, service 호출, 응답 변환 | 직접 질의, 업무 규칙 |
| service | 트랜잭션 경계, 업무 규칙, 잠금 순서 | HTTP 개념(Request·Response) |
| repository | 질의 | 트랜잭션 커밋, 업무 판단 |

**트랜잭션 경계는 service에만 있다.** router나 repository가 커밋하면 FS-006a의 잠금 순서를 보장할 수 없다.

## 4. 정적 콘텐츠 (P-G03 해소)

FS-008a가 남긴 갭이다. 흐름 맵·설명 카드·도움말을 어디에 어떤 형식으로 둘지 정한다.

```
content/
├─ flow-map.json           P-03 전체 업무 흐름 (노드·연결)
├─ cards/
│  ├─ qms.md   wms.md   bems.md   scm.md      P-04 설명 카드 4종
└─ help/
   ├─ portal/*.md    fems/*.md    erp/*.md    mes/*.md    P-05 도움말
```

| 항목 | 규칙 |
|---|---|
| 형식 | 구조가 있는 것(흐름 맵)은 JSON, 글은 Markdown |
| 제공 | **API가 아니다.** 프론트 빌드 시 번들에 포함한다 |
| 키 | 도움말 파일명 = 화면 ID 소문자 (`f-06.md`, `e-10.md`). 화면의 `?` 버튼이 이 키로 찾는다 |
| 번역 | 하지 않는다. 한국어 단일 |

**DB에 넣지 않는다**(FS-013 D6). 버전 관리가 Git으로 되고, 세대 복사 대상에서 빠져 게스트 생성이 무거워지지 않는다.

## 5. 네이밍

| 대상 | 규칙 | 예 |
|---|---|---|
| DB 테이블·컬럼 | `snake_case` | `receipt_apply`, `due_date` |
| Python | `snake_case` / 클래스 `PascalCase` | `sales_service.py`, `SalesRecord` |
| API 경로 | `kebab-case` 복수형 | `/sales-orders`, `/receipt-applies` |
| JSON 필드 | `camelCase` | `dueDate`, `unappliedAmount` |
| TypeScript | `camelCase` / 컴포넌트 `PascalCase` | `useReceivables.ts`, `ReceiptForm.tsx` |
| 화면 ID | 문서와 동일 | `P-02`, `F-06`, `E-10`, `M-04` |

### DB는 snake_case, JSON은 camelCase

변환 계층이 하나 생기지만, 양쪽 관례를 각각 따르는 편이 낫다. **변환은 Pydantic의 alias generator 한 곳에서만 한다.** 손으로 매핑하지 않는다.

### 화면 ID를 코드에 남긴다

컴포넌트 파일 상단 주석에 화면 ID를 적는다. 설계 문서와 코드를 잇는 유일한 끈이다. 54화면을 구현하다 보면 "이게 무슨 화면이었지"가 반드시 생긴다.

## 6. 마이그레이션

### 원칙

- **도구는 Alembic.** 리비전은 순번이 아니라 해시 기반으로 둔다.
- **이미 적용·공유한 리비전을 수정하지 않는다.** 새 리비전을 추가한다(AGENTS §4).
- 리비전 파일명에 작업 ID를 넣는다. `20261001_fs009_initial_schema.py`

### 메타데이터와 마이그레이션의 관계

**`schema.json`이 설계 기준본이고, 마이그레이션이 그 구현이다.** 두 방향이 있는데 하나만 고른다.

| 안 | 내용 | 판단 |
|---|---|---|
| A | `schema.json`에서 DDL을 생성 | 생성기를 또 만들어야 한다 |
| **B** | **첫 마이그레이션을 손으로 쓰고, 이후 `schema.json`과 대조 검사** | **채택** |

B를 택하는 이유: 71테이블의 DDL 생성기를 만드는 비용이, 첫 마이그레이션을 한 번 쓰는 비용보다 크다. 대신 **대조 검사 스크립트(`tools/verify_ddl_matches_schema.py`)를 만들어 둘이 어긋나면 CI가 잡게 한다.**

`migration_revision` 필드가 `schema.json`에 이미 있다(현재 `null`). 첫 마이그레이션 후 여기에 리비전 ID를 기록한다.

### 순서

```
FS-009: 초기 마이그레이션 1개로 71테이블 전체 생성
이후:   변경마다 새 리비전
```

초기 마이그레이션을 테이블별로 쪼개지 않는다. 한 번에 올라가지 않으면 의미가 없다.

## 7. 시드

### 구조

```
backend/seed/
├─ template.py      템플릿 세대 1개 생성
├─ data/            합성 데이터 (CSV 또는 Python 상수)
└─ copy.py          템플릿 → 사용자 공간 복사
```

### 규칙

- **템플릿 세대를 한 번 만들고 `INSERT ... SELECT`로 복사한다**(FS-005b). 매번 생성 로직을 돌리지 않는다.
- **난수를 쓰지 않는다.** 같은 시드는 항상 같은 데이터를 만든다. 디버깅이 가능해야 한다.
- 시간축은 절대 날짜가 아니라 **기준일 T 오프셋**이다.
- 복사 순서는 FS-013 7장(3스키마 부모 → 자식)을 따른다.
- **품목·설비 코드를 mes·erp·fems에 동일하게 심는다.** 마스터가 독립이라 코드 일치는 시드의 책임이다(FS-013 §2).

### 시드 정의 갱신 필요

`architecture/합성데이터_시드정의_FS-005b.md`는 단일 스키마·단일 에너지원·BOM 없음 기준이다. **3스키마·다중 에너지원·자재 투입·회계 A층을 반영해야 한다.** 별도 작업(FS-005g)이며 구현 착수 전에 끝내야 한다.

## 8. 테스트

### 계층

| 종류 | 대상 | 도구 |
|---|---|---|
| 단위 | service의 업무 규칙 | pytest |
| 통합 | API 엔드포인트 + 실제 DB | pytest + testcontainers 또는 전용 테스트 DB |
| 메타데이터 | `schema.json` 정합성·격리 규칙 | 기존 `tools/` 스크립트 |

### 반드시 있어야 하는 테스트

FS-010 10장의 SERVICE 정책 7건은 **DB가 막아주지 않는다.** 전부 통합 테스트로 검증한다.

| 정책 | 검증 |
|---|---|
| Σ소명액 ≤ 수금액·채권 원금 | 초과 요청이 409로 거부되고 아무것도 저장되지 않는다 |
| 배정 합계 ≤ 계획·수주 수량 | 동일 |
| 패킹 수량 ≤ LOT 양품 | 동일 |
| 설비 동시 점유 금지 | 두 실행을 동시에 시작하면 하나만 성공한다 |
| 매출 취소 조건 | 소명이 있으면 거부, 발급완료 세금계산서가 있으면 거부 |
| 멱등키 | 같은 키 재요청은 같은 응답, 다른 본문은 422 |
| 범위 격리 | **다른 공간의 자원 ID로 요청하면 404** |

**마지막 항목이 가장 중요하다.** FS-010의 "범위 키를 클라이언트가 보내지 않는다"가 실제로 지켜지는지 검증한다. 이게 뚫리면 다른 모든 것이 무의미하다.

### 동시성 테스트

소명 한도와 설비 점유는 **동시 요청을 주입해야** 의미가 있다. 순차 호출로는 잠금이 동작하는지 알 수 없다. AC 항목 중 동시성 관련은 여기서 처음 실행된다.

## 10. 코드 스타일

| 대상 | 도구 |
|---|---|
| Python | ruff (lint + format) |
| TypeScript | ESLint + Prettier |
| 타입 | Python은 타입 힌트 필수, TS는 `strict: true` |

**포매터 설정으로 논쟁하지 않는다.** 기본값을 쓰고 CI가 강제한다.

### 주석

- **복잡한 계산 로직에는 한글 주석을 단다.** 잔액 산출, 1차에너지 환산, 분개 규칙 적용, 배분 방법처럼 "왜 이렇게 계산하는가"가 코드만으로 안 보이는 곳이다.
- 자명한 코드에는 주석을 달지 않는다.
- **설계 문서 참조를 남긴다.** `# FS-014b: 잔액은 저장하지 않고 조회 시 산출한다`

## 12. 남은 결정

이 문서로 닫히지 않는 것 2건이다. FS-012 전에 정해야 한다.

| # | 항목 | 선택지 |
|---|---|---|
| **V-1** | 저장소 공개 여부와 시점 | 처음부터 공개 / 완성 후 공개 / 비공개 유지 |
| **V-2** | 배포 대상 | 클라우드 VM / PaaS / 배포하지 않고 로컬 시연 |

**V-1은 `docs/references/`와 얽혀 있다.** 사용자 제공 참고 사본이라 공개 저장소 업로드 대상이 아니라고 이미 표시돼 있다. 공개하려면 그 폴더를 분리하거나 이력에서 제거해야 하고, **커밋이 쌓인 뒤에 하면 이력 정리가 훨씬 어렵다.** 커밋이 1개인 지금이 결정하기 가장 쉬운 시점이다.

**V-2는 포트폴리오 가치에 직접 영향을 준다.** 평가자가 URL을 열어볼 수 있는 것과 "로컬에서 돌려보세요"는 다르다. 다만 게스트 체험이 있으므로 공개 배포 시 비용·남용 대비가 필요하다.

## 13. 이번 작업에서 하지 않은 것

- **코드 없음.** 스캐폴딩·디렉터리 생성도 하지 않았다.
- 라이브러리 버전 확정. 락파일에 맡긴다(2장).
- CI 파이프라인 구성. FS-012에서 다룬다.
- `tools/verify_ddl_matches_schema.py` 작성. FS-009에서 첫 마이그레이션과 함께 만든다.
- 시드 정의 갱신(FS-005g). 별도 작업이다.
- 실제 런타임 설치·호환성 검증. 버전은 공식 릴리스 일정으로 확인했을 뿐 **이 프로젝트 의존성과의 호환을 시험하지 않았다.**
- V-1·V-2 결정.

## 14. FS-017 로컬 실행·프론트 테스트 보완 (2026-09-24 승인)

이전 본문에는 서버 포트와 프론트 테스트 도구가 없었다. 사용자가 다음 규약을 승인했다.

| 대상 | 고정 규약 |
|---|---|
| 백엔드 개발 서버 | Uvicorn, `127.0.0.1:8000` |
| 프론트 개발 서버 | Vite, `http://localhost:5173`, strictPort |
| API 프록시 | Vite `/api` → `http://127.0.0.1:8000` (동일 출처 쿠키·CSRF) |
| PostgreSQL | 기존 Compose `127.0.0.1:55432`, PostgreSQL 18 |
| 컴포넌트·화면 테스트 | Vitest + Testing Library + jsdom, 검증 항목별 독립 테스트 |
| 브라우저 스모크 | Playwright Chromium + 실제 FS-016 API + 전용 `*_test` DB |
| 흐름 맵 계약 | `content/flow-map.schema.json` (JSON Schema draft-07), Ajv 검증 + 참조 무결성 테스트 |

로컬 브라우저는 `localhost`를 사용한다. Secure·HttpOnly 쿠키 속성을 개발용으로 완화하지 않는다. 원격 공개는 HTTPS가 필요하다. 정적 Markdown은 빌드에 포함하고 raw HTML은 렌더링하지 않는다. Vite 파일 접근은 프론트 폴더와 `content/`만 허용한다.

FS-017에서는 업무 화면을 구현하지 않는다. 사용자 승인에 따라 앱 런처와 흐름 맵의 업무 노드는 **기존 해당 솔루션 도움말**로 연결하고 UI에 업무 안내 연결임을 표시한다. FS-018~020에서 실제 업무 경로로 전환한다. SCM은 제목만 둔다.

패키지 버전은 락파일을 기준으로 하며 FS-017 보고서에 최초 추가 버전·이유를 기록한다. 실행 명령·작업 디렉터리·환경변수는 루트 README를 따른다.
