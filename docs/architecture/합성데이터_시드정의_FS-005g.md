## 1. 불변 규칙 (유지)

| 규칙 | 내용 |
|---|---|
| 재현성 | 난수를 쓰지 않는다. 같은 `seed_version`과 같은 T면 결과가 바이트 단위로 같다 |
| 시간축 | 절대 날짜 금지. 모든 시각은 **기준일 T로부터의 오프셋**. T = 세대 생성일의 Asia/Seoul 자정 = `core.data_generation.seed_date` |
| 저장·표시 | 저장 UTC, 표시 Asia/Seoul. 한국은 서머타임이 없어 T 이동 시 시각대가 보존된다 |
| 계측 해상도 | **전력 1시간 고정.** 가스·용수는 **1일 검침**. 1분 해상도(388,800행)와 15분 해상도는 거부 |
| 기간 | 업무 데이터 **T-60일 ~ T**, 계측·배분·FEMS 생산량 **T-30일 ~ T** |
| 복사 | 템플릿 세대 1개를 INSERT ... SELECT로 복사. 게스트마다 생성 로직을 돌리지 않는다 |
| 오류 시나리오 | 의도적으로 심는다(7장). 위반 데이터(한도 초과 등)는 심지 않는다. 사용자가 직접 시도해 거부를 확인한다 |

### 1.1 새로 추가하는 규칙 — 복사 이동에 안전한 값만 쓴다

템플릿은 T0 기준으로 만들어지고, 복사 시 모든 시각에 `(T − T0)`일을 더한다. 이 이동이 깨뜨리는 값은 생성 단계에서 금지한다.

| 금지 | 이유 | 대신 |
|---|---|---|
| **요일에 의존하는 값** (주말 부하 감소 등) | T−T0가 7의 배수가 아니면 요일이 어긋난다 | 시(hour-of-day)와 T 오프셋 일(day index)에만 의존. 이 공장은 3교대 연속 가동으로 정의한다 |
| **코드·키에 날짜 포함** (`LT-260915-01` 등) | 이동 후 코드와 시각이 어긋난다 | 일련번호만 사용(`LT-0001`). 예외는 1.2의 월 파생 코드 2종 |
| 월·연도에 의존하는 값의 **단순 이동** | 달력 경계는 일수 이동으로 보존되지 않는다 | 1.2의 규칙으로 **재계산** |

### 1.2 복사 시 재계산하는 달력 파생 컬럼

일수 이동이 아니라 T에서 다시 계산한다. FS-006b §3.3-5("월/ISO 주차도 T 기준으로 다시 계산")의 구체 목록이다.
M0 = `to_char(T,'YYYY-MM')`, M−k = M0에서 k개월 전. 연도·연월·주차는 모두 **TEXT**다.

| 컬럼 | 규칙 |
|---|---|
| `erp.sales_plan.target_month`, `mes.production_plan.target_month` | 전월 계획 = M−1, 당월 계획 = M0 |
| `erp.sales_plan.plan_code`, `mes.production_plan.plan_code` | `'SP-'` / `'PP-'` ‖ target_month |
| `mes.production_plan.sales_plan_code` | `'SP-'` ‖ target_month (ERP plan_code와 같은 문자열) |
| `mes.production_plan_line.target_week` | 해당 월 **1~21일 사이의 월요일 3개**의 ISO 주차(`'IYYY-"W"IW'`). 1~21일에는 월요일이 정확히 3개이며 연말 주차가 다음 해로 넘어가는 경우가 생기지 않는다. 라인은 주 순번(1·2·3)을 템플릿에서 보존해 재계산한다 |
| `fems.energy_factor.effective_year` | `to_char(T,'YYYY')`와 그 전년. 2개 연도분을 심는다(T가 1~2월이면 T−60일이 전년도에 걸친다) |
| `fems.tariff.effective_from/to` | 5.4 표의 M−k 규칙 |
| `erp.partner_item_price.effective_from/to` | 3.3 표의 M−k 규칙 |
| `fems.energy_target.target_month` | M−1, M0 |
| `fems.energy_baseline.period_from/to` | 5.5 표의 M−k 규칙 |

**알려진 효과.** 계획 주차는 달력에, 실행 시각은 T 오프셋에 묶인다. T가 월초이면 당월 계획 라인에 연결된 지시가 전월 날짜에 실행된 것으로 보인다. 작업지시는 계획 라인에 **순번으로** 연결하며, FS-006b §5는 날짜 포함 관계를 요구하지 않는다(수량·품목·단위만 검사). 결함이 아니라 달력 기반 계획과 상대 시간축을 같이 쓸 때의 한계로 기록한다.

## 2. 코드 사전 — 세 스키마 공통 코드

FS-013 §2 대응 1("표준 코드 체계 문서를 두고 시드가 동일 코드를 각 스키마에 심는다")의 실체다.
**생성기는 `seed/codebook`(형식은 FS-015에서 결정) 한 곳만 읽어 세 스키마에 기록한다.** 스키마별로 코드를 따로 적지 않는다.
업무 스키마 간 FK는 없으므로 일치를 DB가 보장하지 않는다. 생성기 검증(9장)이 보장한다.

| 코드 종류 | 값 | mes | erp | fems |
|---|---|:--:|:--:|:--:|
| 사업장 | `S01` 제1공장 | site | — | site |
| 공간 | `L-INJ` 사출동, `L-ASM` 조립동, `L-INS` 검사실 | location | — | location |
| 공간(FEMS 전용) | `L-UTL` 유틸리티실 | — | — | location |
| 설비 | `INJ-01~03` 사출기, `ASM-01~03` 조립기, `INS-01~02` 검사기 | equipment | — | equipment |
| 품목 | 2.1 표 | item | item | production_record·energy_baseline의 `item_code` |
| 판매계획 | `SP-<YYYY-MM>` | production_plan.`sales_plan_code` | sales_plan.`plan_code` | — |
| 패킹 번호 | `BX-0001~0030`, `PL-0001~0006` | packing_unit.`packing_no` | shipment_line.`packing_no` | — |
| LOT·공정 | `LT-0001~0026` / `INJ`·`ASM`·`INS` | lot·process | — | production_record.`source_key` 안의 문자열 |

**명칭도 같게 심는다.** 코드만 같고 이름이 다르면 화면을 오가는 평가자가 다른 품목으로 읽는다.
실제 회사·제품·고객명은 쓰지 않는다. 아래 명칭은 전부 합성이다.

### 4.2.1 상태 부수 값 (S-12 확인 반영)

`mes.work_order`와 `mes.lot`은 상태에 따라 사유·시각을 CHECK로 강제한다. 비워 두면 삽입이 실패하므로 값을 고정한다.

| 컬럼 | 규칙 | 근거 CHECK |
|---|---|---|
| `released_at` | 첫 공정 시작 일 −1일 09:00. released·in_progress·completed에 필수 | 상태별 필수 |
| `started_at` | 첫 공정 시작 시각(첫날 00:00). **released·cancelled는 NULL** | in_progress·completed에 필수 |
| `completed_at` | 마지막 실적 확정 시각(마지막 날 23:30) | `(status='completed') = (completed_at IS NOT NULL)`, `completed_at >= started_at` |
| `completion_reason` | completed면 `normal`, **W06은 `all_defective`**. 그 외 NULL | `(status='completed') = (completion_reason IS NOT NULL)`, 허용값 normal/all_defective |
| `cancel_reason` | X01만 `계획 변경으로 발행 전 취소`. 그 외 NULL | cancelled면 비공백 필수 |

`mes.lot`도 같은 `completion_reason` 규칙을 따른다. W06의 LOT `LT-0018`만 `all_defective`다.
X01은 draft에서 취소했으므로 `released_at`·`started_at`·`completed_at`이 모두 NULL이다. 취소 상태는 `released_at`을 요구하지 않는다.

**실행의 상태 코드는 지시와 다르다.** `mes.operation_execution`은 `running`/`completed` 두 값뿐이며 `in_progress`가 없다. 진행 중인 W11·W12 조립 실행은 `running` + `ended_at = NULL`이다.

### 4.5 실적 산식

불량률은 품목·공정별 고정값이다. `불량 = 반올림(투입 × 불량률)`(0.5 올림), `양품 = 투입 − 불량`, `산출 = 투입`. 다음 공정 투입 = 앞 공정 양품.

| 품목 | 사출 | 조립 | 검사 | LOT 최종 양품 |
|---|---:|---:|---:|---:|
| C100 (2,000) | 1.5% | 1.0% | 0.5% | 1,970 → 1,950 → **1,940** |
| C200 (2,000) | 2.0% | 1.5% | 0.5% | 1,960 → 1,931 → **1,921** |
| T300 (1,000) | 1.0% | 0.5% | 0.3% | 990 → 985 → **982** |

W06 검사: 투입 985 → 양품 0, 불량 985.

**불량이 있으면 사유가 반드시 있어야 한다.** `mes.operation_result`에 `defect_qty = 0 OR defect_reason 존재` CHECK가 있다(S-6 확인). 산식상 62개 실적의 거의 전부에 불량이 생기므로 공정별 고정 사유를 둔다. 자유 문자열 varchar(300)이며 별도 CHECK는 없다.

| 공정 | `defect_reason` |
|---|---|
| INJ 사출 | `SHORT_SHOT 미충전` |
| ASM 조립 | `PIN_MISALIGN 핀 정렬 불량` |
| INS 검사 | `CONTACT_FAIL 접촉 불량` |
| INS 검사 (W06만) | `MOLD_DAMAGE 금형 손상에 의한 치수 불량` |

불량 0인 실적은 `defect_reason = NULL`이다. 이 목록은 QMS 도입 전까지 MES 내부 고정 목록이다(FS-005b §8 유지).

같은 테이블에 `input_qty = output_qty AND output_qty = good_qty + defect_qty`, `input_qty > 0`, EA 정수 CHECK가 있다. 위 산식은 세 조건을 모두 만족한다.

### 4.6 자재 투입

- 투입 시각 = 실행 시작 시각. 사출 실행마다 `RM-PBT`, 조립 실행마다 `RM-PIN` 1행.

- `bom_version_id` = 지시의 BOM. `material_lot_id` = **NULL**(원자재 LOT은 WMS 소유라 없다).
- 행 수: 사출 실행 24 + 조립 실행 22(실행 중 2 포함) = **46**. 단위는 PBT `KG`, PIN `EA`이며 `issued_qty > 0` CHECK를 만족한다.
- **확정 실적이 있는 실행에는 투입을 추가·변경할 수 없다**는 SERVICE 정책이 있다(S-7). 시드는 직접 쓰기라 막히지 않지만, 생성기는 투입→실적 순서로 기록해 서비스 규칙과 어긋나지 않게 한다.
- NULL `material_lot_id`는 UNIQUE가 중복을 막지 못한다(현황 6장 제약). 생성기는 (실행, 자재) 1행을 보장한다.

### 5.2 계측값 산식

**전력(설비, 1시간).** 해당 시간에 그 설비의 MES 실행이 진행 중이면 가동 부하, 아니면 대기 부하. 판정은 `started_at ≤ 시간 시작 < COALESCE(ended_at, T)`.

| 설비 | 가동 kWh/h | 대기 kWh/h |
|---|---:|---:|
| 사출기 | 45.0 | 3.0 |
| 조립기 | 12.0 | 1.5 |
| 검사기 | 6.0 | 0.8 |

가동 부하에는 교대 교체 시각(06·14·22시)에 계수 0.85를 곱한다. 대기 부하는 계수를 적용하지 않는다.

**전력(수전).** Σ설비 실제값 + 공용 부하(08~19시 25.0, 그 외 15.0 kWh/h).
결측 시간에도 수전은 설비의 **실제 소비를 포함한다.** 하위 계량기만 고장 난 상황이므로 그날 미계측 잔여가 커진다. 의도한 현상이다.

**가스(1일).** `45 + 5 × (|d| mod 3)` Nm3 → 45·50·55 반복. 보일러 기저 부하이며 생산과 무관하다. 요일 의존은 1.1에 따라 금지한다.

**용수(1일).** `8 + 6 × (그날 가동한 사출기 대수)` m3. 8은 공용, 6은 사출기 1대의 금형 냉각수다.

**저장 형식.** 모든 값은 구간 소비량이며 `period_start` = 구간 시작, `observed_at` = 구간 끝이다. `period_start < observed_at` CHECK와 맞는다(S-2 확인). 소수 셋째 자리 반올림. `source_key` = `<채널코드>:H<시간오프셋>` 또는 `:D<일오프셋>`(날짜 없음, 1.1). `input_revision` = 1. 품질은 `valid`다.

**결측 표현 (S-1 확인 결과).** `value`는 NOT NULL이고 `value >= 0` CHECK가 있으며, `quality` 허용값은 `valid`/`estimated`/`reset`/`invalid` 4종이다. **결측 전용 코드도 NULL 값도 쓸 수 없다.**
따라서 결측 6행은 `value = 0` + `quality = 'invalid'`로 저장한다. 상위 호환 규칙을 함께 둔다.

- **집계는 `quality = 'invalid'` 행을 제외한다.** 제외하지 않으면 0이 소비량 0으로 조용히 합산된다. 이것이 이 선택의 유일한 위험이다.
- 화면은 `invalid` 행을 값 없음(결측)으로 표시하고 숫자 0을 보이지 않는다(F-02).
- **한계를 명시한다.** `invalid`는 "측정값 신뢰 불가"이지 "측정 없음"이 아니다. 두 상황을 구분해야 한다면 `quality` CHECK에 `missing`을 추가하는 스키마 변경이 필요하다(10.1 D-3).
- 시드는 보간하지 않으므로 `estimated`를 쓰지 않는다. `reset`(계기 교체·롤오버)도 이번 시드에는 없다.

### 5.3 배분

| 대상 | 방법(제안 키) | 행 수 | 규칙 |
|---|---|---:|---|
| 전력 → 설비 8대 | `DIRECT_METER` 전용 계량기 직접 귀속 | 8 × 30일 = **240** | 하루 24개 시간값의 합. 비가동일도 대기 소비로 행을 둔다 |
| 용수 → 사출기 | `RUNTIME_SHARE` 가동시간 비례 | 사출기 가동일 합계 = **36** | 그날 `용수 − 8`을 가동 사출기에 가동시간 비례 배분. 공용 8 m3는 배분하지 않는다 |
| 가스 | 배분 없음 | 0 | 보일러 공용 부하다. 설비별 원단위에 넣지 않는다 |

구간은 [d일 00:00, d+1일 00:00). `method_version` = 1, `input_revision` = 1, `quality` = `valid`. `basis`(jsonb, NOT NULL)에 합산 시간 수·가동시간·결측 시간 수를 담는다.
`method_key`는 varchar(40) 자유 문자열이며 CHECK가 없다(S-3 확인). 위 두 키를 사용한다.
**ASM-02 d−17 배분은 결측 6시간을 보간하지 않는다.** 18시간 합으로 두고 `quality = 'estimated'`로 표시하며 `basis.missing_hours = 6`을 남긴다.
배분 품질 허용값은 `valid`/`estimated`/`invalid` 3종이다(S-3). **"부분 집계"를 뜻하는 코드는 없다.** 보간을 하지 않으므로 `estimated`는 정확한 말이 아니지만, `invalid`로 두면 실제 포착된 18시간치까지 분석에서 사라진다. 둘 중 덜 해로운 쪽을 고른 것이며, 기록으로 남긴다.

### 9.2 복사 성능에 대한 판단 (측정 전)

- 행 수 자체는 병목이 아닐 것으로 **추정**한다. 측정값이 아니며 FS-015에서 실측한다.
- **ID 재매핑은 부모 테이블에만 필요하다.** 자식이 참조하는 테이블의 행은 약 350행이다(mes 약 210 · erp 약 100 · fems 약 40). `energy_reading`·`energy_allocation`·`production_record`·`material_issue` 등 leaf 테이블은 매핑 없이 새 id로 삽입하고 부모 매핑과 조인만 한다.
- id가 `GENERATED ALWAYS AS IDENTITY`다. 매핑표로 새 id를 미리 발급해 넣으려면 `OVERRIDING SYSTEM VALUE`가 필요하다. leaf 테이블은 id를 생략해 자동 발급한다. FS-015 구현 지침으로 넘긴다.
- **복사를 PL/pgSQL 함수 1회 호출로 구현하면 `statement_timeout`이 복사 전체에 걸린다.** 테이블별 문장이면 문장마다 걸린다. 선택은 FS-015에서 실측과 함께 한다.
- **guest_pool 전역 잠금으로 생성이 직렬화된다.** 동시 진입 대기 시간은 대기 인원 × 1건 복사 시간이다. 2초 목표는 **1건 기준**이며 동시 진입 기준이 아니다. 대기 문장의 timeout 처리는 FS-006b의 대기 안내로 연결한다.

덤프 4개(`fs005g_check2_*.txt`)는 `.gitignore`에 등록된 파생 산출물이다. schema.json에서 언제든 재생성할 수 있다.

### 10.5 남은 한계

- **본문은 이제 CHECK가 요구하는 사유·시각·코드를 모두 지정한다.** 단, 이는 덤프와의 정적 대조다. `created_at`·통화·명세 행 번호 등 문서가 일일이 적지 않은 NOT NULL 컬럼은 생성기가 아래 일반 규칙으로 채운다.

| 테이블 종류 | `created_at` 규칙 |
|---|---|
| 발생·실행·계측 행 | `occurred_at` → `started_at` → `observed_at` → `period_start` 순서로 처음 존재하는 값 |
| 입고·출하·매출·이력·소명·공개·확정 행 | `issued_at` → `received_at` → `shipped_at` → `recognized_at` → `changed_at` → `applied_at` → `released_at` → `published_at` → `confirmed_at` → `completed_at` 순서로 처음 존재하는 값 |
| 일자만 있는 업무 행 | `quoted_on` → `ordered_on` → `invoice_date` → `received_on` → `paid_on` → `issued_on` 순서의 해당 일자 09:00 Asia/Seoul |
| 명세·연결·자식 행 | 자체 업무 시각을 먼저 적용한 뒤 모든 업무 FK 부모의 `created_at` 이상이 되도록 조정 |
| 마스터·기준정보·자체 업무 시각이 없는 행 | 데이터 기간 시작 d−90보다 앞선 **d−91 09:00 Asia/Seoul** |
| core workspace·generation | 마스터와 같은 d−91 09:00. generation 활성 시각은 기존 T 기준을 유지 |

추가 불변 규칙: `confirmed_at`이 있으면 `created_at ≤ confirmed_at`, `cancelled_at`이 있으면 `created_at ≤ cancelled_at`, 업무 FK 자식은 `created_at ≥ 부모.created_at`이다. 복사 시 모든 `created_at`은 다른 시각과 같이 T−T0만큼 이동한다. 통화는 KRW, 명세·규칙 행 번호는 부모별 1부터 연속 부여한다.
- **실제 통과 여부는 FS-015에서 실제 INSERT로만 확인된다.** 7,469행을 PostgreSQL에 넣어 CHECK·FK·UK가 전부 통과하는 것이 완료 조건이다.

## 11. 버전 관리

- 이 정의의 `seed_version`: **`sv-20260924-2`**. 날짜는 정의 작성일이며 T가 아니다.
- `sv-20260924-1`은 FS-015b 이력이다. FS-018e에서 에너지 목표 비율이 95% 고정에서 비율표로 바뀌어 같은 T의 결과 바이트가 달라지므로 버전을 올렸다.
- `sv-20260923-1`은 FS-015 최초 구현 이력이다. FS-015b에서 `created_at` 값이 바뀌어 같은 T의 결과 바이트가 달라지므로 11장 규칙에 따라 버전을 올렸다.
- 시드 구성이 바뀌면 버전을 올린다. 기존 세대는 그대로 두고 새 세대부터 적용한다.

- 이 문서와 `seed/` 구성 파일은 같은 작업에서 함께 갱신한다.
