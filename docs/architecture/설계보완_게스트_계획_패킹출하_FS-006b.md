# FS-006b 게스트·계획·패킹·출하 설계 보완

작성: 2026-09-21. 상태: 후속 진행 요청에 따라 FS-007b 설계 반영 완료. 제품 구현·DB 시험 없음.
이 문서는 FS-006/006a 및 FS-005a/005b와 충돌하는 아래 항목의 대체안이다. 새로운 제한과 보존 정책은 사용자 확인 후 기준으로 채택한다. 변경 없는 기존 계약은 유지한다.
**2026-09-21: 메타데이터/Excel v0.3.0과 모듈 ERD에 반영했다. 실제 DB는 미적용이다.** 전체 설계 확인 전 FS-009 착수 금지.

## 1. 이번 결정의 요약

| 쟁점 | 제안 |
|---|---|
| 게스트 주체 | 사용자 계정을 만들지 않고 MEMBER/GUEST/SYSTEM 주체를 구분 |
| 게스트 회수 | 만료된 공간만 물리 회수, 보존 운영 기록은 FK 분리 후 유지 |
| 동시 게스트 상한 | 생성/회수 공통 전역 잠금 안에서 20개 상한을 검사 |
| 템플릿 복사 | 새 ID 발급 및 모든 업무 FK 재매핑, 글로벌 콘텐츠만 기존 참조 유지 |
| 계획과 지시 | 생산계획 라인 1개 → 작업지시 여러 개, 각 지시는 계획 라인 1개 필수 |
| 패킹 | 단일 품목 BOX → 동일 품목 PALLET, LOT 혼합은 같은 품목·단위에 한해 허용 |
| 입고/출하 | PALLET 단위만, 지시별 전량 1회 출하. 수주는 여러 지시로 분할 가능 |
| 취소 | 미발행 작업지시와 미출하 출하지시만 취소. 확정 입고/출하 역처리는 첫 공개 제외 |

예: 수주 1,000 EA를 600/400 EA의 두 출하지시로 나누는 것은 허용한다. 600 EA 지시에서 400만 확정하는 것은 거부한다. 필요하면 미출하 지시를 취소하고 수량에 맞게 다시 만든다. 제한은 화면에 먼저 설명한다.

## 2. 요청·감사 주체

### 2.1 인증 문맥

- MEMBER: 인증된 사용자 + 본인 workspace. 사용자 ID를 클라이언트 입력으로 신뢰하지 않는다.
- GUEST: 불투명 세션 쿠키의 해시로 찾은 본인 workspace. 서버가 만료와 workspace_kind를 확인한다. 관리자 권한 없음.
- SYSTEM: 허용된 내부 실행 주체와 실행 ID. 게스트를 SYSTEM으로 위장하지 않는다.
- 변경 요청은 회원/게스트 모두 세션·CSRF 검증을 거친다. 주체 종류는 서버가 만든다.

### 2.2 요청 결과와 감사

`mes.request_receipt`는 MES 이름이지만 현재 여러 업무 TX에서 사용하기로 한 기록이다. 모듈 공통 기능이므로 FS-007b에서 **core.request_receipt로 이동**하고 관련 설명·관계를 갱신한다. 세대별 업무 데이터라는 수명은 유지한다.

제안 필드: actor_kind, nullable actor_user_id, actor_key. MEMBER는 user FK 필수, GUEST/SYSTEM은 user FK 금지. actor_key는 내부 안정 식별자이며 쿠키/세션 토큰/그 해시를 저장하지 않는다. GUEST는 공간별 별도 UUID, SYSTEM은 허용된 서비스 식별자를 사용한다.

멱등 키: (S, actor_kind, actor_key, operation_key, request_key). 동일 키·동일 본문은 기존 결과 반환, 다른 본문은 충돌. 다른 주체는 기존 결과를 조회할 수 없다. 상태 재조회에도 인증·공간·세대 검증을 적용한다.

감사도 동일한 actor_kind/key 규약으로 전환한다. 기존 user/system XOR CHECK는 대체한다. actor_key와 FK가 같은 사용자/공간을 가리키는지 서버가 검사한다. 회원 계정 삭제 정책은 별도 범위이며 이번 작업에서 약속하지 않는다.

## 3. 게스트 생성·상한·복사

### 3.1 전역 경쟁 제어

초기 동시 상한은 살아 있는 GUEST workspace 20개다. 아직 삭제되지 않은 만료 공간도 자원 상한에 포함한다. MEMBER/TEMPLATE는 제외한다.

생성과 회수는 동일한 DB 트랜잭션 advisory lock `guest_pool`을 가장 먼저 획득한다. 그 뒤 workspace → 세대 → 업무 순으로 잠근다. 일반 업무는 guest_pool을 획득하지 않는다. workspace를 먼저 잠근 경로가 나중에 guest_pool을 요청하는 것을 금지한다.

생성은 전역 잠금 → 개수 재조회 → 공간 생성/복사/검증 → commit까지 잠금을 유지한다. 첫 버전은 생성이 직렬화되는 비용을 수용하며 2초 목표와 동시 진입을 실측한다. 상한 부족 시 생성 트랜잭션은 종료하고 별도의 회수 작업을 호출한 후 1회만 재시도한다. 유효 공간을 강제로 회수하지 않는다. 여전히 가득 차면 대기 안내와 읽기 전용 전체 맵을 제공한다.

정리 실행은 날짜당 단 한 번이 아니라 시간 슬롯+실행 ID로 구분한다. 같은 실행 ID의 재시도는 중복 효과 없이 처리하고 이후 슬롯은 새로 만료된 공간을 처리할 수 있다. 정기 실행과 상한 도달 시 회수는 공통 서비스 계약을 사용한다.

### 3.2 템플릿 소유와 공개

workspace_kind에 내부용 TEMPLATE를 제안한다. owner_user_id/guest_session_key/expires_at은 NULL, 일반 사용자 API 접근 및 주간 초기화 대상에서 제외한다. 게스트와 회원만 클라이언트 공간으로 노출한다.

템플릿은 seed_version별 검증된 불변 세대로 게시한다. 복사 중 교체/삭제하지 않도록 해당 템플릿 세대를 공유 잠금으로 고정한다. 관리 갱신은 새 템플릿을 게시하고 기존 복사가 끝난 뒤 구버전을 정리한다. 템플릿 작업은 일반 사용자 공간 잠금과 역순으로 결합하지 않는다. 동일 템플릿이 운영 체험 공간으로 선택되는 것을 차단한다.

### 3.3 단일 트랜잭션 복사 계약

1. 게스트 새 공간/새 세대 생성. 템플릿 seed_version과 기준일 T를 고정.
2. 임시 매핑에 각 업무 테이블의 old_id → new_id를 전부 준비한다. 신규 ID를 시퀀스로 예약한다면 IDENTITY 명시 삽입 정책도 DDL 설계에 포함한다. rollback 시 시퀀스 번호 공백은 정상이다.
3. metadata FK 의존 순서에 따라 복사한다. workspace_id/generation_id는 새 S로, 업무 FK는 대응 매핑으로 치환한다. 글로벌 게시 콘텐츠 FK는 기존 대상을 유지한다.
4. 자기참조는 루트부터 삽입: PALLET→BOX, 계측기 부모→자식. 주기나 매핑 누락이 있으면 실패한다. FK를 끄거나 원본 ID를 임시로 연결하지 않는다.
5. 시각뿐 아니라 월/ISO 주차도 T 기준으로 다시 계산하고 계획 기간·참조 관계를 검증한다.
6. 계정·모듈 설정·학습 기록·요청 결과·감사·작업 실행은 복사하지 않는다. 기본 모듈 설정은 별도 기본값으로 생성한다. 합성 과거 업무에는 seed 출처를 표시해 사용자 실행 감사로 위장하지 않는다.
7. 수량·금액·공정 상태·포장/출하 관계·신규 S 참조와 행 수를 검증한 후 active 전환. 실패 시 전체 rollback.

회원 최초 생성과 수동/예약 초기화도 같은 복사 함수를 사용하되 공간별 초기화 잠금/전환 계약을 따른다. 템플릿 준비 정책과 사용자 데이터 접근 권한은 분리한다. 빈 단계별 개발 DB에는 해당 migration 단계에 맞는 축소 seed_version을 사용하며 완성 시드와 혼동하지 않는다.

## 4. 회수와 보존

### 4.1 회원 구세대 정리

활성 세대는 삭제하지 않는다. 공간 잠금을 확보해 대상이 retired인지 재확인하고 자식부터 업무 행만 정리한다. 보존 학습/감사/계정/설정/세대 메타는 유지한다. 필요한 배치마다 공간 잠금을 재획득하고 상태를 재검증한다. 기존 ‘공간 잠금 없이 정리’ 설명은 채택하지 않는다.

세대별 삭제 집합에는 request_receipt, mes.learning_binding, fems.energy_allocation/readings, 예약 BEMS 관측, 모든 ERP/MES 업무와 기준정보를 포함한다. 삭제 순서는 메타데이터 FK 그래프로 계산하며 한글 요약 목록만 하드코딩하지 않는다. 자기참조는 자식 먼저 삭제한다. 바깥의 보존 행에서 삭제 대상 업무를 참조하는 FK가 발견되면 작업을 중단하고 설계 오류로 보고한다.

### 4.2 게스트 전체 회수

선택 후보를 읽은 뒤, **guest_pool → workspace 잠금 안에서 expires_at 경과를 다시 검사**한다. lock 이전 조회 결과만으로 삭제하지 않는다. 신규 업무도 공간 잠금 후 서버 현재 시각으로 만료를 검사한다. 잠금 전에 시작한 HTTP 요청이라는 이유로 만료 후 실행을 허용하지 않는다.

회수 순서:
1. 게스트 업무 전체 세대의 업무 행을 FK 순서로 제거. live learning binding이 학습/업무 양쪽을 참조하므로 먼저 제거.
2. 게스트 학습 답안/단계/시도, 화면 설정/모듈 설정 제거. 회원 보존 정책과 구별.
3. 보존하는 감사·job의 대상 FK를 분리하고 비밀 없는 공간 식별 스냅샷을 남김.
4. workspace.active_generation_id를 NULL로 해제하고 해당 공간의 세대 메타를 삭제.
5. workspace 삭제 후 완료 기록을 남기고 commit. 공간 1개 단위 원자성. 실패 공간은 rollback하고 다음 공간은 별도 트랜잭션으로 처리.

보존 기록 설계 제안: core.job_run.workspace_id/target_generation_id와 audit_event.workspace_id를 nullable로 확장하고 대상 스냅샷 및 scope_kind를 둔다. 전역 guest_cleanup job은 scope_kind=GLOBAL이며 workspace FK가 없다. 삭제 시 먼저 명시적으로 분리하고 RESTRICT는 유지한다. job 관련 감사 FK는 실제 참조 순서에 따라 정리한다. FS-007b에서 모든 제약/보존 순서를 검증한다.

운영 기록의 기본 보존 제안은 30일이며 일반 사용자가 조회할 수 없다. 게스트 쿠키/해시/세션은 보존 기록에 남기지 않는다. 30일 후 감사 등 자식부터 운영 로그 전용 정리 경로로 삭제한다. 게스트 개인정보나 상세 실습 답안을 운영 로그에 복제하지 않는다.

### 4.3 AC-63 정정

업무가 잠금을 먼저 얻고 유효 시간 내 검사·commit한 뒤 회수가 실행되면 **업무와 회수 모두 성공할 수 있다.** 회수가 먼저면 후속 업무는 만료/접근 불가로 종료한다. 핵심 조건은 ‘회수 후 쓰기 성공 금지’다. 요청 성공 후 만료되어 결과가 사라지는 경우 UI는 만료를 안내하며 생산 실패라고 표시하지 않는다.

## 5. 생산계획 → 작업지시

관계: 확정 판매계획 → 생산계획 → 품목/주차별 생산계획 라인 → 여러 작업지시. 한 지시는 한 생산계획 라인에 속한다.

`mes.work_order.production_plan_line_id`를 필수로 추가하는 안이다. 같은 S·품목·단위를 복합 관계 또는 이에 준하는 명시적 서비스/DB 검증으로 일치시킨다. 확정 생산계획에서만 생성할 수 있다.

계획 라인 잠금 후 **취소되지 않은 지시 계획수량 합계 + 새 지시수량 ≤ 생산계획 라인 수량**을 검사한다. draft도 배정 수량에 포함한다. draft 변경은 기존 자신을 합계에서 제외하고 재계산하며, draft 취소는 배정량을 반환한다. 발행 이후 계획 라인/품목/수량 변경은 금지한다.

예: 계획 1,000에서 지시 600+400 가능, 600+500은 차단. 400 draft 취소 후 새 400 생성 가능. 무계획 지시는 첫 공개 범위에 두지 않는다. C1은 seed의 잔여 있는 확정 계획 라인을 선택해 지시 등록부터 실습하며, 기존 released 지시는 별도 ‘이어하기 예시’다.

조회는 계획수량 / 지시 배정량 / 최종 양품 / 누적 불량 / 아직 지시하지 않은 수량을 구분한다. 공정별 양품을 합산해 계획 실적으로 쓰지 않는다. 재고를 고려하는 고급 MRP·자재 소요량 전개는 포함하지 않는다.

## 6. 패킹·입고 계약

- 최종 공정까지 완료된 LOT의 최종 양품만 패킹 가능. 중간 공정 실적이나 all_defective LOT은 거부한다.
- packing_member는 BOX에만 연결한다. PALLET 수량은 하위 BOX의 합계이며 LOT 수량을 PALLET에 중복 기록하지 않는다.
- BOX는 동일 품목·단위 LOT만 포함. PALLET도 동일 품목·단위 BOX만 포함. BOX에는 부모 PALLET 0~1개, PALLET에는 부모 없음.
- open BOX만 수량 수정 가능. 수정 후 전체 LOT의 패킹 합계가 최종 양품 이하인지 잠금 안에서 대사한다. 담을 잔여가 없으면 차단한다.
- BOX 닫기는 비어 있지 않을 때 가능. closed BOX만 open PALLET에 편입할 수 있다. BOX 내용은 불변이지만 open PALLET의 BOX 연결/해제는 허용한다. 이동할 때 이전·새 PALLET 모두 잠근다.
- PALLET 닫기는 모든 BOX가 closed이며 비어 있지 않을 때 가능. closed PALLET의 구성/하위 내용 변경은 금지한다.
- 입고/출하 대상은 PALLET만이다. BOX 단독 입고/출하는 거부한다. 입고 시 PALLET closed→received, 하위 BOX는 closed로 유지하고 화면에는 부모에서 계산한 입고 상태를 표시한다.
- 입고 후 포장 해체·입고 취소·재입고는 첫 공개에서 제외한다. 기존 TX-11의 ‘미출하 입고 취소 가능’ 문장은 대체한다. 예시 재체험은 명시적 공간 초기화로 제공한다.
- 바코드는 LOT/BOX/PALLET 표시번호 출력. 스캔도 현재 S에서 조회하고 일치하지 않으면 거부. 재출력은 업무 수량이나 상태를 변경하지 않는다.

잠금 순서: 공간 → 세대 → 계획 → 지시/LOT/실행 → PALLET(id 순) → BOX(id 순) → 구성/입고 → ERP → 학습 → 결과/감사. LOT 수량을 바꾸는 모든 패킹 경로는 LOT부터 고정한다. 상위 변경 대상은 잠금 후 다시 확인한다. 공간 잠금 완화는 별도 재설계이며 현재 필수 시험에서 임의로 끄지 않는다.

## 7. ERP 지시·출하·매출 계약

### 7.1 출하지시

수주 헤더/라인과 품목·수량·단가는 최초 출하지시 생성 후 변경 금지한다. 지시 명세는 반드시 그 지시 헤더의 수주에 속한다. 복합 FK 보강과 서비스 검사 양쪽으로 보호한다.

수주 라인 잠금 후 취소되지 않은 모든 출하지시 누계가 수주수량 이하인지 검증한다. 지시 상태 open→shipped 또는 open→cancelled. 취소 사유 필수, 취소 지시는 출하 불가. shipped 지시 취소/변경은 지원하지 않는다. 수주 상태는 유효 지시가 없으면 open, 유효 지시가 있고 출하 누계가 수주보다 작으면 shipping, 모든 수주 라인의 출하 누계가 일치하면 closed다. 상태 변경은 관련 수량 변경과 같은 트랜잭션이다.

### 7.2 출하 확정 TX-08 대체

공간/세대/주체 검사 → 멱등 요청 확인 → 선택 PALLET 잠금 → 수주/라인 → 지시/라인 잠금 → 아래 전체 검사 → 출하/명세 → PALLET shipped → 지시 shipped → 수주 상태 재계산 → TX-09 매출 → 감사/요청 결과 → commit.

필수 검사:
1. 모든 명세가 동일 출하지시 헤더에 속하고 지시가 open.
2. 각 선택 단위는 같은 S의 received PALLET, 유효 입고 1건, 출하 이력 없음.
3. PALLET 내용의 품목/단위가 연결 수주 라인과 일치.
4. 각 shipment_line.shipped_qty는 PALLET 전체 수량과 일치(서버 산출). 클라이언트 수량은 대사만 한다.
5. 지시의 **모든 라인**에 대해 선택 PALLET 수량 합계 = 지시수량. 일부 라인 누락이나 부족/초과 모두 거부.
6. 출하 명세↔지시 명세↔수주 명세의 소속이 일치하고 파트너는 헤더에서 도출.

지시당 출하 1건, PALLET당 출하 1건 UNIQUE 유지. 단일 품목 PALLET이므로 한 PALLET을 여러 주문 라인에 나누지 않는다. 같은 요청 재시도는 기존 성공을 반환하고 다른 키의 중복 확정은 거부한다.

### 7.3 매출 TX-09

출하와 같은 트랜잭션의 단일 매출 기록을 유지한다. 교육용 합성 금액 정책은 개발 방식/ERP 명세에서 통화·세율·반올림을 하나로 확정한다. 운영 회계/세무 기준의 구현이라고 표현하지 않는다. 매출 실패 시 출하와 모든 상태 변경도 rollback한다.

## 10. 검토 상태와 다음 작업

검토안에는 업무 제한을 명시하고 식별/수량/복사/삭제의 누락을 보완했다. 문서의 ID 유일성·참조 경로·필수 절 존재를 정적으로 검사한다. 실제 DB/브라우저/보안/성능 검증 결과는 없으며 위 AC는 테스트 명세다.
