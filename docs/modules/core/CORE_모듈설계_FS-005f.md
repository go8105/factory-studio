# FS-005f CORE 모듈 공통 설계서

작성일: 2026-09-21. 상태: 설계 확정. 신규 제안 없음.
기준: [공통 ERD FS-005](../../architecture/공통ERD_데이터관계_FS-005.md), [FS-005d 모듈·하위 모듈 구조](../../architecture/모듈_하위모듈_구조_FS-005d.md).
성격: core는 화면을 가진 업무 모듈이 아니라 **다른 모듈이 서 있는 바닥**이다. 그 역할과 경계를 정의한다.

---

## 1. core는 모듈이 아니다

MES·ERP·FEMS는 앱 런처에 아이콘이 있는 업무 솔루션이다. **core는 아이콘이 없다.**

core가 하는 일은 둘이다.

1. **모든 모듈이 공유하는 기준정보를 한 벌로 소유한다.** 품목·설비·작업장·계측기를 모듈마다 복제하지 않기 위해서다.
2. **모듈이 돌아갈 토대를 제공한다.** 계정·권한·체험 공간·세대·감사·작업 실행.

그래서 core에는 "core 화면"이 없다. core 테이블은 **각 모듈의 기준정보 화면에 참조로 나타난다.**

## 2. 하위 모듈

| 하위 모듈 | 소유 테이블 | 성격 |
|---|---|---|
| `account` 계정·권한 | 사용자, 세션, 역할, 사용자-역할 | 토대 |
| `workspace` 공간·세대 | 체험 공간, 데이터 세대, 모듈 설정, 대시보드 배치 | 토대 |
| `factory_master` 공장 기준정보 | 사업장, 작업장, 설비 | **공유 마스터** |
| `item_master` 품목 기준정보 | 품목, 단위 환산 | **공유 마스터** |
| `metering_master` 계측 기준정보 | 계측기, 계측 채널, 에너지원 | **공유 마스터** |
| `ops` 운영 | 작업 실행, 감사 이벤트, 요청 결과 | 토대 |

소유 19개.

## 3. 공유 마스터를 누가 쓰는가

| 마스터 | 참조하는 모듈 |
|---|---|
| 사업장 | 전부 |
| 작업장·설비 | MES(공정·실행), FEMS(배분·목표) |
| 품목 | MES(경로·계획·지시), ERP(견적·수주·단가), FEMS(원단위 기준선) |
| 계측기·채널·에너지원 | FEMS, BEMS |

**계측 기준정보를 FEMS가 아니라 core에 둔 이유**는 BEMS도 같은 계측기를 쓰기 때문이다. FEMS에 두면 BEMS가 FEMS 테이블을 참조하게 되어 모듈 경계가 깨진다.

## 4. 모듈 경계에서 core의 위치

[FS-005d 3장](../../architecture/모듈_하위모듈_구조_FS-005d.md)의 규칙에서 core는 **필수 참조가 허용되는 유일한 대상**이다.

- `factory_master` · `item_master` · `metering_master` → 공유 마스터. 필수 참조 허용
- `account` · `workspace` · `ops` → 모든 모듈의 토대. 감사에서 예외 처리

즉 **"MES를 꺼도 ERP가 돌아간다"는 성립해야 하지만, "core를 꺼도 ERP가 돌아간다"는 성립하지 않는다.** core는 끌 수 있는 모듈이 아니다.

## 5. 보존과 초기화

주간 세대 교체에서 core의 처리는 하위 모듈마다 다르다.

| 하위 모듈 | 세대 교체 시 |
|---|---|
| `account` | **보존.** 계정·역할은 실습 데이터가 아니다 |
| `workspace` | 공간·모듈 설정·대시보드 배치는 **보존**. 세대 행만 추가 |
| `factory_master` · `item_master` · `metering_master` | **교체.** 세대 범위 업무 기준정보다 |
| `ops` | 작업 실행·감사는 **보존**. 요청 결과는 세대 교체 |

기준정보를 교체하는 이유는 사용자가 품목·설비를 직접 등록해 보는 것도 학습 범위이기 때문이다. 계정까지 날리면 로그인이 풀린다.

## 6. 신규 제안 없음

core는 현재 구조로 충분하다. 추가 제안이 없는 이유를 남긴다.

| 흔히 추가하는 것 | 판단 |
|---|---|
| 회사·법인 마스터 | 사업장으로 충분하다. 다법인은 범위 밖 |
| 메뉴 관리 테이블 | 메뉴는 코드로 관리한다. FS-005에서 배제 결정 |
| 공통 코드 그룹·상세 | 상태값은 CHECK와 코드 목록으로 관리한다. 테이블화하면 상태 전이 규칙이 데이터로 흘러간다 |
| 파일·첨부 | 파일 저장소가 필요하다. 범위 밖 |
| 다국어 메시지 | 범위 밖 |

**공통 코드를 테이블로 만들지 않은 것**은 의식적 결정이다. 화면에서 코드값을 추가했다고 새로운 업무 전이가 자동 허용되면 안 된다. 상태 전이는 코드가 아니라 트랜잭션 계약이 정한다.

## 7. 미확정 / 후속

- 설비 계층(상위 설비)과 작업장의 관계는 실제 화면 설계에서 확인한다.
- 단위 환산은 첫 실습에서 EA만 쓴다. 다단위 환산은 사용 시점에 검증한다.
- BEMS 활성화 시 `metering_master`의 소유 모듈 분리 규칙을 재확인한다.

## 8. 후속 변경 — 게스트 별칭과 접속 이력 (FS-027, 2026-09-29)

- 게스트 생성 `POST /guest-sessions`는 별칭(공백 제거 후 2~20자) 필수. 저장은 새 컬럼 없이 `core.audit_event`(`guest_session.created`)의 `summary.nickname`.
- 관리자 조회 `GET /admin/guest-visits`(P-07 "게스트 접속"). 정리된 공간은 `workspace_snapshot_id`로 남는다.
- 보관: 정리 작업(`cleanup_expired_guests`)이 90일 지난 기록의 `nickname` 키만 지운다 — `core.audit_event` 불변 정책의 유일한 예외.
- 결정서: [FS-027](../../plan/게스트별칭_접속이력_FS-027.md)

## 9. 후속 변경 — 런처 평가 (FS-040, 2026-10-01)

- `ops`에 **`core.app_review`**(별점·한줄평) 1테이블. 범위 global — 공간·세대 FK가 없어 게스트 정리·세대 초기화와 무관하게 남는다. 회원만 `core.app_user` FK.
- 1회 규칙: 회원 계정당 · 게스트 공간당 · 게스트 별칭당(솔루션별). 근거·API는 [FS-040](../../plan/런처평가_한줄평_FS-040.md).
