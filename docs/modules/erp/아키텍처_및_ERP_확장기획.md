# 아키텍처 결정 및 ERP 확장 범위
작성일: 2026-09-16
결정: 개인 서버에서 운영하는 단일 저장소 기반 모듈형 모놀리스. 웹 앱 하나, 업무 API 하나, PostgreSQL 하나. 개인 프로젝트의 코드·설정·가상 데이터를 독립적으로 작성한다. 회사 FEMS의 서버 구성과 코드 재사용을 전제로 하지 않는다.

## 기술 구성
- 프론트엔드: React + TypeScript + Vite. React Router, TanStack Query, Tailwind CSS. Recharts로 기본 차트 구현.
- 백엔드: Python + FastAPI. 모듈별 APIRouter와 업무 서비스 함수. SQLAlchemy + Alembic으로 DB 접근 및 마이그레이션.
- 데이터: PostgreSQL. core/mes/fems/bems/qms/wms/erp 스키마로 책임 구분. 초기 시계열도 PostgreSQL 사용. 실제 용량 측정 후 파티셔닝 여부 결정.
- 인증: 동일 출처 HttpOnly/Secure 쿠키의 서버 세션, CSRF 방어, 역할 권한과 사용자별 체험 범위 검사.
- 배포: Linux + Docker Compose. Caddy가 HTTPS, 정적 웹 파일 제공, /api 역방향 프록시를 담당한다. 상시 컨테이너는 Caddy, FastAPI 앱, PostgreSQL의 3개로 구성한다. React는 빌드된 파일로 제공하므로 별도 Node 서버가 없다.
- 작업 실행: 호스트 systemd timer가 같은 앱 컨테이너의 CLI 명령을 실행한다. 상시 worker 컨테이너는 두지 않는다. 주간 초기화와 정기 외부전송 처리는 PostgreSQL 실행 이력·작업 테이블을 사용한다. 주간 초기화는 날짜별 실행 키와 DB 잠금으로 중복 방지하고, 미실행 주차를 확인해 한 번만 따라잡는다. 외부 발행 요청은 업무 저장과 같은 트랜잭션에 outbox 행을 기록한다. 외부전송 처리 명령은 예를 들어 1분 간격으로 실행하며 중복 실행 잠금, 재시도 횟수, 다음 시도 시각, 응답 불명 시 조회 절차를 갖춘다. 초 단위 처리가 필요해질 때만 동일 이미지의 worker를 분리한다.
- 초기화: 새 예시 세대 생성→검증→활성 세대 전환. 전환 시 입력 잠금과 오래된 요청의 세대 검사. 실패 시 기존 세대 유지. 학습 기록은 체험 행 대신 안정적인 학습 ID 참조.
- PWA: 동일 프론트엔드에 포함. 계정별 업무 응답은 오프라인 캐시에서 제외. 알림함이 기본이며 Web Push는 추가 전달 경로.
- 첨부 증빙: 영속 볼륨에 보관, DB에는 메타데이터 저장. 인증된 다운로드와 파일 검증 적용. 외부 저장소가 필요해지면 교체.
- 테스트: 백엔드 pytest와 실제 PostgreSQL 통합 테스트, 핵심 사용자 여정 Playwright. 금액·재고·권한·초기화·발행 재시도 검증에 집중.
- 버전: 착수 때 호환 가능한 지원 버전을 확인해 잠금 파일로 고정한다.

## 코드 구조
frontend/src/{app,shared,modules/{mes,fems,bems,qms,wms,erp,learning}}
backend/app/{core,modules/{mes,fems,bems,qms,wms,erp,learning},jobs,integrations}
backend/migrations
seed
tests
docs
compose.yaml

모듈은 자기 데이터만 변경한다. 다른 모듈 변경은 해당 모듈의 업무 함수를 호출한다. 같은 DB 내 재고·실적·전표 정합성은 명시적 트랜잭션으로 처리한다. 외부 HTTP 요청은 DB 트랜잭션 안에서 기다리지 않는다.
공유 DB이지만 사용자별 체험 공간과 데이터 세대가 모든 업무 요청에 적용된다. 고유 제약도 해당 범위를 포함한다. 모듈별 DB 복사나 내부 HTTP 호출을 만들지 않는다.

## ERP v1
1. 거래처·품목·과세구분·적용세율·계정과목·회계기간 기준정보.
2. 매입매출: 거래 문서, 부분 입고/출하, 반품, 공급가액·부가세·합계, 원본 증빙, 마감.
3. 채권채무: 수금/지급과 문서별 배분, 미수/미지급 잔액, 만기·연령 현황.
4. 기초회계: 거래별 전표 생성, 차변/대변 검증, 전기, 역분개, 총계정원장·거래처 원장·합계잔액시산표, 기간마감.
5. 전자세금계산서: 모의 발행, 외부 테스트 API, 매출 정발행과 수정발행의 지원 시나리오, 국세청 전송 상태 조회. 매입 증빙 입력/가져오기와 대사.
금액은 Decimal/NUMERIC 사용. 세율·반올림·작성일·수정사유는 하나의 검증 정책으로 관리한다. 증빙 발행만으로 매출/매입을 중복 인식하지 않도록 업무 문서와 전표 연결 키에 고유 제약을 둔다.
지원할 과세·영세·면세 및 수정발행 사유별 규칙은 구현 시 국세청과 사업자 문서로 확인하고 지원 범위를 명시한다. 면세 전자계산서는 전자세금계산서와 문서 종류를 구분한다.
급여·고정자산·연결결산·법인세 신고·은행 자동 수집·실제 제조원가 결산은 후속 범위다.

## 전자세금계산서 연결 결정
우선 외부 사업자는 팝빌로 선정하고 TaxInvoiceProvider 경계만 둔다. 두 구현은 MockProvider와 PopbillProvider이며, 그 외 범용 플러그인 구조는 만들지 않는다.
가상 사업장에서는 모의 발행과 테스트 서버만 사용한다. 운영용 자격정보를 주입하지 않는다.
실제 발행 기능은 사업자 등록·서비스 계약·인증·과금·사용자 발행 권한이 준비된 별도 운영 환경에서 활성화한다. 사용자가 발행할 문서를 검토한 뒤 명시적으로 발행 요청해야 한다.
실제 회계자료와 세금계산서 이력에는 주간 초기화를 적용하지 않는다. 실서비스 전환 시 DB·비밀정보·외부 엔드포인트를 체험 환경과 물리적으로 분리한다. 코드 저장소는 동일하다.
네트워크 시간초과는 발행 실패로 단정하지 않는다. 업무 문서 키로 사업자 상태를 조회하고 중복 전송을 차단한다. 국세청 전송 결과는 별도 상태이며 실패 알림과 재처리 이력을 남긴다.

## 개인 서버 운영 원칙 — 최종 수정
- 회사 FEMS는 업무 개념을 참고하는 자료다. 회사 코드·고객 자료·접속정보·브랜드·운영 설정을 개인 서비스로 옮기는 것을 기본 작업 범위에 포함하지 않는다.
- 기본 배포 대상은 Docker를 지원하는 Linux 개인 서버다. 실제 OS, 도메인, RAM/디스크, 인터넷 접근 경로는 배포 설계 시 확인한다. 특정 CPU/RAM으로 충분하다고 미리 단정하지 않는다.
- 외부 공개 포트는 웹 80/443으로 제한하고 API 및 DB 포트는 호스트에 공개하지 않는다. 관리자 서버 접속 경로는 별도로 제한한다.
- Compose 하나로 빌드·실행하고 이미지 버전과 DB 마이그레이션을 관리한다. DB 마이그레이션은 배포 단계에서 한 번 실행한다. 이전 이미지로의 복귀와 DB 복원 절차를 구분한다.
- PostgreSQL과 첨부파일은 영속 볼륨에 보관한다. 매일 DB와 첨부파일을 백업하고 서버 외부에 암호화 사본을 보관한다. 백업 보관 정책과 실제 복원 시험을 운영 완료 조건으로 둔다.
- 컨테이너 재시작 정책, 상태 점검, 크기 제한 로그, 작업 실패 기록을 둔다. 예약 실행 실패 및 백업 실패를 운영 알림 대상으로 삼는다.
- PostgreSQL 기반 시계열 데이터의 생성량과 보존 기간을 제한한다. 데이터가 늘면 측정 결과를 바탕으로 인덱스·집계·파티셔닝 순서로 개선한다.
- 초기에는 Redis, Kafka, Kubernetes, 별도 시계열 DB, 별도 BFF를 도입하지 않는다.
- 전체 계층은 요청 처리→업무 함수→DB 모델로 구성한다. 반복이 없는 범용 저장소·이벤트 플랫폼과 외부 코드 설치형 플러그인 프레임워크는 만들지 않는다. 내부 모듈 등록·활성화·위젯 구성을 지원한다. 외부 세금계산서 연결만 모의/테스트/운영 경계를 명확히 한다.
- 단일 서버는 고가용성이 아니다. 서버 장애 동안 서비스 중단을 허용하고 백업과 재설치 가능한 배포로 복구하는 것을 v1의 운영 수준으로 정한다.
