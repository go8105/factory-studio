# FS-005e ERP 모듈 공통 설계서

작성일: 2026-09-21. 상태: 설계 초안. 메타데이터 미반영.
기준: [FS-005a 차분 설계](../../architecture/차분설계_게스트_ERP_프로세스맵_FS-005a.md) 3장, [FS-005d 모듈·하위 모듈 구조](../../architecture/모듈_하위모듈_구조_FS-005d.md), `references/ERP_기본_DB설계_PostgreSQL_v1.0.xlsx`(41테이블).
성격: ERP를 **독립 솔루션**으로 성립시키기 위한 모듈 설계서. 4장의 격차 분석과 5장의 제안이 핵심이다.

---

## 1. 이 모듈은 무엇인가

**판매계획부터 매출 인식까지를 담당하는 판매·출하 솔루션이다.**

포털 안의 한 단계가 아니라 **그 자체로 완결된 제품**으로 설계한다. MES를 켜지 않아도 ERP만으로 "거래처를 등록하고, 계획을 세우고, 수주를 받고, 내보내고, 매출을 인식한다"가 성립해야 한다.

단, **데이터는 공유 마스터를 쓴다.** 품목은 `core.item`이 소유하고 ERP는 참조한다. 화면과 문서는 독립, 마스터는 한 벌이다.

## 2. 하위 모듈

| 하위 모듈 | 소유 테이블 | 참조 |
|---|---|---|
| `erp_master` 기준정보 | 거래처 | 품목 |
| `sales_plan` 판매계획 | 판매계획, 판매계획 라인 | 품목 |
| `sales_order` 수주 | 수주, 수주 명세 | 거래처, 품목 |
| `shipping` 출하 | 출하지시, 출하지시 명세, 출하, 출하 명세 | 패킹 단위, 완제품 입고 |
| `revenue` 매출 | 매출 | 출하, 거래처 |

현재 소유 테이블은 10개다.

## 3. 업무 규칙

트랜잭션 계약은 [FS-006a](../../architecture/트랜잭션_락순서_확장_FS-006a.md)에 있다. 요약하면 셋이다.

| 규칙 | 내용 |
|---|---|
| TX-07 출하지시 | 수주 라인별 `Σ 지시수량 ≤ 수주수량`. 초과 지시 거부 |
| TX-08 출하 확정 | 패킹 단위가 입고 완료 상태이고 다른 출하에 쓰이지 않았을 것. `(S, packing_unit_id)` UNIQUE로 이중 출하 차단 |
| TX-09 매출 인식 | 출하 확정과 **같은 트랜잭션**. 출하당 정확히 1건 |

**매출은 출하 시점에 인식한다.** 수주 시점이 아니다. 이게 ERP 학습의 핵심 포인트다.

잠금 순서는 패킹 단위(5) → 수주·출하·매출(6)이다. 패킹을 먼저 잠근다.

## 4. 참조 설계서 대비 격차

참조 설계서는 41개 테이블이다. 현재 ERP-1은 10개다. 무엇이 왜 빠졌는지 정리한다.

| 참조 영역 | 참조 테이블 | 현재 | 판단 |
|---|---:|---|---|
| 공통(회사·사용자·권한·코드·감사) | 8 | core가 담당 | **의도적 제외.** 중복이다 |
| 기준정보 | 6 | 거래처 1개만 | **격차.** 단가 마스터 없음 |
| 견적 | 5 | 없음 | **격차.** 영업 흐름의 시작이 빠졌다 |
| 판매 | 3 | 수주 2개 | 분할청구계획 없음 |
| 구매 | 2 | 없음 | ERP-2로 미룸 |
| 재고 | 4 | 없음 | WMS로 미룸 |
| 채권채무 | 2 | 매출 1개 | 반품·차감전표 없음 |
| 자금 | 2 | 없음 | ERP-2로 미룸 |
| 세금계산서 발행자료 | 3 | 없음 | **재검토 필요.** 5장 참조 |
| 기초회계 | 4 | 없음 | ERP-3로 보류 |
| 문서 첨부 | 2 | 없음 | 범위 밖 |

### 4.1 참조 설계서에서 배울 설계 원칙 3가지

테이블을 가져오지 않더라도 **원칙은 가져와야 한다.**

**(1) 단가는 마스터에서 전표로 복사한다**
참조의 `ITEM_PRICE_MT`는 "적용된 값은 전표에 복사"로 명시한다. 단가 마스터만 참조하면 단가가 개정될 때 과거 수주 금액이 소급 변경된다. FEMS에서 계수 스냅샷을 저장한 것과 **완전히 같은 원리**다.
→ 현재 `erp.sales_order_line.unit_price`가 이미 값을 들고 있으므로 원칙은 지켜지고 있다. 단가 마스터를 추가하더라도 이 구조를 유지한다.

**(2) 잔량은 파생, 원장이 원천**
참조의 `STOCK_BALANCE_MT`는 "파생 잔량", `STOCK_LEDGER_HT`는 "불변 원장"이다. 잔량을 직접 수정하지 않는다.
→ 재고를 도입할 때(WMS) 반드시 이 구조를 따른다.

**(3) 다형 문자열 참조를 쓰지 않는다**
참조의 `DOC_FILE_DT`는 "다형 문자열 참조 사용 안 함"을 명시하고 명시적 FK로 연결한다.
→ **이건 우리 설계와 충돌한다.** FS-005c의 FEMS 증빙 설계에서 `target_type + target_seq` 다형 참조를 쓰기로 했었다. ERP에 문서 첨부를 도입하면 같은 문제가 반복된다. 도입 시 명시적 FK 방식을 택한다.

### 4.2 지금 구조에서 어색한 지점

참조와 대조하며 드러난 것이다.

- **`erp.sales_record`가 "매출"이라기엔 얇다.** 참조의 `TRADE_BILL_MT`는 차감전표(반품·할인)를 포함한다. 현재는 출하당 1건 생성이 전부라 **반품이 발생하면 표현할 방법이 없다.**
- **판매계획이 수주와 연결되지 않는다.** 계획 대비 실적 비교를 조회 계산으로 하기로 했는데, 참조에는 `BILL_PLAN_MT`처럼 계획을 실적에 묶는 장치가 있다. 현재는 품목·연월로만 대사한다.
- **거래처가 고객 전용이다.** 참조는 고객/공급업체 플래그를 동시에 지정할 수 있게 했다. 현재 `partner_kind`는 배타적이다. 구매를 안 하므로 당장 문제는 아니다.

## 5. 제안

ERP를 "독립 전문 솔루션"으로 보이게 하려면 **최소 두 가지가 필요하다.** 셋으로 나눠 제안한다.

### 5.1 넣기를 제안 — 2개 영역, 4테이블

**A. 견적 (`quotation` 하위 모듈 신설) — 3테이블**

`erp.quotation`, `erp.quotation_line`, `erp.quotation_status_history`

ERP를 열었는데 수주부터 시작하면 **영업 솔루션으로 보이지 않는다.** 실제 판매 업무는 견적에서 시작하고, 견적→수주 전환이 ERP에서 가장 자주 보여주는 화면이다. 참조 설계서도 견적에 5테이블을 쓴다.

핵심 규칙은 참조에서 그대로 가져온다. **확정된 견적본은 수정하지 않고 새 개정본으로 복제한다.** 이건 우리가 이미 여러 곳에서 쓰는 "확정 후 불변" 원칙과 같다.

MTS와도 충돌하지 않는다. 견적은 수주의 선행 문서일 뿐 생산을 촉발하지 않는다.

**B. 단가 마스터 (`erp_master`에 추가) — 1테이블**

`erp.partner_item_price` — 거래처·품목별 판매 단가와 적용 기간

지금은 수주 라인에 단가를 매번 직접 입력한다. 실무에서는 거래처별 단가가 정해져 있고 전표가 그걸 **복사**한다. 이 구조가 없으면 "왜 단가를 매번 손으로 치나요"라는 질문을 받는다.

테이블 1개로 ERP의 완성도가 눈에 띄게 올라간다. 비용 대비 효과가 가장 좋다.

### 5.2 판단 필요 — 세금계산서

제가 이전에 **"팝빌 연동은 제외"** 라고 했는데, 참조 설계서를 보고 판단을 수정해야 합니다.

참조의 `TAX_DRAFT_MT`는 **연동이 아니라 "수동 발급용 자료"** 입니다. 명시적으로 "서명·전송·국세청 조회 없음"이라고 적혀 있습니다. 즉 **외부 연동 없이 전표에서 발행 자료를 만들고, 발급 결과를 사용자가 확인·등록**하는 구조입니다.

이거라면 구현 가능하고, 사업자 등록도 필요 없고, ERP다움을 크게 높입니다. 제가 "연동"이라는 단어에 걸려 잘못 판단했습니다.

→ `erp.tax_invoice_draft` 1테이블로 축소해 넣는 것을 검토할 만합니다. 다만 **지금은 우선순위가 견적·단가보다 낮습니다.**

### 5.3 넣지 않기를 제안

| 영역 | 이유 |
|---|---|
| 구매·발주 | ERP-2. 매입이 없으면 발주도 성립하지 않는다 |
| 재고·수불원장 | WMS 소유. 여기 넣으면 나중에 이관해야 한다 |
| 수금·지급·배분 | ERP-2 |
| 기초회계(계정·전표·분개) | ERP-3. 복식부기는 별도 프로젝트 규모다 |
| 문서 첨부 | 파일 저장소가 필요하다. 범위 밖 |
| 회사·사용자·권한·코드 | core 중복 |

### 5.4 신규 엔티티 목록

검증기가 읽는 기준 목록이다. 표기를 바꾸면 정적 검증이 깨진다.

| 엔티티 | 하위 모듈 | 역할 |
|---|---|---|
| `erp.quotation` | quotation | 견적서 헤더. 확정본은 개정본으로 복제 |
| `erp.quotation_line` | quotation | 견적 명세 |
| `erp.quotation_status_history` | quotation | 상태 전이 불변 이력 |
| `erp.partner_item_price` | erp_master | 거래처별 품목 단가 |

### 5.5 규모

| 구분 | 수 |
|---|---:|
| 현재 ERP | 10 |
| 견적 3 + 단가 1 | +4 |
| **ERP 합계** | **14** |
| 전체 테이블 | 60 → **64** |

하위 모듈은 5개에서 **6개**가 된다 (`quotation` 추가).

## 6. 화면 구성 (FS-008a 입력)

| 하위 모듈 | 주요 화면 |
|---|---|
| 기준정보 | 거래처 목록·등록, 거래처별 단가, 품목 조회(참조) |
| 견적 | 견적 목록, 견적 작성·개정, 견적→수주 전환 |
| 판매계획 | 계획 목록, 품목별 계획수량 입력, 계획 확정 |
| 수주 | 수주 목록, 수주 등록, 라인별 잔여 지시수량 |
| 출하 | 출하지시 생성, 패킹 단위 선택, 출하 확정 |
| 매출 | 매출 목록, 출하-매출 대사, 계획 대비 실적 |

**"참조" 표시가 핵심이다.** 품목은 ERP 화면에 보이지만 core 소유라 여기서 수정할 수 없다. 화면에 그 사실을 표시한다.

## 7. 미확정 / 후속

- 견적·단가 테이블의 컬럼별 타입·제약은 채택 결정 후 확정한다.
- 반품·차감전표는 ERP-2와 함께 재검토한다. 지금은 반품을 표현할 수 없다는 점을 명시만 해둔다.
- 거래처 고객/공급업체 동시 지정은 구매 도입 시 변경한다.
- 세액 계산 정책 함수는 단일 함수로 관리한다. 호출부에서 재계산하지 않는다.
- 문서 첨부 도입 시 다형 문자열 참조가 아니라 명시적 FK를 쓴다.
