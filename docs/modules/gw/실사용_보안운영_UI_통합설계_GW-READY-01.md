## 3. 화면 구조와 대표 흐름

### 3.1 직원

- **내 업무**: 현재 허용된 기안/결재·일정·알림·채팅 요약. 개인 체험과 실제 회사 사용 표시 구분. 표시되지 않은 작업도 서버의 객체 ACL이 최종 결정.
- **내 계정 보안**: 인증 앱 등록 여부, 백업 코드 남은 수, 최근 본인 보안 사건, 다른 세션 로그아웃. 활성 TOTP 비밀/타인 인증 수단 조회 없음.
- 로그인: 비밀번호 확인→필요한 경우6자리 인증→검증된 업무 세션. 비밀번호만 확인한 중간 상태는 업무 API에 사용할 수 없음.
- 인증 앱 등록: 현재 비밀번호/현재 세션 확인→앱 등록 QR 또는 설정 키→유효한 번호→백업 코드 한 번 표시→보관 확인. 앱 등록 확인 전 운영 준비 완료 아님.
- 분실: 비밀번호+미사용 백업 코드→복구 전용 제한 세션→새 MFA 등록→기존 세션·이전 코드 회수→새 로그인. 복구 전용 세션으로 결재/문서 열람/역할 변경 불가.
- 기안·결재·댓글 등 현재 업무 입력 계약은 유지한다. MFA 후에도 기안자·배정·위임·회사 범위·버전을 매 요청 재검증한다.

### 3.2 관리자

- **회사 시작 안내**: 회사/부서 확인→직원 본인 연결→보안 수단→운영 기준→백업/복원 시험→시범 업무. 운영 준비 체크리스트이며 학습 진도/채점이 아님.
- **직원 연결**: 기존 G-07을 재사용. 계정·HR 사번·GW 직원·연결·역할의 차이를 안내. 관리자 본인 확인이나 직원 동의를 대신 체크하는 버튼 없음.
- **운영 준비**: 필요한 직원 수/실제 연결·MFA 등록 수, 책임자, 정책 버전, 최신 백업 나이, 복원 결과와 손실 구간, 미해결 차단 사유를 서버 계산. 운영자가 초록 체크를 수동 입력하는 화면이 아님.
- **보관·복구 기준**: 초안/검토/새 버전 적용. RPO/RTO·백업 간격/기간·문서/감사 검토 기한·담당자. 현재 값/다음 값/영향/사유 확인. 최근5분 이내 추가 인증 필요.
- **백업·복구 기록**: 백업 완료와 복원 검증을 구분. 실제 실행 서명·manifest·head·회사 범위·시각·hash·회수 재적용 결과 확인. 비밀번호/암호화 키/원문 출력 금지.
- **보관 검토**: 허용된 기록만 원문 접근. 관리자는 비공개 문서 제목/본문 대신 식별자·기한·담당자 검토 상태만 봄. 보존 중지는 회사 범위에서도 가능하며 사유/기간/해제 이력 보존.

### 3.3 저장·취소·실패

- 서버 성공을 받기 전 ‘저장 완료’ 표시 금지. 작업 중 중복 클릭/공간 전환을 막고 오래된 응답 폐기.
- 불명확한 쓰기는 같은 내용/같은 멱등 키로 현재 상태 확인. 화면/브라우저 종료를 가로지른 복구가 가능하도록 서버의 ‘내 요청 상태’만 조회하며 민감한 본문/OTP/비밀번호는 브라우저 영구 저장하지 않음.
- 취소는 저장 전 값만 버리고 서버의 확정 원본은 바꾸지 않음. 미저장 확인의 ‘계속 편집’은 원래 입력과 포커스 복원. Escape도 같은 규칙.
- OTP 잘못됨/이미 사용/기기 시간 차이/시도 초과/만료는 안전한 오류와 다음 행동을 표시. 계정 존재 여부를 외부에 노출하지 않음.
- 정책409 충돌은 기존 입력을 유지하고 현재 서버 버전과 차이를 검토한 뒤 새 요청. 삭제/회수 같은 고위험 명령을 자동 재실행하지 않음.

## 4. 인증·복구·SSO의 범위

- core는 인증 수단·세션·subject를 소유하고 GW는 직원 연결·역할·문서 ACL을 소유한다. core→GW FK와 업무 스키마 간 FK를 만들지 않는다.
- 회사 운영 모드는 서버 환경에서 정한다. PUBLIC_DEMO/TEAM_TEST/COMPANY를 클라이언트 체크박스로 승격하지 못한다. 실제 COMPANY는 TLS·안전한 쿠키·별도 암호화 키·인증 어댑터 미설정 시 시작/회사 업무를 닫는다. TEST의 모의 IdP/시계/HTTP 예외는 COMPANY에서 거부.
- 관리자 권한 변경·본인 연결 관리·보안 수단 변경·정책 적용·복구/시범 전환에는 최근5분 인증을 다시 확인한다. 일반 직원의 매 승인에 반복 MFA를 강제하는 것은 기본값이 아니며 회사 정책으로 추가 가능.
- 기본 TOTP는 검증된 라이브러리 사용,30초/6자리·±1구간·사용 step 재사용 차단, 계정/네트워크별 시도 제한. 비밀은 별도 키로 암호화하고 백업과 키를 분리한다.
- SSO는 선택한 issuer/client/redirect URI를 서버에 고정하고 서명·issuer/audience/nonce/state/PKCE/만료를 검증한다. IdP의 MFA 증거를 무조건 신뢰하지 않고 공급자별 승인된 정책이 있을 때만 assurance로 인정한다. 불충분하면 로컬 MFA를 추가한다.
- IdP subject는 기존 계정과 명시 연결. 자동 가입/메일 기반 병합/관리 역할 동기화는 기본 범위 밖. IdP 중단 시 MFA 없이 로컬 비밀번호로 우회하지 않음.
- 관리자 복구 수단은 최초 준비 때 별도 보관. 사용 시 만료·한 번 사용·사유·운영자/본인 확인·감사. 복구 담당이 혼자인 최소 구성의 한계를 숨기지 않음. 키까지 분실하면 복구 보장 불가.

## 5. 백업·보존·운영 준비

- DB 백업+현재 code/head/config/key 식별자+manifest를 암호화한다. 실제 비밀·본문은 manifest와 앱 로그에 넣지 않는다. 저장 위치의 비밀은 환경/비밀 저장소에 둔다.
-30분 기본 스케줄 템플릿과 실패/오래된 백업 경고를 구현한다. 사용자 컴퓨터의 스케줄·실서버·외부 저장소를 이 작업에서 몰래 바꾸지 않는다. 첫 설치 명령과 확인을 제공한다.
- 복원은 새 폐쇄 DB/저장소에서 실행. 행/hash/FK·마지막 사건·head·세션 무효화·백업 이후 회수 대조·2계정 업무/거부를 검사한다. 서명한 실행 결과만 증거로 반영하고 목표 초과/누락을 통과로 바꾸지 않음.
- 복구 책임자는 백업과 별도로 계정 정지·역할 회수 이력을 보관한다. 복원 시 되살아난 권한을 대조·회수하기 전 직원 접속과 외부 worker를 열지 않는다.
- 운영 기준과 보존 중지 변경은 감사·추가 인증·버전 확인. 데이터 보존 기간은 삭제 예약이 아니라 검토 기한으로 설명한다. 확정 결재·사건·회수 이력은 기본적으로 자동 삭제하지 않음.
- 업무 보관본 내보내기는 기존 본문 ACL을 그대로 지킨다. 승인된 암호화 백업은 운영 책임자의 별도 권한과 취급 절차로 관리한다. 보안 관리자 API에서 전사 원문을 읽는 우회 경로를 만들지 않는다.
- 삭제 기능을 몰래 추가해 ‘보존 완료’를 만들지 않는다. 실제 삭제/익명화는 법적/업무 보존 조건·외부 사본까지 포함한 별도 상세 확정이 필요한 확장으로 명시한다. 초기 회사는 보관·보존 중지·기한 검토로 운영한다.

## 6. 변경 관리와 구현 묶음

전체 설계 확인 뒤 **GW-READY-02 한 구현 ID** 안에서 A~E 순서로 진행한다. 내부 묶음마다 승인 질문을 반복하지 않고 WIP/검사로 추적한다. 범위 변경이나 외부 서비스 계약·실제 운영 적용이 필요할 때만 별도로 확인한다.

| 순서 | 구현 | 완료 기준 |
|---|---|---|
| A | core MFA/단계 인증/시도 제한·비밀 관리·세션 회수 | 비밀번호 단독 우회0, OTP/코드 동시 재사용0, 실패 횟수 rollback 누락0, 기존 체험/로그인 회귀 |
| B | 계정 복구·긴급 복구·OIDC 선택 연결 | 제한 세션 업무 차단, 모든 세션 회수, subject 탈취/메일 병합0, 모의 IdP 증거와 실제 공급자 검증 구분 |
| C | GW 운영 기준·보관 검토/보존 중지·서명된 증거/운영 게이트 | 정책 새 버전/CAS/현재 권한, 증거 위조/만료·미설정COMPANY 차단 |
| D | 암호화 백업 실행/스케줄 템플릿·폐쇄 복원·회수 기록 재적용 | 별도 복원 자료 보존/누락 탐지·권한 부활 차단·실측/목표 구분 |
| E | 실제 제품 화면/도움말·4대 UI 검증·통합/인수 | 신규/기존 회귀·10인 실제HTTP/Chrome·키보드/390px/오류·전체 기록, 로컬 main 반영 |

각 DB 변경은 새 migration과 현재/목표 schema·Excel·ERD를 같은 작업에서 갱신한다. 적용된 `gw_wms_merge` 이전 revision은 수정하지 않는다. 혼합 버전 배포/rollback·코어 인증 변경의 HR/Flow 영향까지 검사한다. 기존 Flow 프런트7 실패는 원인 분석/범위 확인 후 같은 구현 ID에서 공통 인증 영향 여부를 분리하고, 미해결 상태를 전체 CI 성공이라고 하지 않는다.

## 7. 실제 사용 가능 판정

1. 제품 구현과 합성 검사 통과: 구현된 기능만 완료로 표시.
2. COMPANY 배포 템플릿·운영 점검 통과: 도메인/TLS/쿠키·키 보관·DB/백업 저장소·담당자·실시각/메일 등 선택 연결을 실제 확인.
3. 실제 대표 기기에서 MFA 등록·로그인·휴대폰 분실·복구,2계정 기안/승인·퇴사/연결 회수·권한 변경,10인 부하와 복구 목표 확인.
4. 회사가 초기값/담당자/보관 장소/업무 범위를 확인한 뒤 인수. 실회사/기기가 아직 없으면 준비 가능한 산출물까지만 완료로 표시한다.

사업 시점의 실제 환경·책임자 확인을 소프트웨어 개발로 대체할 수는 없다. 대신 기본 인증/복구 경로와 설치·운영 절차를 구현하고, 마지막에 필요한 실제 확인만 남기는 것이 이 설계의 목표다.
